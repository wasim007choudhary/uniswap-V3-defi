# 5. Dissecting `mul512()`
>nOTE: Also read **notes/CoreLib/MyCustomFullMath_mul512.md** more only mul512 dive. Actually go and read that and come back

The implementation is:

```solidity
function mul512(uint256 a, uint256 b) internal pure returns (uint256 high, uint256 low) {
    assembly ("memory-safe") {
        let mm := mulmod(a, b, not(0))
        low := mul(a, b)
        high := sub(sub(mm, low), lt(mm, low))
    }
}
```

Only **three assembly instructions**.

Yet these three lines compute a complete **512-bit multiplication**.

Let's understand every one.

---

# Step 1 — Compute the Lower 256 Bits

```solidity
low := mul(a, b)
```

This is the multiplication every Solidity developer already knows.

```
low = a × b
```

However,

the EVM only keeps the **lowest 256 bits**.

Anything above bit 255 disappears.

Example:

```
Real Product

↓

+----------------------+----------------------+
|   Upper 256 bits     |   Lower 256 bits     |
+----------------------+----------------------+

                     ▲
                     │

mul()

↓

Only this part survives.
```

So after this instruction,

we know

```
lowerPart
```

but we still have no idea what the upper 256 bits are.

---

# Child Analogy

Imagine pouring water into a bucket.

The bucket can only hold

```
256 litres.
```

If you pour

```
400 litres
```

the bucket keeps

```
256 litres
```

and the rest spills away.

`mul()` only gives us the water that stayed inside the bucket.

The spilled water represents

```
upperPart.
```

---

# Step 2 — Why Can't We Just Ask For UpperPart?

The EVM has instructions like

```solidity
mul
```

and

```solidity
mulmod
```

It does **not** have

```solidity
mul512
```

or

```solidity
getUpper256Bits()
```

There is simply no opcode that returns the missing half.

So OpenZeppelin has to reconstruct it mathematically.

---

# Step 3 — The Clever Trick

Instead of trying to recover the missing bits directly,

OpenZeppelin computes another version of the multiplication.

```solidity
let mm := mulmod(a, b, not(0))
```

This looks mysterious.

Let's decode it.

---

# What Is `mulmod`?

`mulmod` performs:

```
(a × b)

mod

m
```

without overflowing.

General form:

```solidity
mulmod(a, b, modulus)
```

returns

```
(a × b) % modulus
```

---

Example:

```
mulmod(10, 7, 6)

↓

70 % 6

↓

4
```

Unlike

```solidity
mul()
```

it computes the multiplication with full precision before taking the remainder.

This is extremely important.

---

# What Is `not(0)`?

This line confuses many developers:

```solidity
not(0)
```

What is it?

Binary:

```
0

=

000000000000...
```

Applying

```
NOT
```

flips every bit.

```
000000000000

↓

111111111111
```

Every bit becomes

```
1
```

For a uint256,

that equals

```
2²⁵⁶ − 1
```

Therefore

```solidity
not(0)
```

is simply

```
Maximum uint256
```

or

```
2²⁵⁶ − 1
```

---

# Therefore

This instruction becomes

```solidity
mm = (a × b)

mod

(2²⁵⁶ − 1)
```

Notice something.

Previously we computed

```
a × b

mod

2²⁵⁶
```

using

```solidity
mul()
```

Now we compute

```
a × b

mod

(2²⁵⁶ − 1)
```

using

```solidity
mulmod()
```

So we now know the product under **two different moduli.**

---

# Why Two Different Moduli?

This is where the mathematics begins.

We now know:

```
Product mod 2²⁵⁶
```

and

```
Product mod (2²⁵⁶ − 1)
```

That sounds useless.

Surprisingly,

those two remainders uniquely identify the original 512-bit product.

This is exactly what the

```
Chinese Remainder Theorem (CRT)
```

guarantees.

---

# Child Analogy

Imagine someone thinks of a secret number.

They won't tell you the number.

Instead they tell you:

```
When divided by Box A

↓

Remainder = 7
```

and

```
When divided by Box B

↓

Remainder = 12
```

Individually,

those remainders don't tell you much.

Together,

they may uniquely identify the hidden number.

That is exactly what CRT does.

---

# Why CRT Works Here

The two moduli are

```
2²⁵⁶
```

and

```
2²⁵⁶ − 1
```

These numbers are coprime.

Therefore,

CRT guarantees there is exactly one product satisfying both remainders.

In other words,

knowing

```
low

=

Product mod 2²⁵⁶
```

and

```
mm

=

Product mod (2²⁵⁶ − 1)
```

is enough to reconstruct

```
high.
```

---

# The Final Step

Now OpenZeppelin computes

```solidity
high := sub(sub(mm, low), lt(mm, low))
```

At first glance,

this seems impossible to understand.

However,

this single line is simply reconstructing the missing upper 256 bits using the two remainders we already computed.

The next section will derive this formula from scratch and explain exactly why

```solidity
high = mm - low - borrow
```

works.

---

# Key Takeaways

* `mul()` returns only the lower 256 bits.
* The upper 256 bits are not directly accessible in the EVM.
* `mulmod()` computes the multiplication modulo `(2²⁵⁶ − 1)` without overflow.
* `not(0)` is simply `2²⁵⁶ − 1`.
* We now know the product under two different moduli:

  * `2²⁵⁶`
  * `2²⁵⁶ − 1`
* The Chinese Remainder Theorem guarantees these two remainders are enough to reconstruct the complete 512-bit product.
* The final assembly instruction reconstructs the missing upper 256 bits from those two pieces of information.
