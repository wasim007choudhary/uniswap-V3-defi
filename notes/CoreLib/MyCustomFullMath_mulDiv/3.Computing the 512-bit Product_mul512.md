# 4. Computing the 512-bit Product — `mul512()`

The very first executable line inside `mulDiv()` is:

```solidity
(uint256 upperPart, uint256 lowerPart) = mul512(x, y);
```

At first glance this seems simple.

In reality,

this is one of the most impressive parts of the entire algorithm.

It somehow computes a

```
512-bit multiplication
```

while the EVM only supports

```
256-bit integers.
```

The obvious question is:

> **How can we store a 512-bit number when Solidity only has `uint256`?**

The answer is surprisingly elegant.

---

# What Is a 512-bit Product?

Suppose

```
x

×

y
```

produces a huge number.

Instead of pretending it fits into one uint256,

OpenZeppelin stores it as two separate pieces.

```
512-bit Product

=

Upper 256 bits
+
Lower 256 bits
```

or visually,

```
+----------------------+----------------------+
|   Upper 256 bits     |   Lower 256 bits     |
+----------------------+----------------------+

        upperPart              lowerPart
```

Together,

```
[ upperPart | lowerPart ]
```

represent one single 512-bit integer.

Notice something important.

Neither variable contains the entire product.

Only when combined do they reconstruct the complete multiplication.

---

# Child Analogy

Imagine writing a huge phone number.

Unfortunately,

your paper only has room for

```
10 digits.
```

The phone number needs

```
20 digits.
```

Instead of throwing away half the digits,

you use two papers.

Paper 1

```
1234567890
```

Paper 2

```
9876543210
```

Separately,

neither paper contains the full number.

Together,

they represent the entire phone number.

That is exactly what

```
upperPart

and

lowerPart
```

do.

---

# Why Not Just Keep the Lower 256 Bits?

Suppose we multiply:

```
Huge Number

×

Huge Number
```

The lower half alone might look like

```
000011110010...
```

while the upper half contains

```
111001011101...
```

If we only kept the lower half,

everything in the upper half would disappear forever.

That information is required to perform the later division correctly.

So we **must preserve both halves.**

---

# The Goal of `mul512()`

Its purpose is extremely simple.

Given

```solidity
x
```

and

```solidity
y
```

compute

```
x × y
```

without losing a single bit.

The result becomes

```
upperPart

↓

Upper 256 bits

lowerPart

↓

Lower 256 bits
```

---

# But Solidity Doesn't Have uint512

This is where many developers become confused.

There is no type called

```solidity
uint512
```

So how can

```solidity
mul512()
```

possibly return a 512-bit number?

The trick is:

It **doesn't.**

It returns

```
Two uint256 values.
```

Each stores exactly half of the complete product.

Conceptually,

```
512-bit Number

↓

Split

↓

upperPart

+

lowerPart
```

This is exactly the same idea as splitting a very large decimal number.

Example:

```
12345678901234567890
```

can be written as

```
1234567890

|

1234567890
```

Each half is smaller,

but together they still represent the original number.

---

# Why Is This Necessary?

Everything that follows inside `mulDiv()` depends on having the complete product.

For example,

later we subtract the remainder from the **entire 512-bit product.**

If we had thrown away the upper 256 bits,

that subtraction would no longer be mathematically correct.

Similarly,

later we shift bits from

```
upperPart

↓

lowerPart
```

If the upper half never existed,

that operation would be impossible.

So computing the full product is not an optimization.

It is a requirement.

---

# The Interesting Part

Now comes the obvious question.

If Solidity cannot multiply into 512 bits,

then how does

```solidity
mul512()
```

actually compute

```
upperPart
```

and

```
lowerPart
```

using only

```
256-bit arithmetic?
```

The answer involves:

* `mul`
* `mulmod`
* The Chinese Remainder Theorem (CRT)

This is where the real mathematical trick begins.

The next section will dissect the implementation of `mul512()` line by line and explain how OpenZeppelin reconstructs the missing upper 256 bits without ever having a `uint512` type.

---

# Key Takeaways

* A multiplication of two `uint256` values may require 512 bits.
* Solidity has no `uint512`.
* `mul512()` does **not** create a new integer type.
* Instead, it splits the complete product into:

  * `upperPart` (upper 256 bits)
  * `lowerPart` (lower 256 bits)
* Together they represent the full 512-bit multiplication.
* Preserving both halves is essential for the exact division performed later by `mulDiv()`.
