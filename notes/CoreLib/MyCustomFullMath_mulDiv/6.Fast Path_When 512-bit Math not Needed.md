# 7. Fast Path — When 512-bit Math Isn't Needed

After computing the complete product,

the first check inside `mulDiv()` is:

```solidity
(uint256 upperPart, uint256 lowerPart) = mul512(x, y);

// Fast path
if (upperPart == 0) {
    return lowerPart / denominator;
}
```

This is one of the simplest parts of the algorithm,

yet it is an extremely important optimization.

---

# What Does `upperPart == 0` Mean?

Remember,

our complete product is stored as

```text
+----------------------+----------------------+
|   Upper 256 bits     |   Lower 256 bits     |
+----------------------+----------------------+

        upperPart              lowerPart
```

If

```text
upperPart == 0
```

then the picture becomes

```text
+----------------------+----------------------+
|          0           |   Lower 256 bits     |
+----------------------+----------------------+
```

This means

> **The multiplication never exceeded 256 bits.**

In other words,

the entire product already fits inside one uint256.

---

# Child Analogy

Imagine writing a very long number using two notebooks.

Notebook 1:

```text
Upper Half
```

Notebook 2:

```text
Lower Half
```

Now suppose Notebook 1 is completely blank.

```text
Notebook 1

0

Notebook 2

987654321
```

Did you actually need two notebooks?

No.

Everything already fits inside the second notebook.

The first notebook is empty.

That is exactly what

```solidity
upperPart == 0
```

is checking.

---

# Therefore

Instead of running the entire algorithm,

we can simply perform

```solidity
lowerPart / denominator
```

because

```text
Product

=

lowerPart
```

There is no hidden upper half anymore.

---

# Why Is This Safe?

Suppose

```text
upperPart = 0
```

Then

```text
Product

=

0 × 2²⁵⁶

+

lowerPart

=

lowerPart
```

The multiplication never overflowed.

Therefore

```text
Product ÷ denominator

=

lowerPart ÷ denominator
```

Exactly the same answer.

No tricks.

No modular inverse.

No assembly.

No Newton-Raphson.

Just normal Solidity division.

---

# Why Doesn't OpenZeppelin Always Use This?

Because this only works when

```text
upperPart == 0.
```

If

```text
upperPart > 0
```

then

```text
Product

≠

lowerPart
```

The lower 256 bits contain only half of the multiplication.

Dividing only

```text
lowerPart
```

would ignore the upper half entirely.

That would produce a completely incorrect answer.

---

# Example

Suppose the actual product is

```text
+----------------------+----------------------+
|        15            |        200           |
+----------------------+----------------------+
```

The real number is

```text
15 × 2²⁵⁶ + 200
```

If you divide only

```text
200
```

you are pretending the

```text
15 × 2²⁵⁶
```

never existed.

The answer would be completely wrong.

Therefore the fast path is only safe when

```text
upperPart

=

0.
```

---

# Why Is This Optimization Useful?

Many real-world multiplications never overflow.

For those cases,

running:

* remainder subtraction
* bit shifting
* modular inverse
* Newton-Raphson

would all be unnecessary work.

Instead,

OpenZeppelin exits immediately.

This saves gas.

So the function behaves like:

```text
Does multiplication fit inside uint256?

↓

YES

↓

Normal division

↓

Done ✅

↓

NO

↓

Run the complete mulDiv algorithm
```

---

# Key Takeaways

* `upperPart == 0` means the multiplication never exceeded 256 bits.
* The entire product is already stored inside `lowerPart`.
* Normal Solidity division is completely safe.
* No modular inverse or 512-bit division logic is needed.
* This is a gas optimization that avoids unnecessary computation for the common case where overflow never occurred.
