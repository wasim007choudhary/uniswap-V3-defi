# 12. Flipping `twos` — Preparing To Shift The Upper 256 Bits

After extracting the largest power of two, OpenZeppelin executes:

```solidity
assembly ("memory-safe") {
    denominator := div(denominator, twos)
    lowerPart := div(lowerPart, twos)
    twos := add(div(sub(0, twos), twos), 1)
}
```

The first two lines are easy.

```solidity
denominator := div(denominator, twos)
lowerPart := div(lowerPart, twos)
```

Both simply divide by the largest power of two.

The third line, however, looks almost impossible to understand.

```solidity
twos := add(div(sub(0, twos), twos), 1)
```

Let's derive it step by step.

---

# What Is `twos` Right Now?

Suppose

```text
denominator = 40
```

Earlier we extracted

```text
twos = 8
```

because

```text
40

=

8 × 5
```

After dividing,

we now have

```text
denominator = 5
```

Everything is good.

But now OpenZeppelin completely changes the meaning of

```text
twos.
```

Originally

```text
twos

=

8
```

After this line,

```text
twos

=

2²⁵⁶ / 8
```

These are completely different numbers.

The variable is being reused.

---

# Why Do We Need This New Value?

Remember,

we still have

```text
upperPart
```

and

```text
lowerPart.
```

After dividing

```text
lowerPart
```

by

```text
twos,
```

there are missing bits.

Those missing bits must come from

```text
upperPart.
```

To move those bits down,

we need exactly

```text
2²⁵⁶ / twos.
```

That is what this instruction computes.

---

# Step 1 — Compute `0 - twos`

Suppose

```text
twos = 8
```

Normal mathematics says

```text
0 - 8

=

-8
```

But uint256 cannot store

```text
-8.
```

Instead,

it wraps around the

```text
2²⁵⁶
```

clock.

So the result becomes

```text
2²⁵⁶ - 8.
```

Think of a giant clock.

Instead of going below zero,

the number wraps all the way around.

---

# Step 2 — Divide By `twos`

Now compute

```text
(2²⁵⁶ - 8)

÷

8
```

Factor out

```text
8.
```

```text
=

8 × (2²⁵³ - 1)

÷

8
```

Cancel the

```text
8.
```

Result

```text
2²⁵³ - 1
```

---

# Step 3 — Add One

Finally,

```text
(2²⁵³ - 1)

+

1

=

2²⁵³
```

Notice something.

```text
2²⁵³

=

2²⁵⁶

÷

8
```

Exactly what we wanted.

Therefore

```solidity
twos := add(div(sub(0, twos), twos), 1)
```

transforms

```text
8

↓

2²⁵³
```

without ever explicitly writing

```text
2²⁵⁶.
```

---

# Another Example

Suppose

```text
twos = 16
```

Step 1

```text
0 - 16

↓

2²⁵⁶ - 16
```

Step 2

```text
(2²⁵⁶ - 16)

÷

16

=

2²⁵² - 1
```

Step 3

```text
+1

↓

2²⁵²
```

Exactly

```text
2²⁵⁶

÷

16.
```

The trick works for every power of two.

---

# Child Analogy

Imagine a giant circular running track with

```text
2²⁵⁶
```

positions.

You stand at

```text
0.
```

Someone tells you to walk

```text
8
```

steps backwards.

You cannot go below

```text
0.
```

Instead,

you wrap all the way around and land at

```text
2²⁵⁶ - 8.
```

Now divide that distance by

```text
8.
```

Finally,

take one more step.

You end up exactly at

```text
2²⁵⁶ / 8.
```

That is precisely what the assembly instruction computes.

---

# Why Doesn't OpenZeppelin Just Write `2²⁵⁶ / twos`?

Because

```text
2²⁵⁶
```

cannot be represented inside a uint256.

The maximum uint256 is

```text
2²⁵⁶ − 1.
```

So writing

```solidity
2 ** 256
```

is impossible.

Instead,

OpenZeppelin cleverly uses wraparound arithmetic to obtain the same result.

---

# What Happens Next?

Now

```text
twos
```

no longer means

```text
Largest power of two.
```

It now means

```text
2²⁵⁶ / LargestPowerOfTwo
```

This value is immediately used in the next line:

```solidity
lowerPart |= upperPart * twos;
```

That instruction shifts the remaining bits from

```text
upperPart
```

down into

```text
lowerPart,
```

reconstructing the correct 256-bit numerator after the division by the power of two.

---

---

# Key Takeaways

* The meaning of `twos` changes after the denominator is divided.

* Originally:

  ```
  twos = largest power of two dividing denominator
  ```

* Afterwards:

  ```
  twos = 2²⁵⁶ / twos
  ```

* This transformation uses uint256 wraparound arithmetic because `2²⁵⁶` itself cannot be represented.

* The new value is required for shifting bits from `upperPart` into `lowerPart`.

* This is one of the cleverest uses of modular arithmetic in the entire implementation.
