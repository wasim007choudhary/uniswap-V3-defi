# 3. The Problem with Normal Solidity Division

Before understanding `mulDiv()`, we first need to understand **why the normal approach fails.**

Many beginners naturally write:

```solidity
uint256 result = (x * y) / denominator;
```

At first glance, this looks perfectly correct.

Unfortunately, it is not always safe.

---

# The Hidden Problem

Consider the expression:

```solidity
(x * y) / denominator
```

How does Solidity evaluate this?

Does it perform:

```
Multiply

↓

Divide
```

or

```
Divide

↓

Multiply
```

The answer is:

```
Multiply

↓

Divide
```

The multiplication **always happens first.**

This is extremely important.

---

Suppose

```
x = Huge uint256

y = Huge uint256
```

The multiplication becomes

```
Huge

×

Huge
```

which may require

```
512 bits
```

to represent.

However Solidity only has

```
uint256
```

which means only

```
256 bits
```

are available.

So before the division even starts,

the multiplication may already overflow.

```
x

×

y

↓

Needs 512 bits

↓

uint256 cannot hold it

↓

Overflow ❌
```

Notice something interesting.

The **final answer** might actually fit inside a uint256.

The overflow happens only because Solidity performs multiplication first.

---

# Example

Imagine:

```
x = Very Large

y = Very Large

denominator = Very Large
```

Mathematically,

```
(x × y)

↓

Huge number

↓

Divide by denominator

↓

Small enough to fit inside uint256
```

The final quotient is perfectly valid.

But Solidity never gets there.

It first tries to compute

```
x × y
```

inside only

```
256 bits
```

which immediately overflows.

So the division never has a chance to reduce the number.

---

# Why Not Divide First?

A common question is:

> "Why not divide first and then multiply?"

Example:

Instead of

```
(x × y)

↓

÷ denominator
```

why not do

```
x

↓

÷ denominator

↓

× y
```

Unfortunately this changes the mathematics.

Example:

```
10 × 10 / 6
```

Correct answer:

```
100 / 6

=

16
```

(integer division)

Now divide first:

```
10 / 6

=

1
```

Then multiply:

```
1 × 10

=

10
```

The result became

```
10
```

instead of

```
16
```

We lost precision.

So dividing first is **not** a valid solution.

---

# Therefore We Need Both

We want:

✅ No overflow

AND

✅ No precision loss

Unfortunately,

```
Multiply First

↓

Overflow
```

while

```
Divide First

↓

Precision Loss
```

Neither works.

That is exactly why `mulDiv()` exists.

It gives us

```
No Overflow

+

No Precision Loss
```

at the same time.

---

# The Big Idea

Instead of pretending a 512-bit multiplication fits into a uint256,

OpenZeppelin embraces the fact that it doesn't.

Instead of forcing the product into one integer,

it stores it as

```
Upper 256 bits

+

Lower 256 bits
```

Together these represent one

```
512-bit product
```

Only after preserving the complete multiplication does the algorithm begin preparing for the division.

This is the first major trick of `mulDiv()`.

---

# Child Analogy

Imagine you are writing a very large number.

Unfortunately,

your notebook has room for only

```
256 digits
```

Your answer needs

```
512 digits.
```

Instead of throwing away half the number,

you use two notebooks.

Notebook 1:

```
Upper Half
```

Notebook 2:

```
Lower Half
```

Now the entire number is preserved.

Only after safely storing the full number do you begin performing the division.

That is exactly what OpenZeppelin does with

```
upperPart

and

lowerPart.
```

---

# Key Takeaways

* Solidity evaluates `(x * y) / denominator` by multiplying first.
* The multiplication may require 512 bits.
* Solidity only supports integers up to 256 bits.
* Multiplying first can overflow.
* Dividing first causes precision loss.
* `mulDiv()` solves both problems by first computing the complete 512-bit product before performing the division.
