# 17. The Final Division — Replacing Division With Multiplication

After all the preparation, the final lines of `mulDiv()` are surprisingly simple.

```solidity
result = lowerPart * inverse;
return result;
```

Only one multiplication.

After pages of mathematics,

assembly,

CRT,

modular arithmetic,

bit shifting,

and Newton-Raphson,

everything ends with a single multiplication.

Why?

Because we have already solved every difficult problem.

---

# Where Are We Right Now?

Let's summarize our journey.

Originally we wanted to compute

```text
(x × y) ÷ denominator
```

Unfortunately,

the multiplication required

```text
512 bits.
```

The EVM only supports

```text
256 bits.
```

So we transformed the problem step by step.

---

## Step 1

Compute the complete product.

```text
Product

↓

[ upperPart | lowerPart ]
```

---

## Step 2

Verify the final answer fits inside uint256.

```text
upperPart < denominator
```

Otherwise,

revert.

---

## Step 3

Remove the remainder.

```text
Product

↓

Product - Remainder
```

Now the division becomes exact.

---

## Step 4

Remove every power of

```text
2
```

from the denominator.

The denominator becomes

```text
Odd.
```

---

## Step 5

Shift the upper bits into the lower half.

After

```solidity
lowerPart |= upperPart * twos;
```

everything we need is now contained inside

```text
lowerPart.
```

The upper half has completed its job.

---

## Step 6

Compute the modular inverse.

Newton-Raphson gives us

```text
inverse
```

such that

```text
denominator × inverse

≡

1

(mod 2²⁵⁶)
```

Everything is finally ready.

---

# The Beautiful Identity

Remember ordinary mathematics.

Instead of

```text
100 ÷ 5
```

we may write

```text
100 × (1 / 5)
```

Exactly the same idea applies here.

Instead of

```text
ExactNumerator

÷

OddDenominator
```

we compute

```text
ExactNumerator

×

ModularInverse
```

Modulo

```text
2²⁵⁶.
```

That is exactly what this line performs.

```solidity
result = lowerPart * inverse;
```

---

# Why Does This Work?

Earlier we proved

```text
denominator × inverse

≡

1

(mod 2²⁵⁶)
```

Suppose

```text
ExactNumerator

=

Quotient × Denominator
```

Multiply both sides by

```text
inverse.
```

```text
ExactNumerator × inverse

=

Quotient × Denominator × inverse
```

Substitute

```text
Denominator × inverse

↓

1
```

Result

```text
ExactNumerator × inverse

=

Quotient × 1

=

Quotient
```

Exactly the value we wanted.

The division has disappeared.

Only multiplication remains.

---

# Why Is `upperPart` Gone?

Notice something.

The last line uses only

```text
lowerPart.
```

Where did

```text
upperPart
```

go?

Earlier,

we proved

```text
Result

<

2²⁵⁶.
```

Then,

during

```solidity
lowerPart |= upperPart * twos;
```

every bit that could possibly contribute to the final answer was shifted into

```text
lowerPart.
```

The remaining bits inside

```text
upperPart
```

can never affect the result.

Their job is finished.

So OpenZeppelin simply stops using it.

---

# Child Analogy

Imagine moving houses.

Initially,

everything you own is split between

```text
House A

House B
```

During the move,

every useful item is transferred into

```text
House B.
```

Now,

House A is empty.

You don't need to visit it anymore.

That is exactly what happened to

```text
upperPart.
```

Everything useful has already been moved into

```text
lowerPart.
```

The algorithm is not a collection of random tricks.


# Key Takeaways

* The final multiplication is **not** an approximation.

* The modular inverse mathematically replaces division.

* `upperPart` is no longer needed because all useful bits have already been shifted into `lowerPart`.

* Every previous stage transformed an impossible operation:

  ```text
  512-bit ÷ 256-bit
  ```

  into an operation the EVM can perform efficiently:

  ```text
  256-bit × 256-bit
  ```

* The returned value is exactly:

  ```text
  floor(x × y / denominator)
  ```

  with:

  * no overflow,
  * no precision loss,
  * and full 512-bit correctness.
