# Discussion — Where Does the Swap Actually Start?

While studying the swap algorithm, an important question came up.

Suppose Alice is a Liquidity Provider (LP).

She deposited liquidity between:

```text
Pa = $3

Pb = $7
```

The current market price is:

```text
$4
```

Graphically,

the pool looks like this.

```text
           Alice's Liquidity

$3 ---------------- $4 ---------------- $7
                  ↑
             Current Price
```

Now suppose **you** come to perform a swap.

A natural question is:

> **When the swap starts, does the pool begin working with Alice's entire range ($3 → $7), or does it begin somewhere else?**

The answer is:

**The pool always starts from the current market price.**

In this example,

the current market price is

```text
$4
```

That means the current price belongs to the **current tick**.

So the swap begins from the **current tick**, not from the beginning of Alice's range.

It does **not** start from:

```text
Pa
```

It does **not** start from:

```text
Pb
```

Instead,

it starts exactly where the market currently is.

---

# Child Analogy — Train

Imagine a train travelling between stations.

```text
Station A ---- Station B ---- Station C ---- Station D
                 🚆
```

The train is currently stopped at

```text
Station B
```

Now a passenger gets on and says,

> "Take me as far as you can."

Does the train first go backwards to

```text
Station A
```

and then begin the journey?

Of course not.

It starts moving from **its current location**.

Exactly the same thing happens in Uniswap V3.

The pool starts swapping from the **current tick**, because that is where the current market price is.

---

# Small Swap Example

Suppose the current price is

```text
$4
```

Your swap is very small.

The price moves only to

```text
$4

↓

$4.20
```

Notice something.

The price never reaches the next initialized tick.

That means

the pool never leaves the current liquidity range.

It simply performs all of its calculations inside the current tick.

Swap complete.

---

# Large Swap Example

Now suppose your swap is much larger.

The price moves like this.

```text
$4

↓

$5

↓

$6

↓

$7
```

Eventually,

the price reaches

```text
$7
```

This is an initialized tick where liquidity changes.

The pool now says:

> "I'm done using the liquidity available in the current tick."

It crosses the initialized tick,

updates the active liquidity,

and continues swapping using the liquidity available beyond that tick.

---

# Flow of a Swap

The swap always follows this pattern.

```text
Current Price

↓

Current Tick

↓

Use Liquidity Available In This Tick

↓

Price Moves

↓

Reached Next Initialized Tick?

        │
     No │ Yes
        │
        ▼

 Continue     Update Active Liquidity

              Move To Next Tick

              Continue Swapping
```

The swap never jumps directly across multiple liquidity ranges.

Instead,

it progresses one initialized tick at a time.

---

# Key Idea

As a user,

your swap always starts from the pool's **current price**, which belongs to the **current tick**.

The pool first uses the liquidity available inside that current tick.

Only if your swap is large enough to move the price to the next initialized tick does the pool update the active liquidity and continue into the next liquidity range.

This is one of the main reasons Uniswap V3 uses a **while loop** during swaps.

Instead of performing one giant calculation,

the pool repeatedly performs small calculations,

moves the price,

checks whether it has reached the next initialized tick,

updates liquidity if necessary,

and then continues until the swap is complete or the specified `sqrtPriceLimit` is reached.

# Discussion — What Happens When the Swap Leaves Alice's Liquidity Range?

After understanding that the swap always starts from the **current tick**, another important question came up.

Suppose there are **two Liquidity Providers (LPs).**

Alice provides liquidity between:

```text
Pa = $3

Pb = $7
```

Bob provides liquidity between:

```text
Pa = $7

Pb = $10
```

Graphically,

their liquidity positions look like this.

```text
Alice

$3 ---------------- $7

                    Bob

                    $7 ---------------- $10
```

The current market price is

```text
$4
```

which lies inside Alice's liquidity range.

Initially,

the pool is only using Alice's liquidity because the current price belongs to Alice's active range.

---

# The Swap Begins

Suppose you come to swap.

Since the current market price is

```text
$4
```

the swap starts inside Alice's liquidity range.

If your swap is large enough,

the price begins moving upward.

```text
$4

↓

$5

↓

$6

↓

$7
```

Eventually,

the price reaches

```text
$7
```

This is an initialized tick where liquidity changes.

---

# What Happens At $7?

The pool now says:

> "I've finished using Alice's active liquidity."

It now crosses the initialized tick.

Conceptually,

before crossing,

```text
Active Liquidity

=

Alice
```

After crossing,

```text
Active Liquidity

=

Bob
```

The swap then continues using Bob's liquidity.

If multiple LPs start or end their liquidity at the same initialized tick,

the pool updates all of them accordingly.

---

# Child Analogy — Connected Swimming Pools

Imagine two swimming pools connected together.

```text
Pool A

~~~~~~~~~~~~|

            |~~~~~~~~~~~~

               Pool B
```

You begin swimming inside Pool A.

Eventually,

you reach the connection.

Now you simply continue swimming inside Pool B.

You never teleport.

You never restart.

You simply continue from your current position.

The swap behaves exactly the same way.

It begins in one liquidity range,

reaches the next initialized tick,

updates the active liquidity,

and then continues inside the next liquidity range.

---

# One Very Important Clarification

At first,

it might sound like Alice owns one pool,

Bob owns another pool,

and the swap moves from one pool to another.

This is **not** how Uniswap V3 works.

There is only **one** Uniswap V3 Pool for a particular token pair and fee tier.

Inside that one pool,

many Liquidity Providers create different liquidity positions.

Think of it like this.

```text
One Uniswap V3 Pool

│

├── Alice ($3 → $7)

├── Bob ($7 → $10)

├── Charlie ($5 → $12)

├── David ($8 → $15)

└── ...
```

The swap never moves to another pool.

Instead,

the pool changes **which liquidity positions are currently active** as the price moves.

---

# Why Doesn't The Pool Use Every LP's Liquidity At Once?

Only the liquidity whose price range contains the **current market price** is active.

Suppose the current market price is

```text
$4
```

Alice's liquidity

```text
$3 → $7
```

contains

```text
$4
```

so Alice is active.

Bob's liquidity

```text
$7 → $10
```

does **not** contain

```text
$4
```

so Bob is currently inactive.

Only after the price reaches

```text
$7
```

does Bob's liquidity become active.

---

# Complete Flow

```text
Current Price

↓

Current Tick

↓

Use Active Liquidity

↓

Price Moves

↓

Reached Next Initialized Tick?

        │
     No │ Yes
        │
        ▼

 Continue

        │

 Update Active Liquidity

        │

 Continue Swapping
```

---

# Key Takeaways

- A swap **always begins from the current market price (current tick).**
- Initially, only the liquidity active at that current price is used.
- If the swap is small, it may finish entirely inside the current liquidity range.
- If the swap is large enough to reach the next initialized tick, the pool crosses the tick and updates the active liquidity.
- The pool **does not move to another pool**.
- There is only **one Uniswap V3 Pool** for a given token pair and fee tier.
- Different Liquidity Providers simply own different liquidity positions inside that one pool.
- The while loop exists because the swap may need to cross multiple initialized ticks, updating active liquidity each time before continuing.
