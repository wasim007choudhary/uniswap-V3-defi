# Uniswap V3 Swap Algorithm — Complete Dissection (Part 2)

---

# Determining the Swap Type

Once the pool has received all three inputs,

- `zeroForOne`
- `amountSpecified`
- `sqrtPriceLimit`

the first thing it does is determine:

> **What kind of swap is this?**

There are only two possibilities.

---

## Exact Input

If

```text
amountSpecified > 0
```

the user has specified the amount of tokens they want to **give**.

Example:

> "I want to swap exactly 1000 USDC."

Here,

the pool already knows the input.

Its job is to calculate:

> "How much WETH should I give back?"

---

## Exact Output

If

```text
amountSpecified < 0
```

the user has specified the amount of tokens they want to **receive**.

Example:

> "I want exactly 1 WETH."

Now,

the pool already knows the output.

Its job becomes:

> "How much USDC must the user pay?"

---

# Once The Swap Type Is Known...

Now the pool finally has enough information to begin the swap.

At this point,

many beginners imagine something like this:

```text
User wants swap

↓

Pool calculates everything

↓

Swap finished
```

That is **NOT** how Uniswap V3 works.

Instead,

the swap happens little by little.

---

# Why Doesn't Uniswap Do Everything At Once?

Remember what we learned earlier.

Liquidity in Uniswap V3 is **concentrated**.

It is **not** spread across all prices.

Different LPs provide liquidity in different ranges.

For example,

Alice provides liquidity between

```text
$3 ---------------- $7
```

Bob provides liquidity between

```text
$7 ---------------- $10
```

Charlie provides liquidity between

```text
$10 ---------------- $15
```

Notice something.

These are **NOT** different pools.

They are different liquidity positions **inside the same pool.**

---

# One Pool, Many Positions

This is a very important concept.

Some people think:

```text
Alice has Pool A

Bob has Pool B
```

This is incorrect.

There is only **one** Uniswap V3 Pool for a given token pair and fee tier.

Inside that pool,

many Liquidity Providers deposit liquidity.

Think of it like this.

```text
One Pool

│

├── Alice's Position

├── Bob's Position

├── Charlie's Position

├── David's Position

└── ...
```

The pool never switches to another pool.

Instead,

it changes **which liquidity positions are currently active**.

---

# The Current Price

Suppose the current market price is

```text
$4
```

Alice's range is

```text
$3 ---------------- $7
```

Since

```text
$4
```

lies inside Alice's range,

Alice's liquidity is currently active.

We can draw it like this.

```text
Alice

$3 ---------------- $4 ---------------- $7
                  ↑
             Current Price
```

Notice that the current price is inside Alice's position.

Therefore,

the swap begins using Alice's liquidity.

---

# Current Tick

The lesson later refers to the

```text
Current Tick
```

Think of it simply as

> **the tick where the current price currently exists.**

Since the price is currently

```text
$4
```

the swap starts from the tick containing

```text
$4
```

It does **NOT** start from

```text
Pa
```

It does **NOT** start from

```text
Pb
```

It starts exactly where the current market price is.

---

# Child Analogy — A Train

Imagine a train.

```text
Station A ---- Station B ---- Station C ---- Station D
                 🚆
```

The train is currently at

```text
Station B
```

Now someone boards and says

> "Take me as far as possible."

Does the train go back to Station A?

No.

It starts from where it already is.

Exactly the same thing happens during a swap.

The swap begins from the **current price**.

Not from the beginning of the liquidity range.

---

# Why Does The While Loop Exist?

Now we reach the next part of the lesson.

The document says

the algorithm now starts a

```text
while loop
```

Many beginners wonder

> "Why do we even need a loop?"

Because the pool doesn't know whether the swap will finish inside the current liquidity range.

Maybe the user is swapping a very small amount.

Maybe they're swapping millions of dollars.

The pool doesn't know yet.

So instead of trying to calculate everything in one giant step,

it repeatedly performs many small calculations.

---

# Child Analogy — Walking

Imagine walking.

You don't teleport.

You take one step.

```text
Step

↓

Step

↓

Step

↓

Step
```

After every step,

you ask yourself

> "Have I reached my destination?"

If not,

take another step.

That is exactly how the while loop behaves.

---

# Another Child Analogy — Filling a Bucket

Imagine filling a bucket using a small cup.

```text
🥤

↓

Pour

↓

🥤

↓

Pour

↓

🥤

↓

Pour
```

After every pour,

the child asks

> "Is the bucket full?"

If not,

pour again.

When the bucket is full,

stop.

This is exactly what a while loop does.

---

# What Keeps The Loop Running?

The lesson gives two conditions.

The loop continues while

1.

```text
amountSpecifiedRemaining

≠

0
```

AND

2.

```text
Current Price

≠

sqrtPriceLimit
```

As long as **both** conditions are true,

the swap continues.

The moment one of them becomes false,

the swap stops.

---

# First Stopping Condition

Suppose the user wanted to swap

```text
1000 USDC
```

Eventually,

all

```text
1000 USDC
```

has been processed.

Now

```text
amountSpecifiedRemaining

=

0
```

There is nothing left to swap.

The loop stops.

---

# Second Stopping Condition

Suppose instead,

the user specified

```text
sqrtPriceLimit
```

Remember our mango example.

Current price

```text
₹4
```

Maximum price they're willing to buy at

```text
₹5
```

The swap progresses.

```text
₹4

↓

₹4.20

↓

₹4.50

↓

₹4.80

↓

₹5
```

The moment the price reaches

```text
₹5
```

the swap immediately stops.

Even if some input tokens are still left.

---

# Child Analogy — Toy Car

Imagine pushing a toy car.

```text
🚗────────────────────────🧱
```

The brick wall is

```text
sqrtPriceLimit
```

The car keeps moving.

The moment it touches the wall,

it stops.

Even if you still wanted to push further.

The swap behaves exactly the same way.

---

# Summary So Far

The pool now knows:

- The swap direction.
- Whether it's an Exact Input or Exact Output swap.
- The maximum price it's allowed to reach.

The swap always starts from the **current price (current tick)**.

It repeatedly performs small calculations using a while loop.

The loop stops when:

- there is nothing left to swap,

or

- the price reaches the user's specified limit.
