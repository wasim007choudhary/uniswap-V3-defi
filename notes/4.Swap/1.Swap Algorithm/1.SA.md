# Understanding the Swap Algorithm

Before diving into Solidity code, the lesson first explains **how a swap works conceptually**.

This is extremely important.

If we immediately jump into the `swap()` function, we'll see hundreds of lines of code and many variables changing simultaneously.

Instead, we first want to understand **what the pool is trying to accomplish**.

Think of it this way.

Imagine **you are the Uniswap V3 Pool.**

A user walks up to you and says:

> "I want to swap."

Before you can perform the swap, you need to gather some information.

The rest of this lesson is simply the pool's thought process.

---

# What Does The Pool Need To Know?

The pool first asks the user three questions.

Think about ordering food at a restaurant.

The chef doesn't immediately start cooking.

Instead, the waiter asks:

- What do you want?
- How much?
- Any special instructions?

Only after collecting this information does the chef begin cooking.

The swap algorithm works exactly the same way.

---

# 1. zeroForOne

The first thing the pool asks is:

> **Which direction is this swap going?**

Suppose our pool contains two tokens.

```text
Token0 = WETH

Token1 = USDC
```

The user has two possibilities.

Either

```text
WETH

↓

USDC
```

or

```text
USDC

↓

WETH
```

The pool must know which token is coming in and which token is going out.

This is stored inside

```solidity
zeroForOne
```

If

```text
zeroForOne = true
```

then the swap direction is

```text
Token0

↓

Token1
```

If

```text
zeroForOne = false
```

then the swap direction is

```text
Token1

↓

Token0
```

Nothing more.

This variable simply tells the pool:

> "Which direction should I perform the trade?"

---

## Child Analogy

Imagine there are two rooms.

```text
Room A

Room B
```

Someone asks:

> "Which room should I move the toys to?"

There are only two answers.

```text
Room A

↓

Room B
```

or

```text
Room B

↓

Room A
```

That is exactly what `zeroForOne` represents.

It only tells the direction.

# 2. amountSpecified

This is usually the most confusing input for beginners.

The lesson says:

> amountSpecified can be **positive** or **negative**.

At first glance, people think:

> "Negative tokens? That doesn't make sense."

The answer is:

**The sign does NOT represent the amount of tokens.**

Instead,

the sign tells the pool **what the user already knows**.

---

## Positive Amount

Suppose

```text
amountSpecified = 100
```

The user is saying:

> "I am giving exactly 100 USDC."

The pool now thinks:

> "Great.

I already know how many tokens you're giving me.

Now I need to calculate how many WETH you should receive."

This type of swap is called:

```text
Exact Input
```

because the **input amount** is already known.

The output amount is unknown and must be calculated.

---

## Negative Amount

Suppose

```text
amountSpecified = -1
```

This does **NOT** mean:

> "-1 token"

Instead,

it is simply a signal telling the pool:

> "The user already knows how many tokens they want to receive."

For example:

> "I want exactly 1 WETH."

Now the pool thinks:

> "Okay.

I know your desired output.

Now I need to calculate how many USDC you must pay."

This is called

```text
Exact Output
```

because the **output amount** is already known.

The input amount is unknown and must be calculated.

---

# Child Analogy — Buying Chocolates

Imagine you're buying chocolates.

There are two different ways to buy them.

### Situation 1

You hand the shopkeeper

₹100

Now the shopkeeper calculates

₹100 can buy.

This is

because the input is already known.

### Situation 2

Now imagine saying

This time,

the chocolates are fixed.

how much money

This is

```text
Exact Output
```

because the output is already known.

# Important Observation

Notice something elegant.

The algorithm doesn't need another variable called

```text
isExactInput
```

or

```text
swapType
```

Instead,

it simply checks:

```text
amountSpecified
```

If it is

positive

↓

Exact Input.

If it is

negative

↓

Exact Output.

One variable tells the pool everything it needs to know.

# 3. sqrtPriceLimit

The third question the pool asks is:

> "How far am I allowed to move the price?"

This is stored as

```text
sqrtPriceLimit
```

Notice the name carefully.

This is **NOT** the current price.

It is the **maximum (or minimum, depending on swap direction) price that the swap is allowed to reach**.

Think of it as placing a boundary on the trade.

---

# Real Life Example

Suppose the current market price is:

```text
1 Mango = ₹4
```

You want to buy many mangoes.

As you keep buying,

the demand increases,

and the price slowly rises.

```text
₹4

↓

₹4.20

↓

₹4.50

↓

₹4.80

↓

₹5
```

Now suppose you tell the shopkeeper:

> "I'm willing to keep buying only until the price reaches ₹5."

Then

```text
Current Price = ₹4

Price Limit = ₹5
```

The shopkeeper continues buying for you.

As long as the price stays below ₹5,

he keeps buying.

```text
₹4

↓

₹4.20

↓

₹4.50

↓

₹4.80

↓

₹5
```

The moment the price reaches

```text
₹5
```

he immediately stops.

Even if you still have money left.

This is exactly how

```text
sqrtPriceLimit
```

works.

# Summary So Far

Before the swap begins,

the pool knows:

- Which direction is the swap going?
- Did the user specify the input amount or the output amount?
- How far is the swap allowed to move the price?

Only after answering these three questions

does the actual swap algorithm begin.
