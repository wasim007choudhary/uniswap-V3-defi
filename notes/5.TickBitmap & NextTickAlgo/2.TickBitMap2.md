# 🔢 Binary Mechanics — `>> 8` and `% 256`

The actual V3 `position()` logic is:

```solidity
function position(int24 tick) private pure returns (int16 wordPos, uint8 bitPos) {
    wordPos = int16(tick >> 8);
    bitPos = uint8(tick % 256);
}
```

The important part is:

```solidity
tick >> 8
```

and:

```solidity
tick % 256
```

We already know **what they produce conceptually**.

Now let's understand **why**.

---

# 🧩 First: Why `256`?

A bitmap word contains:

```text
256 bits
```

And:

```text
256 = 2⁸
```

That `8` is extremely important.

Because one word contains exactly:

```text
2⁸ = 256
```

positions.

So we can think of a compressed tick as being divided into:

```text
        compressed tick
              ↓
       ┌──────┴──────┐
       ↓             ↓
   word part      bit part
       ↓             ↓
    groups of       inside
     256             256
```

The `>> 8` is basically saying:

> **Move past 8 binary bits because 8 bits represent the position inside one 256-position word.**

---

# 🧠 Tiny Binary Example

Forget Solidity for one second.

Take:

```text
compressed = 263
```

Convert 263 to binary:

```text
263 = 256 + 7
```

So:

```text
263 = 100000111
```

Now look at the binary structure:

```text
100000111
^^^^^^^
```

The last **8 bits** are:

```text
00000111
```

which is:

```text
7
```

Those are the **position inside the word**.

Everything before those 8 bits represents the word number.

So:

```text
100000111
│      │
│      └── last 8 bits → bitPos = 7
│
└───────── remaining bits → wordPos
```

And:

```text
263 = 1 × 256 + 7
```

Therefore:

```text
wordPos = 1
bitPos  = 7
```

Exactly what we already established conceptually in the MD. 

---

# ➡️ What Does `>> 8` Actually Do?

`>>` is the **right-shift operator**.

It moves all binary bits to the right.

Example:

```text
100000111
```

Shift right by 1:

```text
010000011
```

Shift right by 2:

```text
001000001
```

Shift right by 8:

```text
000000001
```

So:

```text
263 >> 8
```

gives:

```text
1
```

because shifting right by 8 effectively removes the lowest 8 binary bits.

Those lowest 8 bits represented:

```text
00000111
```

which was our:

```text
bitPos = 7
```

So:

```text
263
 ↓
100000111
 ↓ >> 8
000000001
 ↓
1
```

Therefore:

```solidity
wordPos = int16(263 >> 8);
```

gives:

```text
wordPos = 1
```

# 🎯 Why Exactly 8 Bits?

This is the key connection.

One word has:

```text
256 positions
```

And:

```text
2⁸ = 256
```

Therefore we need **8 binary bits** to represent:

```text
0 → 255
```

because:

```text
00000000 = 0
00000001 = 1
00000010 = 2
...
11111111 = 255
```

So the lower 8 bits naturally represent:

```text
bitPos = 0 → 255
```

while everything above those 8 bits determines:

```text
wordPos
```

That is why V3 uses:

```text
tick >> 8
```

for the word and:

```text
tick % 256
```

for the bit.

## 🧠 Why does it say **"before"**? Let me explain.

Because the **word index** (wordPos) is literally the count of how many full 256-bit boxes exist **before** your current position.

---

## 📊 Example: `compressed = 263`

Let's break this down:

```text
compressed = 263

Step 1: Divide by 256

263 ÷ 256 = 1 (remainder 7)

Step 2:

wordPos = 1
bitPos  = 7
```

Now look at how the bitmap is organized:

```text
WORD 0         WORD 1         WORD 2
[0 – 255]      [256 – 511]    [512 – 767]
                  ↑
                  Word 1 starts here

Your position 263 is inside WORD 1.
```

### The **"before"** part:

- **WORD 0** (positions 0 to 255) comes **before** WORD 1.
- How many words are **before** WORD 1? **Exactly 1** (WORD 0).
- That's why `wordPos = 1`.

So the `wordPos` doesn't just say "you are in box 1." It says:

> "There is **1 full box** sitting **before** the box that contains you."

---

## 🔢 Another Example: `compressed = 10`

```text
10 ÷ 256 = 0 (remainder 10)

wordPos = 0
bitPos  = 10
```

- How many words are **before** WORD 0? **Zero**.
- So `wordPos = 0`.

---

## 🔢 Negative Example (if needed, but concept same)

```text
compressed = -2
```

With proper two's complement handling (which Uniswap does), the logic still counts *which* word it belongs to, but the "before" concept flips to the left side (negative side). But the principle is the same: `wordPos` tells you how many whole boxes precede the current position along the number line.

---

## 🎯 Why this wording is used

Because the bitmap is just a giant road of tick positions:

```text
... | BOX -2 | BOX -1 | BOX 0 | BOX 1 | BOX 2 | ...
```

If you are in **BOX 1**, there is exactly **1 box before you** (BOX 0).
If you are in **BOX 5**, there are **5 boxes before you** (BOXES 0–4).

The `wordPos` is **literally the number of boxes that come before yours**.

So when you read "How many complete 256-position words are *before* this compressed position?" — it's just the simplest, most accurate way to describe what that division (`>> 8`) calculates.

---

## 💡 One-liner to remember

> `compressed >> 8` = "Count how many 256-bit blocks fit entirely **before** this position — that number is your `wordPos`."
