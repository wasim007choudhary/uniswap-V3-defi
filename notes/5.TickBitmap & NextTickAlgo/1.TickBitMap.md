# 🧭 1️⃣ What Problem Does Tick Bitmap Solve?

First forget the bitmap, bits, `int16`, `uint8`, `XOR` — all of that for now.

We only need to understand why Uniswap needs a Tick Bitmap.

You already know that an LP `position` has a range:

```text
lower tick ---------------- upper tick
     100                         500
```


The `liquidity` is active while the current price is inside that range.

So imagine the swap price is moving:

> **🔄 Flow**  
> 100 → 150 → 200 → 300 → 400 → 500

At certain ticks, `liquidity` changes.

For example:

| `tick` | What happens |
|---:|---|
| `100` | ``liquidity`` **starts** |
| `250` | **another** ``position`` **starts** |
| `400` | **another** ``position`` **ends** |
| `500` | ``liquidity`` **ends** |

> **📍 Tick-by-tick view:** Each row shows what changes at that `tick` boundary.

These are initialized ticks.

> **🧑‍💻 Question**  
> 🧠 What does the swap need to know?

Suppose the current tick is:

Current tick = 150

The swap needs to ask:

> **🧑‍💻 Question**  
> "What is the next tick ahead of me where something important happens to `liquidity`?"

Maybe the answer is:

250

So the swap moves toward:

150 → 250

Then after crossing 250, it asks again:

> **🧑‍💻 Question**  
> 250 → ?

Maybe:

400

So:

250 → 400

# 🧭 2️⃣ What Is an “`initialized tick`”?

Now we only focus on this.

You already know an LP `position` has a range:

```text
lower tick ---------------- upper tick
     100                         500
```


The important thing is that the LP chooses these boundaries.

For example:

```text
LP `position`:

tickLower = 100
tickUpper = 500
```


Those two ticks are special because something happens to `liquidity` there.

> **🧑‍💻 Question**  
> 🧠 What Happens at the Lower Tick?

When price reaches the lower boundary:

100

the LP's `liquidity` can become active.

Conceptually:

```text
below 100
    ↓
LP `liquidity` is not active

cross 100
    ↓
LP `liquidity` becomes active
```


Therefore tick 100 needs to have information stored for it.

That makes tick 100 an:

### 🧩 `initialized tick`


---

> **🧑‍💻 Question**  
> 🧠 What Happens at the Upper Tick?

At:

500

the LP's `liquidity` stops being active when price **crosses** that boundary.

Conceptually:

```text
inside range
    ↓
LP `liquidity` is active

cross 500
    ↓
LP `liquidity` stops being active
```


So tick 500 also needs information stored.

Therefore:

```text
100 → initialized
500 → initialized
```

❌ What About Tick 101?

Nothing special happens to this particular LP at tick 101.

The LP didn't choose:

tickLower = 101

or:

tickUpper = 101

So this particular tick doesn't need to store this `position`'s `liquidity`-boundary information.

Therefore:

```text
100 → initialized ✅
101 → not initialized ❌
102 → not initialized ❌
103 → not initialized ❌
...
500 → initialized ✅
```


> **🧠 Key point**  
> 🎯 Very Important Distinction

This does NOT mean that ticks 101, 102, 103, etc. don't exist mathematically.

They absolutely exist.

> **🧠 Key point**

Every valid mathematical tick exists, but only ticks that need stored `liquidity` information are initialized.

# 🧭 Next concept: Tick compression

> **🧠 Key point**  
> This is important because our “256 ticks inside one word” idea needs one correction for actual Uniswap V3.

We don't directly put every `raw tick` into the bitmap.

> **🧠 Key point**  
> First, remember `tickSpacing`

A pool has a `tickSpacing`.

For example, imagine:

`tickSpacing` = 10

Then the usable/initializable ticks are:

..., -20, -10, 0, 10, 20, 30, 40, 50, ...

We compress the tick by dividing by the spacing:

tick 10  / 10 = 1
tick 20  / 10 = 2
tick 30  / 10 = 3
tick 40  / 10 = 4

So:

```text
`raw tick`       `compressed` tick
   10      →        1
   20      →        2
   30      →        3
   40      →        4
```

## 🧠 Why do this?

Because the bitmap doesn't need a separate `position` for every possible `raw tick`.

It only needs positions for the ticks that can actually be initialized for that pool's tick spacing.

So our previous mental picture:

WORD

is really:

## The actual technique

The key is that V3 wants the `compressed` tick to behave like mathematical floor division:

floor(tick / `tickSpacing`)

But Solidity integer division truncates toward zero.

So V3 does:

`int24` `compressed` = tick / `tickSpacing`;

if (tick < 0 && tick % `tickSpacing` != 0) {
    `compressed`--;
}
Example: -17, spacing 10

Normal Solidity division:

-17 / 10
= -1

But mathematically:

floor(-17 / 10)
= -2

So V3 detects:

```text
tick < 0             → `true`
tick % spacing != 0  → `true`
```


and does:

`compressed`--;

Therefore:

-1 - 1 = -2

Final:

`raw tick`       = -17
`tickSpacing`    = 10
`compressed`     = -2

And:

-2 × 10 = -20

So -17 is mapped to the lower spacing boundary, -20.

Why check the remainder?
Because if the tick is exactly divisible, we must not subtract.

-170 / 10 = -17
-170 % 10 = 0

Therefore:

`compressed` = -17

-17 × 10 = -170
