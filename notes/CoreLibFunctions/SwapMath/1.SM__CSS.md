# 🎯 What Is This Function?

Before reading even one line inside the function, let’s understand **its job**.

Think of this function as answering one question:

> **“Given the current liquidity interval, how much of the swap can I perform?”**
> 

Notice I said **current liquidity interval**.

Not:

> the entire swap.
> 

We already learned:

```
swap()

↓

Find next initialized tick

↓

Current Active Liquidity

↓

computeSwapStep()

↓

Reached target?

↓

swap() decides what to do next
```

This function is **one worker**.

It does **one piece** of the entire swap.

---

# 👶 Child Analogy

Imagine three bridges.

```
Bridge A

↓

Bridge B

↓

Bridge C
```

Your destination is after Bridge C.

Does the engineer of Bridge A care about Bridge B?

No.

His only job is:

> “Can I get you across MY bridge?”
> 

That’s exactly what `computeSwapStep()` does.

It only worries about **one liquidity interval**.

---

# What Does It Need?

To answer that question, it needs five pieces of information:

```
1. Current Price
2. Target Price
3. Active Liquidity
4. Remaining Swap Amount
5. Swap Fee
```

All five are supplied by the caller, mainly `UniswapV3Pool.swap()`.

`computeSwapStep()` itself is a `pure` function, so it does not read pool storage.

---

# `computeSwapStep()` Parameters

```solidity
function computeSwapStep(
    uint160 sqrtRatioCurrentX96,
    uint160 sqrtRatioTargetX96,
    uint128 liquidity,
    int256 amountRemaining,
    uint24 feePips
)
```

---

# Parameter 1 — `sqrtRatioCurrentX96`

```solidity
uint160 sqrtRatioCurrentX96
```

This is the **current price before this swap step starts**.

It is not automatically:

```
Pa
```

and it is not automatically:

```
Pb
```

It is wherever the market price is **right now**.

Example:

```
Pa ----------- Current Price ----------- Pb
1000                1500                2000
```

The current price is:

```
1500
```

So conceptually:

```
sqrtRatioCurrentX96
        ↓
Current Price
```

But there is an important technical detail.

The actual Solidity value is **not literally `1500`**.

Uniswap V3 stores the square root of the price using Q64.96 fixed-point encoding:

```
sqrtPriceX96 = √P × 2^96
```

Therefore:

```
sqrtRatioCurrentX96
```

is the encoded square-root representation of the current price.

For our conceptual discussion, we can simply think:

```
sqrtRatioCurrentX96
        ↓
Current Price
```

But in the actual contract:

```
sqrtRatioCurrentX96
        ↓
encoded √Price
```

---

## 👶 Child Version

Imagine you’re standing here:

```
1000 ----------- 1500 ----------- 2000
```

Your feet are at:

```
1500
```

That is the conceptual meaning of:

```
sqrtRatioCurrentX96
```

The swap starts from **where your feet are**, not automatically from either wall.

---

## Is `sqrtRatioCurrentX96` the Lower Limit?

No.

It is the **current price**.

For example:

```
Pa ---------------- Current Price ---------------- Pb
10                         16                         20
```

Here:

```
Pa = 10
Pb = 20
Current Price = 16
```

So:

```
sqrtRatioCurrentX96
        ↓
16
```

conceptually.

It does not mean:

```
sqrtRatioCurrentX96 = Pa
```

and it does not mean:

```
sqrtRatioCurrentX96 = Pb
```

unless the current price actually happens to be at that boundary.

---

## Who Sets `sqrtRatioCurrentX96`?

`UniswapV3Pool.swap()`.

The pool already knows its current price because the current square-root price is stored in the pool’s state, specifically through `slot0`.

When `swap()` calls:

```solidity
computeSwapStep(...)
```

it passes the current encoded square-root price.

Conceptually:

```
Pool

↓

"What is my current price?"

↓

Current Price

↓

Encode as sqrtPriceX96

↓

Pass it into computeSwapStep()
```

---

## Why Is It `uint160`?

The type is:

```solidity
uint160
```

not:

```solidity
uint256
```

because Uniswap V3 has a defined valid range for its `sqrtPriceX96` representation.

The protocol knows the maximum valid encoded square-root price it needs to represent, so 160 bits are sufficient for the valid range.

The important point is:

```
uint160
        ↓
Encoded sqrt-price representation
```

It does **not** mean:

```
Actual human-readable price
        ↓
must be smaller than 2^160
```

The `uint160` bound applies to the **stored encoded square-root price**, not directly to the human-readable price `P`.

---

## Why Not `uint256`?

Because the protocol does not need the full `uint256` range for this value.

The valid Uniswap V3 price range can be represented by the chosen `uint160` `sqrtPriceX96` type.

Using a narrower type gives the protocol a deliberately bounded representation instead of using a full 256-bit integer everywhere.

---

## Why Is There `X96` At The End?

The `X96` tells us that the square-root price uses a fixed-point scale involving:

```
2^96
```

Conceptually:

```
sqrtPriceX96 = √P × 2^96
```

This allows the protocol to represent fractional square-root prices using an integer type.

So:

```
sqrtPrice
```

is not stored as a Solidity floating-point number.

Instead:

```
√P
```

is converted into a fixed-point integer representation.

We will dissect the exact implementation and arithmetic behind this later when we get to the `SqrtPriceMath` library.

# Parameter 2 — `sqrtRatioTargetX96`

```solidity
uint160 sqrtRatioTargetX96
```

This is the **target price for this swap step**.

Notice:

> **this swap step**
> 

It is **not necessarily the final price of the entire swap**.

Usually, this target is related to the next initialized tick.

If the user has supplied a stricter price limit, the price limit can also determine the stopping point.

So this parameter effectively says:

> **“You are not allowed to move beyond this price during this step.”**
> 

Example:

```
1000 ----------- 1500 ----------- 2000
                Current
```

Suppose the swap is moving toward `1000`.

Then conceptually:

```
sqrtRatioTargetX96
        ↓
1000
```

represents the stopping point for this step.


Someone tells you:

> “Don’t walk past 1000.”

That wall at:

```
1000
```

is the conceptual role of:

```
sqrtRatioTargetX96
```

Whether you actually reach it depends on how much swap amount the trader has supplied or requested.

## Who Sets `sqrtRatioTargetX96`?

`UniswapV3Pool.swap()`.

Before each call to:

```solidity
computeSwapStep(...)
```

the pool already knows the relevant stopping point.

Conceptually:

```
Current Price

↓

Find next stopping point

↓

Choose the applicable target

↓

Pass sqrtRatioTargetX96

↓

computeSwapStep()
```

---

## Is The Target Always The Next Tick?

Not necessarily.

The target used for the current step is determined by the larger swap process.

It can be:

```
Next initialized tick
```

or, depending on the situation:

```
User's price limit
```

The important idea for `computeSwapStep()` is simply:

```
Current Price
      ↓
Target Price
      ↓
Do not go beyond this target in this step
```

---

## Why Is It Also `uint160`?

For the same reason as:

```
sqrtRatioCurrentX96
```

It is another encoded `sqrtPriceX96` value.

So:

```
uint160
    ↓
Encoded sqrt-price
```

Both current and target prices use the same representation.

# Parameter 3 — `liquidity`

```solidity
uint128 liquidity
```

This is the **currently active liquidity** for this swap step.

It is not:

```
Total liquidity of the entire pool
```

It is not:

```
Liquidity belonging to every LP everywhere
```

It is not:

```
The amount of Token0 or Token1 deposited by an LP
```

It is the active liquidity value:

```
L
```

that applies at the current price for this particular swap step.

Conceptually:

```
Current Price

↓

Which LP positions are active here?

↓

Their liquidity contributes to active L

↓

computeSwapStep(..., liquidity, ...)
```

The function only needs:

```
500
```

because that is the capacity relevant to the current bridge.

When the swap crosses into another range, the active liquidity can change.

## Who Sets `liquidity`?

`UniswapV3Pool.swap()`.

The pool tracks the active liquidity.

When a tick is crossed, the pool updates the active liquidity using the tick’s liquidity change.

Conceptually:

```
Cross Tick

↓

Update Active Liquidity

↓

New Liquidity

↓

Next computeSwapStep()
```

# Why Is `liquidity` `uint128`?

This was an important question.

At first it may look like:

> “If liquidity is `uint128`, doesn’t that mean an LP can only add `2^128 - 1` tokens?”
> 

No.

That is the wrong way to think about it.

`liquidity` is **not the raw token deposit amount**.

An LP can deposit Token0 and Token1, and the protocol converts that position into a liquidity value `L`.

So:

```
Token0 + Token1

↓

Liquidity Position

↓

Liquidity L
```

The `uint128` applies to the **liquidity value**, not directly to the number of Token0 or Token1 units the LP deposits.

---

## Can An LP Add More Than `2^128 - 1` Tokens?

The existence of:

```solidity
uint128 liquidity
```

does not mean:

> “An LP can never deposit more than `2^128 - 1` tokens.”
> 

Token amounts and the resulting liquidity value are separate quantities.

However, the liquidity value represented by this variable must fit inside the protocol’s chosen `uint128` representation.

The protocol deliberately defines the representable liquidity range around that type.

The important distinction is:

```
uint128 liquidity
        ≠
uint128 token deposit
```

---

## Why Not Make `liquidity` `uint256`?

Because Uniswap V3 does not need the full `uint256` range for its liquidity representation.

The protocol was designed around:

```solidity
uint128
```

for liquidity.

The narrower type gives the protocol a bounded representation that is sufficient for the protocol’s valid liquidity range.

This is a protocol design choice, not a statement that token balances themselves are limited to `uint128`.

---

## Can Multiple LPs Contribute To Active Liquidity?

Yes.

For example:

```
LP A → L = 100
LP B → L = 500
LP C → L = 1000
```

If all three positions are active at the current price:

```
Active Liquidity

= 100 + 500 + 1000

= 1600
```

So the active liquidity used by the swap is the aggregate active liquidity.

Again:

```
Token Amount
      ≠
Liquidity Amount
```

---

## What If An LP Wants To Add More Liquidity?

They can create/add a position with the required liquidity as long as the resulting liquidity value fits within the protocol’s supported limits.

The `uint128` type is not saying:

```
"You can only own 128 bits worth of tokens."
```

It is saying:

```
"The liquidity value used by the protocol is represented using 128 bits."
```

This distinction is important when reading the code.

# Parameter 4 — `amountRemaining`

```solidity
int256 amountRemaining
```

This means:

> **How much of the user’s specified swap amount is still left to process.**
> 

If this is the first swap step, it is initially based on the user’s requested swap amount.

If the swap crosses a tick and continues into another liquidity range, some amount has already been processed.

The next call receives the remainder.

Example:

```
Trader wants:

100 Token0
```

First range consumes:

```
60
```

Remaining:

```
40
```

The next call receives:

```
amountRemaining = 40
```

---

# Why Is `amountRemaining` `int256`?

Because Uniswap uses the **sign** to encode the swap mode.

Positive:

```
+100
```

means:

```
Exact In
```

Negative:

```
-100
```

means:

```
Exact Out
```

So one variable can represent both cases.

Later the function does:

```solidity
bool exactIn = amountRemaining >= 0;
```

That single comparison tells the function which mode it is processing.

---

## 👶 Child Version

Imagine two signs on a box.

```
+100
```

means:

> “I have 100 input tokens to spend.”
> 

```
-100
```

means:

> “I still need 100 output tokens.”
> 

Same variable.

The sign tells Uniswap which question it needs to solve.

---

## Who Sets `amountRemaining`?

`UniswapV3Pool.swap()`.

The pool keeps track of the remaining specified amount as the swap moves through ranges.

Conceptually:

```
Original Amount

↓

Swap Step 1

↓

Amount Used

↓

Remaining Amount

↓

Swap Step 2

↓

Amount Used

↓

Remaining Amount
```

```solidity
uint24 feePips
```

This is the pool’s swap fee represented in Uniswap’s fee units.

Examples:

```
500
=
0.05%
```

```
3000
=
0.30%
```

```
10000
=
1%
```

The fee is represented relative to:

```
1e6
```

So:

```
500 / 1,000,000
=
0.0005
=
0.05%
```

and:

```
3000 / 1,000,000
=
0.003
=
0.30%
```

---

## Why Is `feePips` `uint24`?

Because Uniswap only needs a relatively small range to represent the pool’s fee in these fee units.

The fee is expressed relative to:

```
1e6
```

so a full `uint256` would be unnecessary.

A `uint24` is more than sufficient for the fee representation used by the protocol.

The important point is:

```
uint24 feePips
        ↓
Fee representation
```

not:

```
uint24
        ↓
Token amount
```

---

## Who Sets `feePips`?

The pool has a configured fee tier.

When the pool is created, its fee tier is selected.

When `swap()` calls:

```solidity
computeSwapStep(...)
```

it passes that fee into the function.

Conceptually:

```
Pool Fee Tier

↓

feePips

↓

computeSwapStep()
```

# Why Is `computeSwapStep()` `pure`?

The function is:

```solidity
internal
pure
```

It does not read:

- pool storage
- ticks
- balances
- reserves
- LP positions
- fee configuration from storage

Everything it needs is passed through its parameters.

So it simply performs:

```
Inputs

↓

Mathematical Calculation

↓

Outputs
```

That makes the function deterministic, reusable, and independently testable.

---

# What Does `computeSwapStep()` Return?

The function eventually returns:

```solidity
returns (
    uint160 sqrtRatioNextX96,
    uint256 amountIn,
    uint256 amountOut,
    uint256 feeAmount
)
```

These represent:

### `sqrtRatioNextX96`

The next price after this swap step.

It may be:

- the target price, if the target is reached
- an intermediate price, if the trader’s amount runs out before reaching the target

### `amountIn`

The amount of input token actually used during this swap step.

Depending on the swap direction, this is either:

```
Token0
```

or:

```
Token1
```

### `amountOut`

The amount of output token produced during this swap step.

It is the opposite token from `amountIn`.

### `feeAmount`

The amount of input token taken as the swap fee for this step.

# One Swap Step Is Not The Entire Swap

Suppose the swap travels through:

```
Range A
1000 -------- 1500

Range B
1500 -------- 2000

Range C
2000 -------- 2500
```

A large swap can move through all three.

Conceptually:

```
computeSwapStep()
        ↓
Range A
        ↓
Reach Boundary
        ↓
Cross Tick
        ↓
Update Liquidity
        ↓
computeSwapStep()
        ↓
Range B
        ↓
Reach Boundary
        ↓
Cross Tick
        ↓
Update Liquidity
        ↓
computeSwapStep()
        ↓
Range C
```

So:

> **`computeSwapStep()` handles one range at a time.**
> 

The larger `swap()` process coordinates everything around it.

---

# What If The Calculated Price Wants To Go Outside The Range?

Suppose:

```
Current Range

1000 ---------------- 2000
          ↑
        1500
```

The swap calculation wants to move the price to:

```
900
```

But:

```
900 < 1000
```

The current liquidity range cannot continue beyond its boundary.

So the swap step stops at:

```
1000
```

Then the larger swap process can:

```
Reach Boundary

↓

Cross Tick

↓

Update Active Liquidity

↓

Continue With Remaining Amount

↓

Call computeSwapStep() Again
```

This is why `sqrtRatioTargetX96` is so important.

It gives this one step a stopping point.

---

# Final Mental Model

Think of `computeSwapStep()` as a **single-range calculator**.

The caller gives it:

```
Current Price

Target Price

Active Liquidity

Remaining Amount

Fee
```

Then it calculates:

```
Next Price

Amount In

Amount Out

Fee
```

The overall architecture is:

```
UniswapV3Pool.swap()

        ↓

Prepare parameters

        ↓

computeSwapStep()

        ↓

Calculate one range

        ↓

Did we reach target?

        ├── NO
        │
        │   Swap is finished
        │
        └── YES
            ↓
        Cross Tick
            ↓
        Update Liquidity
            ↓
        Continue if amount remains
            ↓
        computeSwapStep() again
```

Now we are ready to dissect the first executable lines:

```solidity
bool zeroForOne = sqrtRatioCurrentX96 >= sqrtRatioTargetX96;
bool exactIn = amountRemaining >= 0;
```

These two lines answer two fundamental questions:

```
1. Which direction is the swap moving?

2. Is this Exact In or Exact Out?
```
