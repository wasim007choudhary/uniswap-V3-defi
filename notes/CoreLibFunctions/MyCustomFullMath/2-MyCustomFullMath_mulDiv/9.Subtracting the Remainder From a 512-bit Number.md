# 10. Subtracting the Remainder From a 512-bit Number

The assembly code is:

```solidity
assembly ("memory-safe") {
    remainder := mulmod(x, y, denominator)

    upperPart := sub(upperPart, gt(remainder, lowerPart))
    lowerPart := sub(lowerPart, remainder)
}
```

The first line computes the remainder.

The next two lines subtract that remainder from the **entire 512-bit product**.

This is much harder than subtracting from a normal uint256.

---

# The Problem

Remember,

our product is not stored as one number.

It is stored as

```text
+----------------------+----------------------+
|   Upper 256 bits     |   Lower 256 bits     |
+----------------------+----------------------+

        upperPart              lowerPart
```

Together,

these two variables represent one huge

```text
512-bit integer.
```

Now suppose we want to subtract

```text
remainder
```

Where should we subtract it?

Only from

```text
lowerPart.
```

Why?

Because

```text
remainder

<

denominator

<

2²⁵⁶
```

So the remainder always fits inside

```text
256 bits.
```

---

# The Easy Case

Suppose

```text
upperPart = 10

lowerPart = 100

remainder = 30
```

Subtract.

```text
100 - 30

=

70
```

No problem.

The new number becomes

```text
upperPart = 10

lowerPart = 70
```

Nothing special happened.

---

# The Difficult Case

Now suppose

```text
upperPart = 10

lowerPart = 20

remainder = 30
```

Can we compute

```text
20 - 30 ?
```

No.

Unsigned integers cannot become negative.

Instead,

we must borrow.

---

# Child Analogy

Imagine the decimal number

```text
1000
```

Subtract

```text
1
```

You cannot subtract

```text
1
```

from the last digit

```text
0.
```

So you borrow

```text
1
```

from the next digit.

```text
1000

↓

Borrow

↓

09910

↓

0999
```

This is exactly how we learned subtraction in school.

The same thing happens here.

---

# Borrowing In Binary

Our "digits" are not decimal digits.

Instead,

each "digit" is

```text
256 bits.
```

The picture becomes

```text
+----------------------+----------------------+
|   upperPart          |   lowerPart          |
+----------------------+----------------------+

Borrow

↓

+----------------------+----------------------+
| upperPart - 1        | lowerPart + 2²⁵⁶     |
+----------------------+----------------------+
```

Notice what happened.

Borrowing

```text
1
```

from the upper block adds an entire

```text
2²⁵⁶
```

to the lower block.

Exactly the same idea as

```text
Borrowing 1 ten

↓

Adds 10 ones.
```

except our base is

```text
2²⁵⁶.
```

---

# How Does The EVM Know When To Borrow?

Look at this instruction.

```solidity
gt(remainder, lowerPart)
```

`gt` means

```text
Greater Than.
```

It returns

```text
1

if

remainder > lowerPart
```

otherwise

```text
0.
```

Example

```text
lowerPart = 20

remainder = 30
```

Then

```text
30 > 20

↓

true

↓

1
```

But if

```text
lowerPart = 100

remainder = 30
```

Then

```text
30 > 100

↓

false

↓

0
```

---

# Therefore

This instruction

```solidity
upperPart := sub(upperPart, gt(remainder, lowerPart))
```

really means

```text
If borrowing is needed

↓

Subtract 1 from upperPart

Otherwise

↓

Leave upperPart unchanged
```

Nothing more.

---

# Then We Subtract

Finally,

```solidity
lowerPart := sub(lowerPart, remainder)
```

If no borrow occurred,

this is ordinary subtraction.

If borrowing did occur,

the subtraction automatically wraps around modulo

```text
2²⁵⁶.
```

That wraparound is exactly equivalent to

```text
(lowerPart + 2²⁵⁶)

-

remainder
```

because we already removed

```text
1
```

from the upper block.

Together,

both assembly instructions perform

```text
[ upperPart | lowerPart ]

-

remainder
```

as if the product were one giant 512-bit integer.

---

# Why Do We Subtract UpperPart First?

Notice the order.

```solidity
upperPart := ...

lowerPart := ...
```

Why not the other way around?

Because first we must decide

whether a borrow is required.

Once we know that,

we reduce the upper block.

Then,

when the lower subtraction wraps,

everything is already consistent.

---

# Visual Flow

```text
512-bit Product

↓

Need to subtract remainder

↓

Is remainder > lowerPart ?

│
├── NO
│      ↓
│   lowerPart -= remainder
│
└── YES
       ↓
Borrow one 2²⁵⁶ block

↓

upperPart -= 1

↓

lowerPart wraps

↓

Subtract remainder

↓

Entire 512-bit subtraction completed
```

---

# Key Takeaways

* The remainder always fits inside one `uint256`.
* Therefore it is always subtracted from `lowerPart`.
* If `remainder > lowerPart`, subtraction would underflow.
* The EVM solves this exactly like elementary subtraction:

  * Borrow `1` from the upper block.
  * Add one full `2²⁵⁶` block to the lower block.
* `gt(remainder, lowerPart)` detects whether borrowing is necessary.
* The two assembly instructions together subtract the remainder from the **entire 512-bit product**, not just the lower 256 bits.
