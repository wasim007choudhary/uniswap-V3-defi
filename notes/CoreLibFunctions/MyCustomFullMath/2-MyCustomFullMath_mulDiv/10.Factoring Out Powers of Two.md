# 11. Factoring Out Powers of Two

After making the division exact, the next code is:

```solidity
uint256 twos = denominator & (0 - denominator);
```

followed by

```solidity
assembly ("memory-safe") {
    denominator := div(denominator, twos)
    lowerPart := div(lowerPart, twos)
    twos := add(div(sub(0, twos), twos), 1)
}

lowerPart |= upperPart * twos;
```

At first glance,

this looks completely unrelated to division.

Why are we suddenly doing bitwise operations?

The answer is simple.

> **The modular inverse only exists for odd numbers.**

Therefore,

before computing the inverse,

we must first remove every factor of

```
2
```

from the denominator.

---

# Why Does The Denominator Need To Be Odd?

Suppose we have

```
40 ÷ 10
```

Notice

```
10

=

2 × 5
```

The denominator contains a factor of

```
2.
```

The modular inverse algorithm used later only works when

```
gcd(denominator, 2²⁵⁶) = 1
```

The only numbers satisfying this are

```
Odd numbers.
```

Even numbers always share at least one factor of

```
2.
```

Therefore,

before computing the inverse,

the denominator must become odd.

---

# Child Analogy

Imagine you need a special key.

Unfortunately,

the lock only accepts

```
Odd keys.
```

You arrive with

```
40.
```

The first thing you do is remove every

```
2
```

until only the odd part remains.

```
40

↓

20

↓

10

↓

5
```

Now the key works.

That is exactly what this stage does.

---

# Finding The Largest Power Of Two

OpenZeppelin computes

```solidity
uint256 twos = denominator & (0 - denominator);
```

This famous bit trick extracts

> **The largest power of two dividing the denominator.**

Examples

```
Denominator = 40

Binary

101000
```

Largest power of two dividing 40:

```
8
```

because

```
40

=

8 × 5
```

So

```
twos = 8
```

---

Another example

```
48

=

16 × 3
```

Therefore

```
twos = 16
```

---

If the denominator is already odd,

for example

```
35
```

then

```
twos = 1.
```

Nothing needs to be removed.

---

# Why Remove The Same Factor From lowerPart?

Remember,

after subtracting the remainder,

our equation is

```
ExactProduct

=

Quotient × Denominator
```

Suppose

```
ExactProduct = 40

Denominator = 10
```

We cannot simply change

```
10

↓

5
```

because then

```
40 ÷ 5

=

8
```

instead of

```
4.
```

The equation would change.

So whatever we divide the denominator by,

we must also divide the numerator by.

Example

```
40 ÷ 10

↓

Divide both by 2

↓

20 ÷ 5
```

The quotient stays

```
4.
```

Nothing changed mathematically.

---

# Why Doesn't upperPart Get Divided?

This often confuses people.

We divide

```solidity
lowerPart
```

but not

```solidity
upperPart.
```

Why?

Because

```
upperPart

+

lowerPart
```

still represent one

```
512-bit number.
```

The remaining bits from

```
upperPart
```

will be shifted into

```
lowerPart
```

immediately afterwards.

So OpenZeppelin is **not ignoring upperPart.**

It simply handles it in the next step.

---

# The State Of The Algorithm

Before this section,

we had

```
ExactProduct

÷

Denominator
```

After removing the common power of two,

we have

```
ReducedExactProduct

÷

OddDenominator
```

The quotient is identical.

The only difference is that

```
OddDenominator
```

now has a modular inverse.

---

# Visual Flow

```
Exact Division

↓

Denominator may be even

↓

Find largest power of two

↓

Divide denominator by it

↓

Divide numerator by it

↓

Denominator becomes odd

↓

Ready for modular inverse
```

---

# Key Takeaways

* The modular inverse only exists when the denominator is odd.
* Every factor of two must be removed first.
* `denominator & (-denominator)` extracts the largest power of two dividing the denominator.
* Whatever is removed from the denominator must also be removed from the numerator.
* This preserves the quotient exactly.
* `upperPart` is **not forgotten**—its contribution is restored during the next step when the 512-bit number is reconstructed.
