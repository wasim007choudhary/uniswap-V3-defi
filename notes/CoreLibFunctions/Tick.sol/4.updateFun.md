# Tick.sol — `update()` Function

## What is `update()`?

`update()` does **not** find the next tick.

Finding the next initialized tick is the job of:

```solidity
TickBitmap.nextInitializedTickWithinOneWord()
```

`update()` is also **not changing the pool's current tick**.

Instead:

> `update()` updates the accounting/state of **one specific tick** that has already been identified.

The caller passes the tick that needs to be updated:

```solidity
tick
```

So the mental model is:

```text
TickBitmap
    │
    │ finds the relevant initialized tick
    ▼
nextInitializedTickWithinOneWord()
    │
    ▼
specific tick identified
    │
    ▼
update(tick, ...)
    │
    ├── update liquidityGross
    ├── update liquidityNet
    ├── initialize accounting if needed
    └── tell caller whether initialized status changed
```

### 🧒 Child analogy

Imagine a road with many houses:

```text
🏠 100     🏠 200     🏠 300     🏠 400     🏠 500
```

`TickBitmap` is like:

> 🔍 "Which special house is the next one?"

It finds the relevant tick.

Then `update()` is like:

> 📝 "Okay, we found house 300. Now update house 300's records."

It does **not** go searching for house 400.

The function receives:

## `tick`

```solidity
int24 tick
```

This is the **specific tick that needs to be updated**.

It is not the "next tick finder."

The relevant tick has already been identified by the caller.

### 🧒 Child analogy

```text
TickBitmap → "I found tick 500!" 🔍

```

## `tickCurrent`

```solidity
int24 tickCurrent
```

This is the pool's **current tick**.

It tells `update()` where the current price is relative to the tick being updated.

For example:

```text
tick = 500
tickCurrent = 700
```

means:

```text
500                700
│                   │
│───────────────────●
tick             current
```

So the current tick is to the right of the tick being updated.

## `liquidityDelta`

```solidity
int128 liquidityDelta
```

This is the amount of liquidity being **added or removed** from the tick's liquidity accounting.

It can be positive or negative.

```text
+100 → add liquidity

-100 → remove liquidity
```

### 🧒 Child analogy

Think of a bucket:

```text
🪣
```

Adding liquidity:

```text
🪣 + 💧💧💧
```

Removing liquidity:

```text
🪣 - 💧💧
```

The signed type `int128` is needed because the change can go in either direction.

---

## `feeGrowthGlobal0X128`

```solidity
uint256 feeGrowthGlobal0X128
```

The pool-wide cumulative **fee growth per unit liquidity for token0**, represented in X128 fixed-point format.

It is used when a tick is initialized so the tick can take a fee-growth checkpoint.

Later:

```solidity
info.feeGrowthOutside0X128 = feeGrowthGlobal0X128;
```

### 🧒 Child analogy

Imagine the pool has a giant fee scoreboard:

```text
💰 TOKEN0 FEE SCOREBOARD

0 ───── 10 ───── 20 ───── 30 ───── 40
```

`feeGrowthGlobal0X128` is the current value on that scoreboard.

---

## `feeGrowthGlobal1X128`

```solidity
uint256 feeGrowthGlobal1X128
```

Same idea as token0, but for **token1**.

```text
feeGrowthGlobal0X128 → token0 fee growth

feeGrowthGlobal1X128 → token1 fee growth
```

The two tokens need separate accounting.

---

## `secondsPerLiquidityCumulativeX128`

```solidity
uint160 secondsPerLiquidityCumulativeX128
```

A cumulative accounting value representing **seconds per unit of liquidity**.

The actual pool accounting uses:

```text
seconds / max(1, liquidity)
```

and the value is stored in **X128 fixed-point format**.

### 🧒 Child analogy

Imagine a stopwatch ⏱️ watching the pool.

If:

```text
10 seconds
2 liquidity
```

then conceptually:

```text
10 / 2 = 5 seconds per liquidity
```

If the pool continues operating, this value keeps accumulating.

It is **not** simply:

> "How long has the current price been sitting at this tick?"

It is pool-wide cumulative time/liquidity accounting.

It is later useful for **time-based/oracle accounting**.

When a tick initializes, it can save this value as a checkpoint:

```solidity
info.secondsPerLiquidityOutsideX128 =
    secondsPerLiquidityCumulativeX128;
```

---

## `tickCumulative`

```solidity
int56 tickCumulative
```

A cumulative value based on:

```text
tick × time
```

### 🧒 Child analogy

Suppose:

```text
Tick 10 → for 5 seconds
```

Contribution:

```text
10 × 5 = 50
```

Then:

```text
Tick 20 → for 3 seconds
```

Contribution:

```text
20 × 3 = 60
```

Cumulative value:

```text
50 + 60 = 110
```

So `tickCumulative` is basically a **running scoreboard of tick × time**.

### Why `int56`?

Ticks can be negative:

```text
tick = -100
time = 5

-100 × 5 = -500
```

Therefore the cumulative value can also be negative, so it needs a **signed integer**.

This value is particularly important for **time-weighted/oracle calculations**.

When a tick initializes, it can be saved:

```solidity
info.tickCumulativeOutside = tickCumulative;
```

---

## `time`

```solidity
uint32 time
```

The current block timestamp, represented as a `uint32`.

It is used for time-based accounting.

When a tick initializes, it can save the current timestamp:

```solidity
info.secondsOutside = time;
```

### 🧒 Child analogy

Think of taking a photograph of a clock:

```text
🕐 10:00:00
```

We record:

```text
time = current timestamp
```

Later, another timestamp can be compared with it:

```text
current time - saved time
```

to determine how much time has passed.

## `upper`

```solidity
bool upper
```

Tells `update()` whether the tick being updated is the **upper boundary** of the position.

```text
A = lower                    B = upper
↓                              ↓
●══════════════════════════════●
```

Possible values:

```text
upper = false → lower tick

upper = true  → upper tick
```

### 🧒 Child analogy

Imagine a range has two doors:

```text
🚪 A ====================== B 🚪
   lower                    upper
```

`upper` tells `update()`:

> "Are we working with the right-hand/upper door?"

This matters later when calculating `liquidityNet`, because lower and upper ticks need opposite liquidity-direction behavior.

## `maxLiquidity`

```solidity
uint128 maxLiquidity
```

The maximum total `liquidityGross` allowed at **one tick**.

Later the function checks:

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

### 🧒 Child analogy

Imagine every tick is a bucket:

```text
Tick A → 🪣
Tick B → 🪣
Tick C → 🪣
```

`maxLiquidity` says:

> "This bucket cannot hold more than this much liquidity."

Example:

```text
maxLiquidity = 1,000
```

Then:

```text
liquidityGrossAfter = 900
        ↓
      ≤ 1,000
        ↓
       ✅
```

But:

```text
liquidityGrossAfter = 1,001
        ↓
      > 1,000
        ↓
       ❌ revert
```

This prevents one tick from accumulating more `liquidityGross` than its allowed per-tick limit.

# Return Value — `flipped`

The function returns:

```solidity
returns (bool flipped)
```

`flipped` tells us whether the tick changed between:

```text
initialized
      ↕
uninitialized
```

More precisely, it tells us whether the tick's **zero/non-zero `liquidityGross` state changed**.

The relevant code is:

```solidity
flipped =
    (liquidityGrossAfter == 0)
    !=
    (liquidityGrossBefore == 0);
```

The `!=` asks:

> "Are these two zero/non-zero states different?"

---

## Example — Uninitialized → Initialized

Before:

```text
liquidityGrossBefore = 0
```

After adding liquidity:

```text
liquidityGrossAfter = 500
```

So:

```text
Before → zero
After  → non-zero
```

The states are different:

```text
0 != 500
```

Therefore:

```solidity
flipped = true;
```

The tick flipped:

```text
UNINITIALIZED
      │
      ▼
 INITIALIZED
```

---

## Example — Initialized → Initialized

Before:

```text
liquidityGrossBefore = 500
```

After:

```text
liquidityGrossAfter = 800
```

Both are non-zero:

```text
Before → initialized
After  → initialized
```

Therefore:

```solidity
flipped = false;
```

The initialization status did not change.

---

## Example — Initialized → Uninitialized

Before:

```text
liquidityGrossBefore = 500
```

After removing all liquidity:

```text
liquidityGrossAfter = 0
```

So:

```text
non-zero → zero
```

Therefore:

```solidity
flipped = true;
```

The tick flipped:

```text
INITIALIZED
      │
      ▼
UNINITIALIZED
```

---

# Why does `flipped` matter?

When a tick changes between:

```text
0 liquidityGross
       ↕
non-zero liquidityGross
```

its **initialized status changes**.

That matters to the tick bitmap.

Conceptually:

```text
                 update()
                    │
                    ▼
       Did initialization status change?
                    │
             ┌──────┴──────┐
             │             │
            YES            NO
             │             │
             ▼             ▼
       flipped=true   flipped=false
             │
             ▼
   caller can update
   the bitmap accordingly
```

### 🧒 Simple analogy

Think of a classroom attendance board:

```text
Tick 500 → ❌ nobody
```

Someone provides liquidity:

```text
Tick 500 → ✅ someone is there
```

The status **flipped**.

Later everyone removes their liquidity:

```text
Tick 500 → ❌ nobody
```

It flipped again.

`flipped` simply tells the caller:

> **"This tick changed between having liquidity and having no liquidity."**

## `require(liquidityGrossAfter <= maxLiquidity, 'LO');`

This line checks whether the tick's **new total gross liquidity** is within the maximum liquidity allowed for that tick.

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

### What is it checking?

It checks:

```text
liquidityGrossAfter
        ≤
   maxLiquidity
```

If true:

```text
✅ Continue
```

If false:

```text
❌ Revert
```

---

### 🧒 Child analogy

Imagine every tick has a bucket 🪣 with a maximum capacity.

```text
maxLiquidity = 1,000

        🪣
┌─────────────────┐
│ 💧 💧 💧 💧     │
│                 │
└─────────────────┘
       1,000 max
```

If the new liquidity is:

```text
liquidityGrossAfter = 800
```

then:

```text
800 ≤ 1,000
```

✅ Allowed.

But if:

```text
liquidityGrossAfter = 1,200
```

then:

```text
1,200 ≤ 1,000  ❌
```

The transaction reverts.

---

### 🔥 Important — This is NOT a normal Solidity overflow/underflow check

There are **two different types of protection** here.

#### 1. Arithmetic overflow/underflow

This is handled when calculating:

```solidity
liquidityGrossAfter =
    LiquidityMath.addDelta(
        liquidityGrossBefore,
        liquidityDelta
    );
```

This makes sure the arithmetic itself is valid.

For example, removing too much liquidity must not produce an invalid negative `uint128` value.

---

#### 2. Uniswap's per-tick liquidity limit

This line:

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

checks a **protocol-level rule**:

> One tick cannot have more than its allowed `maxLiquidity`.

So even if the arithmetic is perfectly valid:

```text
500 + 700 = 1,200
```

there is no arithmetic overflow.

But if:

```text
maxLiquidity = 1,000
```

then:

```text
1,200 > 1,000
```

❌ The protocol rejects it.

---

### Solidity 0.8.20 — do we still need this?

**YES.**

Solidity 0.8.x automatically checks normal arithmetic overflow/underflow, but Solidity does **not** know Uniswap's custom rule:

```text
"One tick may hold at most maxLiquidity."
```

The compiler cannot automatically enforce that business/protocol rule.

So:

```text
Solidity's protection
        ↓
"Did the integer arithmetic overflow/underflow?"

        VS

Uniswap's protection
        ↓
"Did this tick exceed its allowed liquidity?"
```

They are **different checks**, and both are needed.

---

### 🧠 Mental hook

> **`addDelta()` protects the arithmetic.**  
> **`maxLiquidity` protects the tick's allowed liquidity capacity.**

## `flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);`

This line determines whether the tick's **initialized status changed**.

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

### 🧠 Break it down

Each `== 0` comparison produces a `bool`:

```text
(liquidityGrossAfter == 0)   → true / false
(liquidityGrossBefore == 0)  → true / false
```

Then `!=` compares those two Boolean values:

```text
true  != false → true
false != true  → true

true  != true  → false
false != false → false
```

So `flipped` becomes `true` **only when one value is zero and the other is non-zero**.

---

### 🔥 This is basically XOR

This is an **XOR (exclusive OR) pattern**.

```text
Before = 0?     After = 0?     Flipped?
────────────────────────────────────────
   No              No             No
   No              Yes            YES
   Yes             No             YES
   Yes             Yes            No
```

In simple words:

> **`flipped = true` only when the tick changes between zero liquidity and non-zero liquidity.**

---

### 🧒 Child analogy

Think of a light switch 💡:

```text
liquidityGross == 0      → OFF
liquidityGross != 0      → ON
```

If we go:

```text
OFF → ON
```

the switch flipped:

```text
flipped = true
```

If we go:

```text
ON → OFF
```

it also flipped:

```text
flipped = true
```

But:

```text
OFF → OFF
```

or:

```text
ON → ON
```

means the state did not change:

```text
flipped = false
```

---

## Can we write it with `if/else`?

Yes, but it is more verbose:

```solidity
if (
    (liquidityGrossAfter == 0 && liquidityGrossBefore != 0) ||
    (liquidityGrossAfter != 0 && liquidityGrossBefore == 0)
) {
    flipped = true;
} else {
    flipped = false;
}
```

The original is much cleaner:

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

---

## What style is this?

You can call it:

- **Boolean expression**
- **Boolean XOR pattern**
- **Compact XOR using `!=`**
- **Expression-based assignment**

It is **not** the ternary operator.

There is also no special Boolean XOR keyword/operator being used here. `!=` is simply comparing the two Boolean results.

---

## Which costs more gas?

For your V3 implementation, keep the original:

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

The `if/else` version is unnecessarily verbose.

With Solidity 0.8.x and the optimizer enabled, the compiler can optimize equivalent Boolean logic heavily, so you should **not expect a meaningful gas difference merely because one is written as an expression and the other as an `if/else`**.

The original is preferable because it expresses the actual logic directly.

### Best form

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

It effectively says:

```text
Before = 0?     After = 0?     Flipped?
   No              No            No
   No              Yes           YES
   Yes             No            YES
   Yes             Yes           No
```

### 🧠 Mental hook

> **`!=` here does NOT compare the liquidity amounts themselves.**

It compares the **Boolean results** of:

```solidity
liquidityGrossAfter == 0
```

and:

```solidity
liquidityGrossBefore == 0
```

Therefore:

> **If the zero/non-zero status changes → `flipped = true`.**

# Tick.sol — `update()` — Tick Initialization Block

## The initialization block

```solidity
if (liquidityGrossBefore == 0) {
    // by convention, we assume that all growth before a tick was initialized happened _below_ the tick
    if (tick <= tickCurrent) {
        info.feeGrowthOutside0X128 = feeGrowthGlobal0X128;
        info.feeGrowthOutside1X128 = feeGrowthGlobal1X128;
        info.secondsPerLiquidityOutsideX128 = secondsPerLiquidityCumulativeX128;
        info.tickCumulativeOutside = tickCumulative;
        info.secondsOutside = time;
    }
    info.initialized = true;
}
```

We already know:

```solidity
liquidityGrossBefore == 0
```

means:

> **This tick was previously uninitialized.**

So this entire block handles the moment when the tick is being **initialized for the first time**.

---

## 🧩 What is this whole block doing?

When a tick becomes initialized, Uniswap has two jobs:

```text
1. Establish the tick's initial accounting checkpoints
2. Mark the tick as initialized
```

Conceptually:

```text
Tick was uninitialized
        ↓
liquidityGrossBefore == 0
        ↓
Initialize the tick
        ↓
Establish accounting baseline
        ↓
Mark initialized = true
```

The accounting fields being initialized are:

## `info.liquidityNet = upper ? ... : ...;`

This line updates the tick's **`liquidityNet`**.

Original Uniswap-style code:

```solidity
info.liquidityNet = upper
    ? int256(info.liquidityNet).sub(liquidityDelta).toInt128()
    : int256(info.liquidityNet).add(liquidityDelta).toInt128();
```

The important logic is simply:

```text
lower tick → +liquidityDelta
upper tick → -liquidityDelta
```

---

## 🧠 Why does lower add and upper subtract?

A position has two boundaries:

```text
A = lower                         B = upper
↓                                  ↓
●══════════════════════════════════●
```

When price moves **left → right**:

```text
        ENTER                         EXIT
          ↓                             ↓
──────────A═════════════════════════════B────────→
          +                             -
       ADD LIQUIDITY                REMOVE LIQUIDITY
```

At the **lower tick A**, crossing into the position means:

```text
liquidityNet += liquidityDelta
```

At the **upper tick B**, crossing out of the position means:

```text
liquidityNet -= liquidityDelta
```

Therefore:

```text
upper = false → ADD liquidityDelta
upper = true  → SUBTRACT liquidityDelta
```

---

## 🧒 Child analogy — A room with two doors 🚪

Imagine the position range is a room:

```text
A 🚪════════════════════════════🚪 B
  LOWER                       UPPER
```

Walking from left to right:

```text
outside → A → INSIDE → B → outside
             ↑             ↑
           enter          exit
```

At A:

```text
+ liquidity
```

At B:

```text
- liquidity
```

So the two boundaries need opposite `liquidityNet` signs.

---

## What about moving right → left?

The physical movement is reversed:

```text
←──────── B ═════════════════════ A ────────
         ↑                             ↑
       ENTER                          EXIT
```

Now:

```text
cross B → add liquidity
cross A → remove liquidity
```

But **we do not change how `liquidityNet` is stored based on direction**.

The stored convention remains:

```text
lower → +liquidityDelta
upper → -liquidityDelta
```

The crossing logic later uses that signed value appropriately depending on the direction.

### 🔥 Important

`update()` is setting the tick's **stored net liquidity change**.

It is not asking:

> "Which direction is the price moving right now?"

Instead it asks:

> **"Is this tick the upper boundary or the lower boundary?"**

That is what `upper` tells us.

# 🔥 Solidity 0.8.20 version

For your Solidity **0.8.20** implementation, you do **not** need to preserve that old conversion/math-library pattern for this operation.

You can write it directly:

```solidity
info.liquidityNet = upper
    ? info.liquidityNet - liquidityDelta
    : info.liquidityNet + liquidityDelta;
```

Or, even more explicitly:

```solidity
if (upper) {
    info.liquidityNet -= liquidityDelta;
} else {
    info.liquidityNet += liquidityDelta;
}
```

No need for:

```solidity
int256(...)
```

No need for:

```solidity
.add(...)
```

No need for:

```solidity
.sub(...)
```

No need for:

```solidity
.toInt128()
```

for this particular `int128` arithmetic.

Solidity 0.8.x provides checked arithmetic for normal `+` and `-`, so an arithmetic overflow/underflow will revert automatically. :contentReference[oaicite:1]{index=1}

Solidity's type system also permits `int128` to be implicitly converted to `int256` when such widening is needed, but there is no reason to manually force that widening here merely to perform this operation. :contentReference[oaicite:2]{index=2}

```text
NEW liquidityNet
```

## What Does `liquidityNet` Mean?

`liquidityNet` represents the **signed net change in active liquidity when the price crosses a tick**.

For a single position:

```text
Position: [20, 50)

Liquidity: 100
```

The position starts at tick `20` and ends at tick `50`.

Therefore:

```text
tick 20 → +100
tick 50 → -100
```

### 📐 Formula — `liquidityNet` Contribution of One Position

At the lower boundary:

\[
\boxed{liquidityNet = +liquidityDelta}
\]

At the upper boundary:

\[
\boxed{liquidityNet = -liquidityDelta}
\]

- **Lower tick:** crossing upward means the position enters the active range, so active liquidity increases.
- **Upper tick:** crossing upward means the position leaves the active range, so active liquidity decreases.

---

## Why Is It `-liquidityDelta` at the Upper Boundary?

The subtraction is **not because `liquidityNet` is inherently subtractive**.

It is because the tick is the **upper boundary of the position**.

For:

```text
Position: [20, 50)

Liquidity: 100
```

when price crosses upward:

```text
cross 20:

active liquidity += 100

cross 50:

active liquidity -= 100
```

Since `liquidityNet` stores the signed change at the boundary:

```text
tick 20 → liquidityNet = +100

tick 50 → liquidityNet = -100
```

### 📐 Formula — Active Liquidity Change When Crossing Upward

\[
\boxed{L_{after}=L_{before}+liquidityNet}
\]

At the upper tick:

\[
L_{after}
=
L_{before}+(-100)
=
L_{before}-100
\]

```solidity
    : int256(info.liquidityNet).add(liquidityDelta).toInt128();
```

can be written in Solidity 0.8.20 as:

```solidity
if (upperBoundary) {
    tickInfo.liquidityNet -= liquidityDelta;
} else {
    tickInfo.liquidityNet += liquidityDelta;
}
```

This is **only the `liquidityNet` update**.

The `liquidityGross` update happens separately.

### 📐 Core Distinction

\[
\boxed{
liquidityGross
=
\text{total liquidity attached to positions using the tick as a boundary}
}
\]

\[
\boxed{
liquidityNet
=
\text{signed active-liquidity change when crossing the tick}
}
\]

For one position `[20, 50)` with liquidity `100`:

```text
tick 20:

    gross = +100

    net   = +100


tick 50:

    gross = +100

    net   = -100
```

### 🔥 Final takeaway

> **Gross is increased at both boundaries.**

> **Net is increased at the lower boundary and decreased at the upper boundary.**

```text
                 LOWER              UPPER
                   ↓                   ↓
                tick 20             tick 50

GROSS             +100                 +100
NET               +100                 -100
```

The reason is simple:

```text
GROSS
→ "How much liquidity is attached to this boundary?"

NET
→ "When crossing this boundary upward,
   how does active liquidity change?"
```

# 🧩 The Function We Are Running

```solidity
function update(
    mapping(int24 => Tick.Info) storage self,
    int24 tick,
    int24 tickCurrent,
    int128 liquidityDelta,
    uint256 feeGrowthGlobal0X128,
    uint256 feeGrowthGlobal1X128,
    uint160 secondsPerLiquidityCumulativeX128,
    int56 tickCumulative,
    uint32 time,
    bool upper,
    uint128 maxLiquidity
) internal returns (bool flipped) {
    Tick.Info storage info = self[tick];

    uint128 liquidityGrossBefore = info.liquidityGross;
    uint128 liquidityGrossAfter =
        LiquidityMath.addDelta(liquidityGrossBefore, liquidityDelta);

    require(liquidityGrossAfter <= maxLiquidity, 'LO');

    flipped =
        (liquidityGrossAfter == 0) !=
        (liquidityGrossBefore == 0);

    if (liquidityGrossBefore == 0) {
        // by convention, we assume that all growth before a tick was initialized happened _below_ the tick
        if (tick <= tickCurrent) {
            info.feeGrowthOutside0X128 = feeGrowthGlobal0X128;
            info.feeGrowthOutside1X128 = feeGrowthGlobal1X128;
            info.secondsPerLiquidityOutsideX128 =
                secondsPerLiquidityCumulativeX128;
            info.tickCumulativeOutside = tickCumulative;
            info.secondsOutside = time;
        }

        info.initialized = true;
    }

    info.liquidityGross = liquidityGrossAfter;

    info.liquidityNet = upper
        ? int256(info.liquidityNet).sub(liquidityDelta).toInt128()
        : int256(info.liquidityNet).add(liquidityDelta).toInt128();
}
```

# 📐 Formula — Position Boundary Liquidity

**What it does:**  
Shows how one position contributes to both boundary ticks.

**Applies to:**  
A position with liquidity `L` and boundaries `[lower, upper)`.

```text
lower tick:

liquidityGross += L
liquidityNet   += L

upper tick:

liquidityGross += L
liquidityNet   -= L
```

For:

```text
L = 100
```

we get:

```text
lower:

gross = +100
net   = +100

upper:

gross = +100
net   = -100
```

# 🧠 WHY THIS MAKES SENSE

The position is active between:

```text
20 ─────────────────────── 50
```

When price moves:

```text
LEFT → RIGHT
```

it crosses 20 first.

At 20:

```text
ENTER POSITION

active liquidity:
+100
```

Then it eventually reaches 50.

At 50:

```text
EXIT POSITION

active liquidity:
-100
```

Therefore:

```text
20 → +100

50 → -100
```

Exactly what `liquidityNet` stores.

# 🏁 FINAL MENTAL MODEL OF `Tick.update()`

If you forget everything else, remember this:

```text
1️⃣ Find the specific tick
        ↓
2️⃣ Read its old gross liquidity
        ↓
3️⃣ Apply liquidityDelta
        ↓
4️⃣ Make sure gross <= maxLiquidity
        ↓
5️⃣ Check whether zero/non-zero state flipped
        ↓
6️⃣ If previously uninitialized:
        establish accounting baseline
        ↓
7️⃣ Mark initialized
        ↓
8️⃣ Store new gross liquidity
        ↓
9️⃣ Update signed net liquidity
        ↓
🔟 DONE
```

# 🔥🔥 THE ULTIMATE ONE-LINER

> **`TickBitmap` finds the relevant tick. `Tick.update()` updates that tick's liquidity and accounting state, initializes it when necessary, and returns `flipped` when its zero/non-zero liquidity state changes.**

And inside that:

```text
liquidityGross
    ↓
total liquidity attached to the boundary

liquidityNet
    ↓
signed active-liquidity change at the boundary

initialized
    ↓
whether the tick is active as an initialized boundary

flipped
    ↓
whether that initialized state changed during this update
```
