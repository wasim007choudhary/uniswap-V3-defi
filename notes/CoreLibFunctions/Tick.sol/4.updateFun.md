# Tick.sol — `update()` Function

## What is `update()`?

`update()` does **not** find the next tick.

Finding the next initialized tick is the job of:

```solidity
TickBitmap.nextInitializedTickWithinOneWord()
```

`update()` is also **not changing the pool's current tick**.

Instead:

> `update()` updates the accounting/state of **one specific tick** that has already been identified.

The caller passes the tick that needs to be updated:

```solidity
tick
```

So the mental model is:

```text
TickBitmap
    │
    │ finds the relevant initialized tick
    ▼
nextInitializedTickWithinOneWord()
    │
    ▼
specific tick identified
    │
    ▼
update(tick, ...)
    │
    ├── update liquidityGross
    ├── update liquidityNet
    ├── initialize accounting if needed
    └── tell caller whether initialized status changed
```

### 🧒 Child analogy

Imagine a road with many houses:

```text
🏠 100     🏠 200     🏠 300     🏠 400     🏠 500
```

`TickBitmap` is like:

> 🔍 "Which special house is the next one?"

It finds the relevant tick.

Then `update()` is like:

> 📝 "Okay, we found house 300. Now update house 300's records."

It does **not** go searching for house 400.

---

# `update()` Arguments

The function receives:

```solidity
function update(
    mapping(int24 => Tick.Info) storage self,
    int24 tick,
    int24 tickCurrent,
    int128 liquidityDelta,
    uint256 feeGrowthGlobal0X128,
    uint256 feeGrowthGlobal1X128,
    uint160 secondsPerLiquidityCumulativeX128,
    int56 tickCumulative,
    uint32 time,
    bool upper,
    uint128 maxLiquidity
) internal returns (bool flipped)
```

```solidity

```

`self` is the mapping containing the information for each tick.

Conceptually:

```text
tick
  │
  ▼
Tick.Info
  │
  ├── liquidityGross
  ├── liquidityNet
  ├── feeGrowthOutside
  ├── tickCumulativeOutside
  ├── secondsPerLiquidityOutside
  ├── secondsOutside
  └── initialized
```

## `tick`

```solidity
int24 tick
```

This is the **specific tick that needs to be updated**.

It is not the "next tick finder."

The relevant tick has already been identified by the caller.

### 🧒 Child analogy

```text
TickBitmap → "I found tick 500!" 🔍

update() → "Okay, give me tick 500's record. 📝"
```

---

## `tickCurrent`

```solidity
int24 tickCurrent
```

This is the pool's **current tick**.

It tells `update()` where the current price is relative to the tick being updated.

For example:

```text
tick = 500
tickCurrent = 700
```

means:

```text
500                700
│                   │
│───────────────────●
tick             current
```

So the current tick is to the right of the tick being updated.

---

## `liquidityDelta`

```solidity
int128 liquidityDelta
```

This is the amount of liquidity being **added or removed** from the tick's liquidity accounting.

It can be positive or negative.

```text
+100 → add liquidity

-100 → remove liquidity
```

### 🧒 Child analogy

Think of a bucket:

```text
🪣
```

Adding liquidity:

```text
🪣 + 💧💧💧
```

Removing liquidity:

```text
🪣 - 💧💧
```

The signed type `int128` is needed because the change can go in either direction.

---

## `feeGrowthGlobal0X128`

```solidity
uint256 feeGrowthGlobal0X128
```

The pool-wide cumulative **fee growth per unit liquidity for token0**, represented in X128 fixed-point format.

It is used when a tick is initialized so the tick can take a fee-growth checkpoint.

Later:

```solidity
info.feeGrowthOutside0X128 = feeGrowthGlobal0X128;
```

### 🧒 Child analogy

Imagine the pool has a giant fee scoreboard:

```text
💰 TOKEN0 FEE SCOREBOARD

0 ───── 10 ───── 20 ───── 30 ───── 40
```

`feeGrowthGlobal0X128` is the current value on that scoreboard.

---

## `feeGrowthGlobal1X128`

```solidity
uint256 feeGrowthGlobal1X128
```

Same idea as token0, but for **token1**.

```text
feeGrowthGlobal0X128 → token0 fee growth

feeGrowthGlobal1X128 → token1 fee growth
```

The two tokens need separate accounting.

---

## `secondsPerLiquidityCumulativeX128`

```solidity
uint160 secondsPerLiquidityCumulativeX128
```

A cumulative accounting value representing **seconds per unit of liquidity**.

The actual pool accounting uses:

```text
seconds / max(1, liquidity)
```

and the value is stored in **X128 fixed-point format**.

### 🧒 Child analogy

Imagine a stopwatch ⏱️ watching the pool.

If:

```text
10 seconds
2 liquidity
```

then conceptually:

```text
10 / 2 = 5 seconds per liquidity
```

If the pool continues operating, this value keeps accumulating.

It is **not** simply:

> "How long has the current price been sitting at this tick?"

It is pool-wide cumulative time/liquidity accounting.

It is later useful for **time-based/oracle accounting**.

When a tick initializes, it can save this value as a checkpoint:

```solidity
info.secondsPerLiquidityOutsideX128 =
    secondsPerLiquidityCumulativeX128;
```

---

## `tickCumulative`

```solidity
int56 tickCumulative
```

A cumulative value based on:

```text
tick × time
```

### 🧒 Child analogy

Suppose:

```text
Tick 10 → for 5 seconds
```

Contribution:

```text
10 × 5 = 50
```

Then:

```text
Tick 20 → for 3 seconds
```

Contribution:

```text
20 × 3 = 60
```

Cumulative value:

```text
50 + 60 = 110
```

So `tickCumulative` is basically a **running scoreboard of tick × time**.

### Why `int56`?

Ticks can be negative:

```text
tick = -100
time = 5

-100 × 5 = -500
```

Therefore the cumulative value can also be negative, so it needs a **signed integer**.

This value is particularly important for **time-weighted/oracle calculations**.

When a tick initializes, it can be saved:

```solidity
info.tickCumulativeOutside = tickCumulative;
```

---

## `time`

```solidity
uint32 time
```

The current block timestamp, represented as a `uint32`.

It is used for time-based accounting.

When a tick initializes, it can save the current timestamp:

```solidity
info.secondsOutside = time;
```

### 🧒 Child analogy

Think of taking a photograph of a clock:

```text
🕐 10:00:00
```

We record:

```text
time = current timestamp
```

Later, another timestamp can be compared with it:

```text
current time - saved time
```

to determine how much time has passed.

---

## `upper`

```solidity
bool upper
```

Tells `update()` whether the tick being updated is the **upper boundary** of the position.

```text
A = lower                    B = upper
↓                              ↓
●══════════════════════════════●
```

Possible values:

```text
upper = false → lower tick

upper = true  → upper tick
```

### 🧒 Child analogy

Imagine a range has two doors:

```text
🚪 A ====================== B 🚪
   lower                    upper
```

`upper` tells `update()`:

> "Are we working with the right-hand/upper door?"

This matters later when calculating `liquidityNet`, because lower and upper ticks need opposite liquidity-direction behavior.

---

## `maxLiquidity`

```solidity
uint128 maxLiquidity
```

The maximum total `liquidityGross` allowed at **one tick**.

Later the function checks:

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

### 🧒 Child analogy

Imagine every tick is a bucket:

```text
Tick A → 🪣
Tick B → 🪣
Tick C → 🪣
```

`maxLiquidity` says:

> "This bucket cannot hold more than this much liquidity."

Example:

```text
maxLiquidity = 1,000
```

Then:

```text
liquidityGrossAfter = 900
        ↓
      ≤ 1,000
        ↓
       ✅
```

But:

```text
liquidityGrossAfter = 1,001
        ↓
      > 1,000
        ↓
       ❌ revert
```

This prevents one tick from accumulating more `liquidityGross` than its allowed per-tick limit.

# Return Value — `flipped`

The function returns:

```solidity
returns (bool flipped)
```

`flipped` tells us whether the tick changed between:

```text
initialized
      ↕
uninitialized
```

More precisely, it tells us whether the tick's **zero/non-zero `liquidityGross` state changed**.

The relevant code is:

```solidity
flipped =
    (liquidityGrossAfter == 0)
    !=
    (liquidityGrossBefore == 0);
```

The `!=` asks:

> "Are these two zero/non-zero states different?"

---

## Example — Uninitialized → Initialized

Before:

```text
liquidityGrossBefore = 0
```

After adding liquidity:

```text
liquidityGrossAfter = 500
```

So:

```text
Before → zero
After  → non-zero
```

The states are different:

```text
0 != 500
```

Therefore:

```solidity
flipped = true;
```

The tick flipped:

```text
UNINITIALIZED
      │
      ▼
 INITIALIZED
```

---

## Example — Initialized → Initialized

Before:

```text
liquidityGrossBefore = 500
```

After:

```text
liquidityGrossAfter = 800
```

Both are non-zero:

```text
Before → initialized
After  → initialized
```

Therefore:

```solidity
flipped = false;
```

The initialization status did not change.

---

## Example — Initialized → Uninitialized

Before:

```text
liquidityGrossBefore = 500
```

After removing all liquidity:

```text
liquidityGrossAfter = 0
```

So:

```text
non-zero → zero
```

Therefore:

```solidity
flipped = true;
```

The tick flipped:

```text
INITIALIZED
      │
      ▼
UNINITIALIZED
```

---

# Why does `flipped` matter?

When a tick changes between:

```text
0 liquidityGross
       ↕
non-zero liquidityGross
```

its **initialized status changes**.

That matters to the tick bitmap.

Conceptually:

```text
                 update()
                    │
                    ▼
       Did initialization status change?
                    │
             ┌──────┴──────┐
             │             │
            YES            NO
             │             │
             ▼             ▼
       flipped=true   flipped=false
             │
             ▼
   caller can update
   the bitmap accordingly
```

### 🧒 Simple analogy

Think of a classroom attendance board:

```text
Tick 500 → ❌ nobody
```

Someone provides liquidity:

```text
Tick 500 → ✅ someone is there
```

The status **flipped**.

Later everyone removes their liquidity:

```text
Tick 500 → ❌ nobody
```

It flipped again.

`flipped` simply tells the caller:

> **"This tick changed between having liquidity and having no liquidity."**

> **Find the `Tick.Info` belonging to `tick` and create a storage reference called `info` that points directly to it.**

## `require(liquidityGrossAfter <= maxLiquidity, 'LO');`

This line checks whether the tick's **new total gross liquidity** is within the maximum liquidity allowed for that tick.

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

### What is it checking?

It checks:

```text
liquidityGrossAfter
        ≤
   maxLiquidity
```

If true:

```text
✅ Continue
```

If false:

```text
❌ Revert
```

---

### 🧒 Child analogy

Imagine every tick has a bucket 🪣 with a maximum capacity.

```text
maxLiquidity = 1,000

        🪣
┌─────────────────┐
│ 💧 💧 💧 💧     │
│                 │
└─────────────────┘
       1,000 max
```

If the new liquidity is:

```text
liquidityGrossAfter = 800
```

then:

```text
800 ≤ 1,000
```

✅ Allowed.

But if:

```text
liquidityGrossAfter = 1,200
```

then:

```text
1,200 ≤ 1,000  ❌
```

The transaction reverts.

---

### 🔥 Important — This is NOT a normal Solidity overflow/underflow check

There are **two different types of protection** here.

#### 1. Arithmetic overflow/underflow

This is handled when calculating:

```solidity
liquidityGrossAfter =
    LiquidityMath.addDelta(
        liquidityGrossBefore,
        liquidityDelta
    );
```

This makes sure the arithmetic itself is valid.

For example, removing too much liquidity must not produce an invalid negative `uint128` value.

---

#### 2. Uniswap's per-tick liquidity limit

This line:

```solidity
require(liquidityGrossAfter <= maxLiquidity, 'LO');
```

checks a **protocol-level rule**:

> One tick cannot have more than its allowed `maxLiquidity`.

So even if the arithmetic is perfectly valid:

```text
500 + 700 = 1,200
```

there is no arithmetic overflow.

But if:

```text
maxLiquidity = 1,000
```

then:

```text
1,200 > 1,000
```

❌ The protocol rejects it.

---

### Solidity 0.8.20 — do we still need this?

**YES.**

Solidity 0.8.x automatically checks normal arithmetic overflow/underflow, but Solidity does **not** know Uniswap's custom rule:

```text
"One tick may hold at most maxLiquidity."
```

The compiler cannot automatically enforce that business/protocol rule.

So:

```text
Solidity's protection
        ↓
"Did the integer arithmetic overflow/underflow?"

        VS

Uniswap's protection
        ↓
"Did this tick exceed its allowed liquidity?"
```

They are **different checks**, and both are needed.

---

### 🧠 Mental hook

> **`addDelta()` protects the arithmetic.**  
> **`maxLiquidity` protects the tick's allowed liquidity capacity.**

## `flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);`

This line determines whether the tick's **initialized status changed**.

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

### 🧠 Break it down

Each `== 0` comparison produces a `bool`:

```text
(liquidityGrossAfter == 0)   → true / false
(liquidityGrossBefore == 0)  → true / false
```

Then `!=` compares those two Boolean values:

```text
true  != false → true
false != true  → true

true  != true  → false
false != false → false
```

So `flipped` becomes `true` **only when one value is zero and the other is non-zero**.

---

### 🔥 This is basically XOR

This is an **XOR (exclusive OR) pattern**.

```text
Before = 0?     After = 0?     Flipped?
────────────────────────────────────────
   No              No             No
   No              Yes            YES
   Yes             No             YES
   Yes             Yes            No
```

In simple words:

> **`flipped = true` only when the tick changes between zero liquidity and non-zero liquidity.**

---

### 🧒 Child analogy

Think of a light switch 💡:

```text
liquidityGross == 0      → OFF
liquidityGross != 0      → ON
```

If we go:

```text
OFF → ON
```

the switch flipped:

```text
flipped = true
```

If we go:

```text
ON → OFF
```

it also flipped:

```text
flipped = true
```

But:

```text
OFF → OFF
```

or:

```text
ON → ON
```

means the state did not change:

```text
flipped = false
```

---

## Can we write it with `if/else`?

Yes, but it is more verbose:

```solidity
if (
    (liquidityGrossAfter == 0 && liquidityGrossBefore != 0) ||
    (liquidityGrossAfter != 0 && liquidityGrossBefore == 0)
) {
    flipped = true;
} else {
    flipped = false;
}
```

The original is much cleaner:

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

---

## What style is this?

You can call it:

- **Boolean expression**
- **Boolean XOR pattern**
- **Compact XOR using `!=`**
- **Expression-based assignment**

It is **not** the ternary operator.

There is also no special Boolean XOR keyword/operator being used here. `!=` is simply comparing the two Boolean results.

---

## Which costs more gas?

For your V3 implementation, keep the original:

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

The `if/else` version is unnecessarily verbose.

With Solidity 0.8.x and the optimizer enabled, the compiler can optimize equivalent Boolean logic heavily, so you should **not expect a meaningful gas difference merely because one is written as an expression and the other as an `if/else`**.

The original is preferable because it expresses the actual logic directly.

### Best form

```solidity
flipped = (liquidityGrossAfter == 0) != (liquidityGrossBefore == 0);
```

It effectively says:

```text
Before = 0?     After = 0?     Flipped?
   No              No            No
   No              Yes           YES
   Yes             No            YES
   Yes             Yes           No
```

### 🧠 Mental hook

> **`!=` here does NOT compare the liquidity amounts themselves.**

It compares the **Boolean results** of:

```solidity
liquidityGrossAfter == 0
```

and:

```solidity
liquidityGrossBefore == 0
```

Therefore:

> **If the zero/non-zero status changes → `flipped = true`.**
