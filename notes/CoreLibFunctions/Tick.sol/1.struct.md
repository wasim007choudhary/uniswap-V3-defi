# Info` Struct Dissection
The `Tick` library stores information about each initialized tick.

Each tick has a `Tick.Info` struct containing:

- liquidity information
- fee-growth information
- cumulative tick/oracle information
- time-related information
- initialization state

```solidity
struct Info {
    // the total position liquidity that references this tick
    uint128 liquidityGross;

    // amount of net liquidity added (subtracted) when tick is crossed
    // from left to right (right to left)
    int128 liquidityNet;

    // fee growth per unit of liquidity on the _other_ side of this tick
    // (relative to the current tick)
    uint256 feeGrowthOutside0X128;

    uint256 feeGrowthOutside1X128;

    // the cumulative tick value on the other side of the tick
    int56 tickCumulativeOutside;

    // the seconds per unit of liquidity on the _other_ side of this tick
    // (relative to the current tick)
    uint160 secondsPerLiquidityOutsideX128;

    // the seconds spent on the other side of the tick
    // (relative to the current tick)
    uint32 secondsOutside;

    // true iff the tick is initialized
    bool initialized;
}
```

---

# 🧩 What is a `Position`?

A **position** is a liquidity provider's chosen price range.

For example:

```text
Position:
Lower tick = 100
Upper tick = 500
```

```text
100 ├──────────────────────────────┤ 500
    ↑                              ↑
  start                          ending
  (lower)                        (upper)
```

A tick can therefore be used by a position as either:

- its **lower/start boundary**, or
- its **upper/ending boundary**.

A single tick can be referenced by many different positions.

Example:

```text
Position A: 100 ───────── 500
                         ↑
                    upper boundary

Position B: 500 ───────── 900
             ↑
        lower boundary
```

Therefore, when Uniswap says that a position **references a tick**, it means that the position uses that tick as one of its boundaries.

---

# 1. `liquidityGross`

```solidity
uint128 liquidityGross;
```

## What does it mean?

`liquidityGross` is the **total liquidity from all positions that use this tick as either their lower or upper boundary**.

For example:

```text
Position A → 100 liquidity → uses tick 500
Position B → 300 liquidity → uses tick 500
Position C → 200 liquidity → uses tick 500
```

Then:

```text
liquidityGross
    =
100 + 300 + 200
    =
600
```

Therefore:

> **`liquidityGross` = total position liquidity that references this tick.**

---

## Why `uint128`?

Liquidity cannot be negative.

```text
liquidity:

0 ───────────────→ positive
```

Therefore it uses an unsigned integer:

```solidity
uint128
```

rather than a signed integer.

---

# 2. `liquidityNet`

```solidity
int128 liquidityNet;
```

## What does it mean?

`liquidityNet` tells Uniswap **how much active liquidity changes when the price crosses this tick**.

Unlike `liquidityGross`, it can be positive or negative.

```text
liquidityNet > 0
        ↓
liquidity is added when crossed
```

```text
liquidityNet < 0
        ↓
liquidity is removed when crossed
```

This depends on:

1. whether the tick is a lower or upper boundary, and
2. the direction in which the price crosses the tick.

---

## Example

Suppose:

```text
Position:
Lower tick = 100
Upper tick = 500
```

```text
100 ─────────────────── 500
↑                       ↑
lower                   upper
```

When price moves **up**:

```text
100 → 500
left → right
```

Crossing the lower tick:

```text
100
 ↓
liquidity is ADDED
```

Crossing the upper tick:

```text
500
 ↓
liquidity is REMOVED
```

When price moves **down**:

```text
500 → 100
right → left
```

the opposite happens:

```text
cross 500
    ↓
liquidity is ADDED

cross 100
    ↓
liquidity is REMOVED
```

Therefore:

> **Depending on whether a tick is a lower or upper boundary, crossing that tick can either add liquidity or remove liquidity; the direction of the price movement determines which happens.**

This is why `liquidityNet` is:

```solidity
int128
```

and not `uint128`.

---

# 3. `feeGrowthOutside0X128`

```solidity
uint256 feeGrowthOutside0X128;
```

This stores **fee growth per unit of liquidity for token0 on the other/outside side of this tick**, relative to the current tick.

The important word here is:

```text
outside
```

A tick is a boundary:

```text
                 TICK
                   │
                   │
       LEFT SIDE   │   RIGHT SIDE
───────────────────┼───────────────────
```

The "outside" side is **not permanently the left side or permanently the right side**.

Which side is considered outside depends on where the **current tick/price is relative to that tick**.

---

## Example — current tick is to the RIGHT

Suppose:

```text
tick = 500
current tick = 700
```

```text
                 500                    700
                  │                      │
──────────────────┼──────────────────────┼──────
                tick                  current
```

The current tick is to the **right** of tick `500`.

Therefore, relative to tick `500`, the other/outside side is the **left side**:

```text
        OUTSIDE
           ↓
───────────┤ 500 ├──────────────────────────→
                                      700
                                    current
```

---

## Example — current tick is to the LEFT

Now suppose:

```text
tick = 500
current tick = 300
```

```text
                300                    500
                 │                      │
─────────────────┼──────────────────────┼──────
              current                  tick
```

The current tick is to the **left** of tick `500`.

Therefore, relative to tick `500`, the other/outside side is the **right side**:

```text
300
current
  │
  ↓
──┼───────────────────────────────┤ 500 ├──────→
                                  ↑
                               OUTSIDE
```

Therefore:

> **"Outside" can be either the left side or the right side. It depends on where the current tick is relative to the tick being examined.**

---

## Important

`feeGrowthOutside0X128` does **not** simply mean:

> "All fees that happened on the right side."

Nor does it simply mean:

> "All fees that happened on the left side."

It is **relative accounting**.

Its meaning depends on:

- when the tick was initialized,
- where the current tick is,
- and whether the tick has been crossed.

Later, Uniswap uses this value together with global fee growth and the lower/upper ticks to calculate the fee growth **inside a position**.

That happens in:

```solidity
getFeeGrowthInside()
```

---

# 4. `feeGrowthOutside1X128`

```solidity
uint256 feeGrowthOutside1X128;
```

This is the same concept as:

```solidity
feeGrowthOutside0X128
```

but for **token1**.

```text
feeGrowthOutside0X128
        ↓
outside fee growth
        ↓
token0

feeGrowthOutside1X128
        ↓
outside fee growth
        ↓
token1
```

A V3 pool has two tokens, so fee growth is tracked separately for each token.

---

# 5. `tickCumulativeOutside`

```solidity
int56 tickCumulativeOutside;
```

This stores the **cumulative tick value on the other/outside side of this tick**, relative to the current tick.

---

## 🧒 First: what does "other side" mean?

Imagine tick `500` as a wall:

```text
                    TICK 500
                       │
                       │
        LEFT SIDE      │      RIGHT SIDE
───────────────────────┼───────────────────────
```

There are two sides:

```text
left
right
```

The outside/other side can be **either one**.

It depends on where the current tick is.

---

## Example 1 — current tick is to the RIGHT

```text
300 ───────── 500 ───────── 700
               ↑             ↑
             tick          current
```

For tick `500`:

```text
current tick = 700
```

The current tick is on the right.

Therefore the outside/other side is the **left side**:

```text
        OUTSIDE
           ↓
300 ────────┤ 500 ├──────────────────── 700
                                      ↑
                                    current
```

---

## Example 2 — current tick is to the LEFT

```text
300 ───────── 500 ───────── 700
 ↑             ↑
current       tick
```

Now:

```text
current tick = 300
```

The current tick is on the left.

Therefore the outside/other side is the **right side**:

```text
300 ────────────────┤ 500 ├────────────── 700
 ↑                       ↑
current                OUTSIDE
```

So:

> **The "outside" side can be the left or right side depending on where the current tick is relative to the tick.**

---

## 🧒 What does "cumulative tick" mean?

It is **not simply the current tick value**.

It is tick information **accumulated over time**.

Imagine:

```text
Time        Tick
────        ────
0 sec        10
10 sec       20
20 sec       30
```

The cumulative tick value keeps accumulating tick × time information.

Conceptually:

```text
tick × time
```

For example:

```text
10 tick × 10 seconds = 100
20 tick × 10 seconds = 200
30 tick × 10 seconds = 300
```

So the cumulative value incorporates the tick values that existed during different periods of time.

This is useful for Uniswap V3's **time-weighted oracle calculations**.

Therefore:

```text
tick
  ↓
accumulated over time
  ↓
on the outside side
  ↓
of this tick
```

= `tickCumulativeOutside`.

---

# 6. `secondsPerLiquidityOutsideX128`

```solidity
uint160 secondsPerLiquidityOutsideX128;
```

This stores the **cumulative seconds per unit of liquidity on the other/outside side of the tick**.

Again, "outside" can mean either:

```text
LEFT
```

or:

```text
RIGHT
```

depending on where the current tick is.

---

## 🧒 Simple example

Suppose:

```text
tick = 500
current tick = 700
```

```text
300 ───────── 500 ───────── 700
               ↑             ↑
             tick          current
```

The outside side of tick `500` is the **left side**.

Suppose that side has:

```text
10 seconds
```

with:

```text
2 units of liquidity
```

Then conceptually:

```text
seconds per liquidity
=
10 seconds ÷ 2 liquidity
=
5
```

So the seconds-per-liquidity accumulator increases according to this relationship.

---

## Another example — outside is the RIGHT side

Suppose:

```text
tick = 500
current tick = 300
```

```text
300 ───────── 500 ───────── 700
 ↑             ↑
current       tick
```

The outside side is now the **right side**.

Suppose:

```text
20 seconds
```

have passed with:

```text
4 units of liquidity
```

Then:

```text
seconds per liquidity
=
20 ÷ 4
=
5
```

Again, this value is **cumulative**, so it continues accumulating as time passes.

---

## 🧠 Why does Uniswap store this?

Uniswap needs to know how much time/liquidity accounting belongs to different sides of tick boundaries.

Instead of going through every tick and calculating everything from scratch, each initialized tick stores the information needed to derive the relevant values efficiently.

So:

```text
secondsPerLiquidityOutsideX128
            ↓
cumulative
            ↓
seconds per unit of liquidity
            ↓
on the outside/other side
            ↓
of this tick
```

---

# 7. `secondsOutside`

```solidity
uint32 secondsOutside;
```

This stores the **cumulative amount of time spent on the other/outside side of the tick**, relative to the current tick.

The same outside-side concept applies:

```text
current tick on LEFT
        ↓
outside can be RIGHT

current tick on RIGHT
        ↓
outside can be LEFT
```

---

## Difference from `secondsPerLiquidityOutsideX128`

These two fields are related but are **not the same thing**:

```text
secondsOutside
      ↓
raw time
```

while:

```text
secondsPerLiquidityOutsideX128
      ↓
time relative to liquidity
```

So:

```text
secondsOutside
=
"How many seconds?"

secondsPerLiquidityOutsideX128
=
"How many seconds per unit of liquidity?"
```

---

# 8. `initialized`

```solidity
bool initialized;
```

This tells us whether the tick is initialized.

The important relationship is:

```text
initialized
     ⇕
liquidityGross != 0
```

So:

```text
liquidityGross == 0
        ↓
uninitialized
```

and:

```text
liquidityGross != 0
        ↓
initialized
```

Uniswap still stores the `bool` because it is useful for **gas/storage optimization**, particularly around tick crossing.

# 🧠 Important Mental Model — All Fields Together

Think of `Tick.Info` as the complete **state record attached to one tick boundary**:

```text
┌──────────────────────────────────────────────┐
│                  Tick.Info                   │
├──────────────────────────────────────────────┤
│ liquidityGross                               │
│   ↓                                          │
│ total position liquidity using this tick     │
├──────────────────────────────────────────────┤
│ liquidityNet                                 │
│   ↓                                          │
│ liquidity change when this tick is crossed   │
├──────────────────────────────────────────────┤
│ feeGrowthOutside0X128                        │
│   ↓                                          │
│ token0 fee growth on the outside side        │
├──────────────────────────────────────────────┤
│ feeGrowthOutside1X128                        │
│   ↓                                          │
│ token1 fee growth on the outside side        │
├──────────────────────────────────────────────┤
│ tickCumulativeOutside                        │
│   ↓                                          │
│ cumulative tick information on outside side  │
├──────────────────────────────────────────────┤
│ secondsPerLiquidityOutsideX128               │
│   ↓                                          │
│ cumulative seconds/liquidity outside         │
├──────────────────────────────────────────────┤
│ secondsOutside                               │
│   ↓                                          │
│ cumulative seconds on outside side           │
├──────────────────────────────────────────────┤
│ initialized                                  │
│   ↓                                          │
│ whether this tick is initialized              │
└──────────────────────────────────────────────┘
```

---

# 🔑 The Most Important Distinction

```text
liquidityGross
        ↓
"How much total position liquidity references
 this tick as a boundary?"
```

versus:

```text
liquidityNet
        ↓
"How much active liquidity changes when
 this tick is crossed?"
```

And for the `Outside` fields:

```text
                    TICK
                     │
          ┌──────────┴──────────┐
          │                     │
       LEFT SIDE             RIGHT SIDE
          │                     │
          └──────────┬──────────┘
                     │
               "outside"
```

**Outside is not permanently LEFT or RIGHT.**

It depends on where the **current tick/price is relative to the tick being examined**.

As price moves and crosses tick boundaries, Uniswap updates the outside accounting so that it continues to represent the correct opposite side.

```text
Price movement
      ↓
cross a tick
      ↓
update outside accounting
      ↓
continue moving
      ↓
cross another tick
      ↓
update that tick's accounting
```

This is why the `cross()` function later becomes extremely important.
