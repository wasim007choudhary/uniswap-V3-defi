# 🧠 Uniswap V3 — Tick.sol
# `tickSpacingToMaxLiquidityPerTick()`

This function calculates the **maximum `liquidityGross` that can be stored at one tick**, based on the pool's `tickSpacing`.

---

## 🔹 Function

```solidity
function tickSpacingToMaxLiquidityPerTick(
    int24 tickSpacing
) internal pure returns (uint128) {
    int24 minTick = (TickMath.MIN_TICK / tickSpacing) * tickSpacing;
    int24 maxTick = (TickMath.MAX_TICK / tickSpacing) * tickSpacing;
    uint24 numTicks = uint24((maxTick - minTick) / tickSpacing) + 1;
    return type(uint128).max / numTicks;
}
```

---

# 1️⃣ Function Signature

```solidity
function tickSpacingToMaxLiquidityPerTick(
    int24 tickSpacing
) internal pure returns (uint128)
```

### What is this function doing?

It calculates:

> **The maximum amount of `liquidityGross` that can exist at any single tick for a particular `tickSpacing`.**

The function receives:

```solidity
int24 tickSpacing
```

and returns:

```solidity
uint128
```

because `liquidityGross` is stored as:

```solidity
uint128 liquidityGross;
```

---

## 🧠 What is `tickSpacing`?

`tickSpacing` determines which ticks can be used as tick boundaries.

For example, if:

```text
tickSpacing = 10
```

then usable tick boundaries look like:

```text
... -30  -20  -10   0   +10  +20  +30 ...
```

You cannot use:

```text
-25
-17
+13
+27
```

as initialized position boundaries because they don't lie on the spacing grid.

So:

```text
smaller tickSpacing
        ↓
more usable ticks

larger tickSpacing
        ↓
fewer usable ticks
```

---

# 2️⃣ `minTick`

```solidity
int24 minTick = (TickMath.MIN_TICK / tickSpacing) * tickSpacing;
```

This finds:

> **The lowest usable tick according to this pool's `tickSpacing`.**

---

## 🧠 First: `TickMath.MIN_TICK`

Uniswap V3 defines:

```solidity
TickMath.MIN_TICK = -887272
```

This is the **absolute minimum tick supported by the V3 tick/price system**.

The corresponding price is also the lower mathematical price boundary of the supported V3 price range.

The relationship is approximately:

\[
P = 1.0001^{tick}
\]

Therefore:

```text
MIN_TICK
   ↓
minimum supported tick
   ↓
minimum corresponding price
```

Similarly:

```solidity
TickMath.MAX_TICK = 887272
```

is the maximum supported tick and corresponding upper price boundary.

---

## 📐 Why `±887272`?

The number is not arbitrary.

Uniswap uses approximately:

\[
P = 1.0001^{tick}
\]

and therefore:

\[
1.0001^{887272} \approx 2^{128}
\]

while:

\[
1.0001^{-887272} \approx 2^{-128}
\]

So the tick range provides an enormous price range.

Conceptually:

```text
2^-128                                      2^128
  │--------------------------------------------│
  ↑                                            ↑
MIN_TICK                                    MAX_TICK
-887272                                      +887272
```

The limits are also chosen around the representational boundaries needed by V3's `sqrtPriceX96` / `uint160` price representation.

The important distinction is:

```text
TickMath.MIN_TICK / MAX_TICK
        ↓
absolute protocol/math boundaries


minTick / maxTick
        ↓
spacing-aligned usable boundaries
        ↓
depend on THIS pool's tickSpacing
```

---

# 3️⃣ Why multiply by `tickSpacing`?

The line is:

```solidity
int24 minTick = (TickMath.MIN_TICK / tickSpacing) * tickSpacing;
```

Suppose, for a small example:

```text
MIN_TICK    = -887
tickSpacing = 10
```

Then:

```text
-887 / 10 = -88
```

Solidity signed integer division truncates toward zero.

So:

```text
-88 × 10 = -880
```

Therefore:

```text
minTick = -880
```

---

## 🧠 Why does this work?

The multiplication brings the value back onto the spacing grid.

For spacing `10`, valid boundaries must be multiples of `10`:

```text
... -900  -890  -880  -870 ... 0 ... +870 +880 +890 +900 ...
```

The absolute lower boundary is:

```text
-887
```

but `-887` is not divisible by `10`.

So the lowest spacing-aligned value inside the supported range is:

```text
-880
```

Visual:

```text
MIN_TICK = -887
       │
       │ not aligned with spacing 10
       ↓
-880 ──────────────── ← lowest usable tick
-870
-860
-850
...
```

---

# 4️⃣ Important Signed-Division Detail

Solidity signed division truncates toward zero.

For example:

```text
 15 / 10 =  1
-15 / 10 = -1
```

Mathematical floor would give:

```text
floor(-15 / 10) = -2
```

but Solidity gives:

```text
-15 / 10 = -1
```

The identity is:

\[
a = (a/b)\times b + (a\%b)
\]

For:

```text
-15 / 10
```

we get:

```text
-15 = (-1 × 10) + (-5)
```

So:

```text
-15 / 10 = -1
-15 % 10 = -5
```

This matters when working with negative ticks.

For this particular `minTick` calculation:

```text
-887272 / tickSpacing
```

is followed by:

```text
× tickSpacing
```

which brings the value to the spacing-aligned tick.

---

# 5️⃣ `minTick` Is NOT `MIN_TICK`

This distinction is very important.

```text
TickMath.MIN_TICK
        ↓
absolute lowest supported tick


minTick
        ↓
lowest tick aligned to this pool's spacing
```

Example:

```text
MIN_TICK = -887
tickSpacing = 10

minTick = -880
```

So:

```text
absolute limit:       -887
lowest usable grid:   -880
```

---

## 🧒 Simple Analogy

Imagine a building.

```text
🏢 -887  ← absolute bottom of the building
```

But your elevator only stops every 10 floors:

```text
-880
-870
-860
...
```

Then:

```text
-887 = absolute boundary
-880 = lowest usable stopping point
```

So:

> `MIN_TICK` is the fence/wall of the supported range, while `minTick` is the lowest spacing-aligned point that the pool can use.

---

# 6️⃣ `maxTick`

```solidity
int24 maxTick = (TickMath.MAX_TICK / tickSpacing) * tickSpacing;
```

This is the exact mirror of `minTick`.

It finds:

> **The highest usable tick according to this pool's `tickSpacing`.**

Suppose:

```text
MAX_TICK    = 887
tickSpacing = 10
```

Then:

```text
887 / 10 = 88
```

Integer division removes the remainder:

```text
88 × 10 = 880
```

Therefore:

```text
maxTick = 880
```

Visual:

```text
                    MAX_TICK
                       887
                        │
                        │ not aligned
                        ↓
... 850  860  870  880
                    ↑
             highest usable tick
```

---

## 📐 Formula — Highest spacing-aligned tick

\[
\boxed{
maxTick =
\left\lfloor
\frac{MAX\_TICK}{tickSpacing}
\right\rfloor
\times tickSpacing
}
\]

### What it does

Finds the highest tick that lies exactly on the pool's spacing grid.

### Applies to

The upper boundary of the usable tick range for that pool.

---

# 7️⃣ `numTicks`

```solidity
uint24 numTicks = uint24((maxTick - minTick) / tickSpacing) + 1;
```

This answers:

> **How many usable tick positions exist between `minTick` and `maxTick`?**

Important:

It is counting **usable spacing-aligned tick positions**, not actually initialized ticks.

---

## 🧮 Small Example

Suppose:

```text
minTick     = -20
maxTick     = +20
tickSpacing = 10
```

The usable tick positions are:

```text
-20    -10     0     +10    +20
  ●─────●──────●──────●──────●
```

---

## Step 1 — Calculate total tick distance

```solidity
maxTick - minTick
```

becomes:

```text
20 - (-20)
= 40
```

So there are:

```text
40 tick units
```

between the endpoints.

---

## Step 2 — Divide by `tickSpacing`

```solidity
(maxTick - minTick) / tickSpacing
```

becomes:

```text
40 / 10
= 4
```

This gives:

> **4 spacing intervals/gaps.**

They are:

```text
-20 → -10    1
-10 →   0    2
  0 → +10    3
+10 → +20    4
```

Visual:

```text
-20────-10────0────+10────+20
  1      2      3      4
       spacing intervals
```

---

# 8️⃣ Why `+ 1`?

Because **4 gaps contain 5 points**.

```text
●────●────●────●────●
1    2    3    4    5
```

There are:

```text
4 gaps
```

but:

```text
5 tick positions
```

Therefore:

```text
4 + 1 = 5
```

So:

```solidity
numTicks = 5;
```

---

## 📐 Formula — Number of Usable Tick Positions

\[
\boxed{
numTicks =
\frac{maxTick-minTick}{tickSpacing}+1
}
\]

### What it does

Converts the total tick range into the number of spacing-aligned tick positions.

### Why `+1`?

Because the calculation before `+1` counts **intervals/gaps**, while `numTicks` needs to count **positions**.

```text
       4 gaps
     ↓  ↓  ↓  ↓

●────●────●────●────●
↑                   ↑
1                   5

4 gaps + 1 = 5 positions
```

---

# 9️⃣ Very Important: Usable ≠ Actually Initialized

This distinction matters.

When we calculate:

```solidity
numTicks
```

we are **NOT** asking:

> "How many ticks currently have liquidity?"

We are asking:

> "How many ticks COULD be used as initialized tick boundaries in this pool because they are aligned with `tickSpacing`?"

For example:

```text
tickSpacing = 10

-20   -10    0   +10   +20
 ●     ●     ●     ●     ●
```

There are **5 usable positions**.

But perhaps only:

```text
-20
+10
```

are actually initialized because LPs have positions using those ticks.

Then:

```text
usable tick positions = 5
actually initialized   = 2
```

So:

```text
numTicks = 5
```

not `2`.

---

# 🔟 Final Line

```solidity
return type(uint128).max / numTicks;
```

This calculates:

> **The maximum `liquidityGross` that can be stored at one individual tick.**

Remember:

```solidity
uint128 liquidityGross;
```

Therefore the maximum value that the storage type can represent is:

```solidity
type(uint128).max
```

which mathematically is:

\[
2^{128}-1
\]

So Uniswap calculates:

\[
\boxed{
maxLiquidityPerTick =
\frac{2^{128}-1}{numTicks}
}
\]

---

# 🧠 Why Divide by `numTicks`?

The idea is to create a **per-tick liquidity cap** based on how many usable ticks exist.

Conceptually:

```text
uint128 maximum capacity
        │
        ÷
number of usable ticks
        │
        ↓
maximum liquidityGross
allowed at ONE tick
```

So:

```text
smaller tickSpacing
        ↓
more usable ticks
        ↓
larger numTicks
        ↓
smaller max liquidity per tick
```

And:

```text
larger tickSpacing
        ↓
fewer usable ticks
        ↓
smaller numTicks
        ↓
larger max liquidity per tick
```

---

# 🧮 Tiny Example

Suppose:

```text
numTicks = 5
```

Then conceptually:

```text
uint128 MAX
     ÷
     5
     ↓
maximum liquidityGross allowed
at one tick
```

It does **not** mean that each tick permanently receives one-fifth of the pool's liquidity.

It is a **per-tick safety limit**.

# 🧠 The Core Mental Model

Remember this chain:

```text
tickSpacing
     ↓
which tick boundaries are usable
     ↓
minTick + maxTick
     ↓
how many usable tick positions exist
     ↓
numTicks
     ↓
uint128 capacity divided by numTicks
     ↓
maxLiquidityPerTick
```

And the most important distinction:

```text
TickMath.MIN_TICK / MAX_TICK
        =
absolute supported boundaries


minTick / maxTick
        =
spacing-aligned usable boundaries


numTicks
        =
number of POSSIBLE usable tick positions


initialized ticks
        =
ticks actually used by LP positions
```

Those last two are **not the same thing**.
