# 🔄 `Tick.cross()` — Start From Zero

This is the complete `Tick.cross()` dissection from the beginning of the discussion to the final rule.

The goal is not just to know what each line does.

The goal is to understand:

```text
WHY is this function needed?
WHEN is it called?
WHAT is the crossed tick?
WHAT does "outside" mean here?
WHY does GLOBAL - OLD OUTSIDE work?
WHY is there no currentTick / direction argument?
WHERE is liquidityNet actually created?
WHO updates active liquidity?
AND how does the whole thing work in both directions?
```

---

# 🎯 First: What Is `cross()`?

The function:

```solidity
function cross(
    mapping(int24 => Tick.Info) storage self,
    int24 tick,
    uint256 feeGrowthGlobal0X128,
    uint256 feeGrowthGlobal1X128,
    uint160 secondsPerLiquidityCumulativeX128,
    int56 tickCumulative,
    uint32 time
) internal returns (int128 liquidityNet) {
    Tick.Info storage info = self[tick];

    info.feeGrowthOutside0X128 =
        feeGrowthGlobal0X128 - info.feeGrowthOutside0X128;

    info.feeGrowthOutside1X128 =
        feeGrowthGlobal1X128 - info.feeGrowthOutside1X128;

    info.secondsPerLiquidityOutsideX128 =
        secondsPerLiquidityCumulativeX128 -
        info.secondsPerLiquidityOutsideX128;

    info.tickCumulativeOutside =
        tickCumulative - info.tickCumulativeOutside;

    info.secondsOutside =
        time - info.secondsOutside;

    liquidityNet = info.liquidityNet;
}
```

At the highest level:

> `cross()` is called when price crosses an initialized tick.

It does two main things:

```text
1. Flip the tick's "outside" accounting.
2. Return the tick's already-stored liquidityNet.
```

---

# 🧒 Child Analogy — A Hallway With Doors

Imagine the whole tick system as a hallway:

```text
A 🚪--------B 🚪--------C 🚪--------D 🚪--------E 🚪--------F 🚪
100         200         300         400         500         600
```

Each initialized tick is like a door.

The price is a kid walking through the hallway.

If the kid reaches `D`:

```text
A -------- B -------- C -------- D -------- E -------- F
100 ----- 200 ----- 300 ----- 400 ----- 500 ----- 600
                              ↑
                           TICK D
```

and the price crosses it, `cross()` runs for that tick.

So:

```text
kid              = current price
door             = initialized tick
cross()          = update the tick because price crossed it
```

---

# 🔥 The Most Important Idea — `Outside` Flips

Suppose:

```text
PRICE -------- TICK 500 --------
```

The price is on the left side of tick `500`.

Then after crossing:

```text
--------- TICK 500 -------- PRICE
```

Now the price is on the right side.

The tick itself did not move.

The price moved.

Because the price moved from one side of the tick to the other, the side considered **outside** flips.

That is why `cross()` changes all the stored `Outside` values.

---

# 🧠 The Core Trick

Instead of figuring out everything again after every crossing, Uniswap uses:

```text
NEW OUTSIDE
=
GLOBAL
-
OLD OUTSIDE
```

This is the central trick of `cross()`.

---

# 🧮 Why Does `GLOBAL - OLD OUTSIDE` Work?

Suppose:

```text
GLOBAL = 100
```

and:

```text
OLD OUTSIDE = 30
```

The whole cumulative accounting can be viewed as:

```text
GLOBAL = OLD OUTSIDE + OTHER SIDE

100 = 30 + 70
```

Therefore:

```text
OTHER SIDE = 100 - 30 = 70
```

After the price crosses the tick, the other side becomes the new outside side.

So:

```text
OLD OUTSIDE = 30

       CROSS

NEW OUTSIDE = 70
```

That is exactly what:

```solidity
GLOBAL - OLD OUTSIDE
```

does.

---

# ⚠️ "Flip" Does NOT Mean Negate

This is very important.

When we say `cross()` **flips** the outside value, we do NOT mean:

```text
new = -old
```

For example:

```text
old = 300
global = 1000
```

Then:

```text
new = 1000 - 300
    = 700
```

So:

```text
300 → 700
```

not:

```text
300 → -300
```

# 🧭 Does `cross()` Have a Fixed Direction?

No.

`cross()` itself is **direction-agnostic**.

There is no parameter like:

```solidity
bool movingRight
```

and no:

```solidity
bool movingLeft
```

Instead, `cross()` is used whenever the price crosses an initialized tick.

So it can happen in both directions:

```text
LEFT → RIGHT
```

and:

```text
RIGHT → LEFT
```

# 🔥 Important Clarification About Direction

The fact that `cross()` itself is direction-agnostic does **NOT** mean direction is irrelevant to the entire swap.

Direction is still important to the **swap caller**.

The split is:

```text
cross()
    ↓
flip tick accounting
    ↓
return liquidityNet

swap logic
    ↓
knows movement direction
    ↓
applies liquidityNet appropriately
```

# 🧩 Compare `updateTick()` and `cross()`

This distinction is extremely important.

## `updateTick()`

`updateTick()` is used when a position's liquidity is being added or removed.

It establishes the tick's signed `liquidityNet`.

For:

```text
A ---------------- B
↑                    ↑
lower                upper
```

and:

```text
L = 100
```

the convention is:

```text
A.liquidityNet = +100
B.liquidityNet = -100
```

That is created here:

```solidity
if (upperBoundary) {
    tickInfo.liquidityNet -= liquidityDelta;
} else {
    tickInfo.liquidityNet += liquidityDelta;
}
```

---

## `cross()`

Later, when price actually crosses one of those initialized ticks:

```text
price moves
    ↓
crosses tick
    ↓
cross()
```

`cross()` does NOT recreate the `+100` or `-100`.

It reads it:

```solidity
liquidityNet = info.liquidityNet;
```

---

# 🔥 Where Is `liquidityNet` Actually Created?

Earlier, `updateTick()` does the work.

For one position:

```text
A ---------------- B
↑                    ↑
lower                upper
```

with:

```text
L = 100
```

At lower:

```text
0 + 100 = +100
```

At upper:

```text
0 - 100 = -100
```

So the ticks end up with:

```text
A → liquidityNet = +100
B → liquidityNet = -100
```

Later:

```text
cross(A)
```

returns:

```text
+100
```

and:

```text
cross(B)
```

returns:

```text
-100
```

# 🧠 `cross()` Does Not Calculate LiquidityNet

This was an important question.

The final line is:

```solidity
liquidityNet = info.liquidityNet;
```

It is simply:

```text
READ
 ↓
RETURN
```

There is no:

```text
+ liquidityDelta
```

or:

```text
- liquidityDelta
```

inside `cross()`.

Those signs were established earlier by `updateTick()`.

# 🧠 Then Who Updates Active Liquidity?

The **swap logic that calls `cross()`**.

The complete relationship is:

```text
LP creates/removes position
            ↓
       updateTick()
            ↓
    liquidityNet stored
            ↓
       time passes
            ↓
      price moves
            ↓
 price crosses initialized tick
            ↓
         cross()
            ↓
 flips outside accounting
            ↓
 returns stored liquidityNet
            ↓
      swap caller
            ↓
 updates ACTIVE liquidity
```

So there are three separate jobs:

```text
updateTick()
    → establishes liquidityNet

cross()
    → reads and returns liquidityNet

swap logic
    → applies liquidityNet to active liquidity
```

Imagine a door has a sign attached to it:


When the position was created, the protocol wrote a number on the door:



`cross()` does not calculate a new number.

It says:

> "The door was crossed. Flip its accounting and give me the number written on the door."

# 🧠 Why Does `cross()` Return `liquidityNet` Instead of Updating Active Liquidity?

Because `cross()` does not own the complete swap-direction context.

The caller knows whether the price is moving:

```text
LEFT → RIGHT
```

or:

```text
RIGHT → LEFT
```

The same stored signed `liquidityNet` can therefore be applied differently depending on direction.

Conceptually:

```text
Left → Right:
activeLiquidity += liquidityNet
```

```text
Right → Left:
activeLiquidity -= liquidityNet
```

The exact caller code handles this direction-aware application.

The key point is:

> `cross()` returns the number. The swap logic applies the number.

# 🧭 Reverse Direction

Now price is above the range:

```text
100 ------------------------- 500 -------- PRICE
```

and moves left:

```text
PRICE ←
```

It first crosses the upper boundary:

```text
500
```

The stored value is:

```text
-100
```

The caller applies the reverse-direction effect:

```text
activeLiquidity -= (-100)
```

which becomes:

```text
activeLiquidity += 100
```

The position becomes active again.

Later crossing the lower boundary:

```text
100
```

uses:

```text
+100
```

and the reverse-direction caller applies:

```text
activeLiquidity -= (+100)
```

so:

```text
activeLiquidity -= 100
```

The position leaves the active range.

---

# 🔥 This Is the Key to the `liquidityNet` Sign

Stored at boundaries:

```text
lower → +L
upper → -L
```

But the effect on active liquidity depends on movement direction.

Therefore:

```text
             STORED
              NET
               │
        ┌──────┴──────┐
        ↓             ↓
     lower          upper
       +L             -L
```

Then:

```text
LEFT → RIGHT
    ↓
activeLiquidity += liquidityNet
```

and:

```text
RIGHT → LEFT
    ↓
activeLiquidity -= liquidityNet
```

The swap caller handles this.

The tick does not need two stored numbers like:

# 🔥 `cross()` vs `getFeeGrowthInside()`

These functions use the same `feeGrowthOutside` data but for different jobs.

## `getFeeGrowthInside()`

It asks:

> "How much fee growth belongs inside this LP's range?"

Therefore it must determine:

```text
BELOW
INSIDE
ABOVE
```

and use:

```text
tickCurrent
```

to decide how the stored outside checkpoints should be interpreted.

Example:

```text
A -------- C -------- B
```

The function needs to know where `C` is relative to `A` and `B`.

---

## `cross()`

It asks:

> "The price just crossed this tick. Flip the tick's outside accounting."

The crossing itself tells us the side has flipped.

Therefore:

```text
NEW OUTSIDE
=
GLOBAL
-
OLD OUTSIDE
```

No `currentTick` condition is necessary.

---

# 🧠 Fixed "Below"/"Above" vs Relative "Outside"

This was an important distinction.

For a position:

```text
A ---------------- B
```

the meanings:

```text
Below A
Above B
```

are fixed spatial regions.

Below A is always:

```text
<---------------- A
```

Above B is always:

```text
B ---------------->
```

The current tick does not change those meanings.

But `Outside` is a stored accounting relationship that depends on which side of a boundary the pool is currently on.

That is why the interpretation changes.

---

# 🧩 Why `getFeeGrowthInside()` Can Need `GLOBAL - OUTSIDE`

Suppose:

```text
C -------- A -------- B
```

Current is below the range.

At lower `A`, the stored outside checkpoint does not directly equal the fixed spatial region "below A" in the way needed for the inside calculation.

So the function uses the complement:

```text
GLOBAL - OUTSIDE
```

Likewise, if:

```text
A -------- B -------- C
```

current is above the range, the upper boundary's stored outside value may need to be complemented to recover the fixed above region.

---

# 🧠 Why `cross()` Does Not Need That Whole Decision

Because `cross()` already knows:

```text
the tick was crossed
```

Therefore it knows the outside relationship needs to flip.

So it can directly do:

```text
GLOBAL - OLD OUTSIDE
```

for each cumulative field.

This is the "shortcut" or "trick" we were talking about.

---

# 🔥 Another Way to See the Trick

Without the crossing fact, you might think:

```text
Where is current?
Which side is outside?
Is the desired value below?
Is it above?
Should I use OUTSIDE?
Should I use GLOBAL - OUTSIDE?
```

That can require conditions.

But when a crossing has already happened:

```text
OLD OUTSIDE
     ↓
cross happened
     ↓
other side is now outside
```

So:

```text
GLOBAL - OLD OUTSIDE
```

is enough.

---

# 🏗️ `cross()` Is Small Because the Earlier System Did the Setup

This is another major mental point.

By the time `cross()` is called:

```text
the tick already exists
the tick is initialized
liquidityNet already exists
outside checkpoints already exist
```

So `cross()` does not have to build any of that.

It only transitions the stored cumulative state.

`cross()` does not:

The relevant responsibilities are elsewhere.

# 🧠 Who Finds the Next Tick?

`cross()` itself does not find the next initialized tick.

The swap logic uses the tick-search mechanism, such as `TickBitmap`, to find the relevant initialized tick.

Conceptually:

```text

    ↓

    ↓
price reaches it
    ↓
cross()
```

So:

```text
TickBitmap = finds the tick
cross()    = updates the tick after crossing
```
