# Uniswap V3 — `SafeCast.toInt256()`

## Third Function: `uint256 → int256`

This is the **third function** in Uniswap V3's `SafeCast` library.

```solidity
/// @notice Cast a uint256 to a int256, revert on overflow
/// @param y The uint256 to be casted
/// @return z The casted integer, now type int256
function toInt256(uint256 y) internal pure returns (int256 z) {
    require(y < 2**255);
    z = int256(y);
}
```

---

# 1. What does this function do?

It takes a positive number (`uint256`) and turns it into a number that can be positive or negative (`int256`).

Think of it like this:

```text
uint256 = a jar that can ONLY hold positive candies
         (0, 1, 2, 3, ...)

int256  = a jar that can hold positive OR negative candies
         (..., -3, -2, -1, 0, 1, 2, 3, ...)
```

Sometimes we need to put a positive number into the "positive or negative" jar, but we need to make sure it fits.

So the function's job is:

```text
uint256
   ↓
check whether it fits into int256
   ↓
convert it
   ↓
int256
```

---

# 2. The magic number: `2**255`

The key to understanding this function is the range of the two types.

### `int256`

An `int256` can hold:

```text
-2^255  to  2^255 - 1
```

### `uint256`

A `uint256` can hold:

```text
0  to  2^256 - 1
```

Visualized:

```text
uint256 range:

[0 ..................................................... 2^256 - 1]


int256 range:

[-2^255 ................................ 0 ................................ 2^255 - 1]
     ↑                                  ↑                         ↑
 very negative                         zero                 very positive
```

The important thing is that the largest positive value of `int256` is only:

```text
2^255 - 1
```

while `uint256` can go all the way up to:

```text
2^256 - 1
```

---

# 3. Why `require(y < 2**255)`?

The function says:

```solidity
require(y < 2**255);
```

This means:

> **"Make sure this positive `uint256` number is small enough to fit inside the positive side of `int256`."**

Why exactly `2**255`?

Because the biggest positive number an `int256` can hold is:

```text
2^255 - 1
```

And:

```text
y < 2^255
```

is equivalent to:

```text
y <= 2^255 - 1
```

because `y` is an integer.

So:

```text
y < 2^255
    ↓
y can be at most 2^255 - 1
    ↓
fits inside positive int256
```

If:

```text
y >= 2^255
```

then the number is too large for the positive range of `int256`.

Therefore:

```solidity
require(false);
```

and the function reverts.

---

# 4. Example table

| Value of `y` | Does it pass? | Why? |
|---|---:|---|
| `0` | ✅ Yes | `0 < 2^255` |
| `100` | ✅ Yes | It easily fits |
| `2^255 - 1` | ✅ Yes | It is the maximum positive `int256` value |
| `2^255` | ❌ No | Too large for positive `int256` |
| `2^256 - 1` | ❌ No | Way too large |

So the check creates a boundary:

```text
0 ─────────────── 2^255 - 1 │ 2^255 ─────────────── 2^256 - 1
        SAFE                  │             TOO LARGE
        for int256             │             for int256
```

---

# 5. Then the actual conversion happens

After the check:

```solidity
z = int256(y);
```

This converts:

```text
uint256
   ↓
int256
```

The order is important:

```text
1. Check that `y` fits.
2. Convert `y`.
```

The function does **not** blindly convert first.

It first makes sure the conversion is safe.

# 6. A tiny-number example

Imagine we had much smaller integer types.

Suppose:

```text
uint4 = 0 to 15

int4 = -8 to 7
```

The same principle applies.

The biggest positive `int4` is:

```text
7
```

which is:

```text
2^3 - 1
```

So the safe check would be:

```solidity
require(y < 2**3);
```

or:

```text
require(y < 8);
```

Example:

| `y` | Pass? | Why? |
|---:|:---:|---|
| `0` | ✅ | `0 < 8` |
| `5` | ✅ | Fits |
| `7` | ✅ | Maximum positive `int4` |
| `8` | ❌ | Too large |
| `15` | ❌ | Way too large |

The real `uint256 → int256` conversion follows exactly the same idea, just with 256-bit types.

# 7. Visual memory trick: the `2^255` door

Think of `2^255` as a door between two rooms.

```text
uint256 room:

[0 .............................................. 2^256 - 1]
                                                ↑
                                           too big!
                                                ↑


int256 room:

[-2^255 ........................ 0 ........................ 2^255 - 1]
     ↑                                                     ↑
 very negative                                       max positive
```

The function asks:

> **"Is this `uint256` number small enough to fit through the door into the positive side of the `int256` room?"**

If:

```text
0 → 2^255 - 1
```

then:

```text
✅ It fits.
```

If:

```text
2^255 → 2^256 - 1
```

then:

```text
❌ It does not fit.
```

---

# 8. Why can't the `uint256` use the negative portion of `int256`?

This is a very important point.

You might initially think:

> "If the positive side of `int256` is full, can't we put the number into the negative side?"

No.

Because the source is:

```solidity
uint256 y
```

A `uint256` can **never be negative**.

Its range is:

```text
0 → 2^256 - 1
```

So when converting a `uint256` into an `int256`, the value must fit into the **non-negative portion** of `int256`.

The negative portion:

```text
-2^255 → -1
```

cannot be used to represent a positive `uint256` value.

Therefore:

```text
uint256 value
      ↓
must fit into
      ↓
positive int256 range
      ↓
0 → 2^255 - 1
```

That is exactly why the check is:

```solidity
require(y < 2**255);
```

---

# 9. Your question: Are `uint256` max and `int256` max equal?

**No.**

Their **maximum positive values are different**.

```text
uint256 max = 2^256 - 1

int256 max = 2^255 - 1
```

So `uint256` can hold positive numbers that `int256` cannot.

For example:

```text
2^255 - 1
```

fits in both.

But:

```text
2^255
```

fits in `uint256` but does **not** fit in positive `int256`.

Therefore:

```text
uint256 has the larger maximum positive value.
```

---

# 10. But do they have the same total capacity?

**Yes.**

This is the important distinction between **maximum value** and **total number of possible values**.

### `uint256`

Range:

```text
0 → 2^256 - 1
```

Number of possible values:

```text
2^256
```

### `int256`

Range:

```text
-2^255 → 2^255 - 1
```

Number of possible values:

```text
2^256
```

So both types can represent exactly:

```text
2^256
```

different values.

They simply use those possible values differently.

---

# 11. How do they use the space differently?

### `uint256`

All its possible values are non-negative:

```text
[0 ........................................ 2^256 - 1]
```

It uses its entire 256-bit capacity for non-negative values.

### `int256`

Its values are split between negative and non-negative numbers:

```text
[-2^255 ........ -1] [0] [1 ........ 2^255 - 1]
```

So it uses part of its range for negative numbers.

This gives it a smaller maximum positive value.

---

# 12. Full comparison

| Property | `uint256` | `int256` |
|---|---:|---:|
| Minimum | `0` | `-2^255` |
| Maximum | `2^256 - 1` | `2^255 - 1` |
| Total possible values | `2^256` | `2^256` |
| Negative values | No | Yes |
| Positive maximum | Larger | Smaller |

So the correct statement is:

> **`uint256` and `int256` have the same total number of possible values, but `uint256` can represent much larger positive values because it does not need to represent negative values.**

This becomes easier with tiny types.

### `uint4`

```text
0 to 15
```

So:

```text
0, 1, 2, 3, ..., 15
```

There are:

```text
16 = 2^4
```

possible values.

### `int4`

```text
-8 to 7
```

So:

```text
-8, -7, ..., -1, 0, 1, ..., 7
```

There are also:

```text
16 = 2^4
```

possible values.

But look at the maximum:

```text
uint4 max = 15
int4 max  = 7
```

Exactly the same thing happens with 256-bit integers:

```text
uint256 max = 2^256 - 1

int256 max  = 2^255 - 1
```

---

# 14. Why does `int256` have this range?

At a high level, a signed integer needs to represent both positive and negative values.

So the available 256-bit value space is distributed across:

```text
negative values
+
zero
+
positive values
```

For `int256`, that produces:

```text
-2^255 → 2^255 - 1
```

while `uint256` can use the entire space for:

```text
0 → 2^256 - 1
```

The exact representation is based on the signed integer representation used by Solidity/EVM, but for understanding this function, the critical fact is simply the range above.

# 15. Why does `toInt256()` need this check?

Now the whole function makes sense:

```solidity
function toInt256(uint256 y) internal pure returns (int256 z) {
    require(y < 2**255);
    z = int256(y);
}
```

Read it like a child:

```text
"I have a positive number."
        ↓
"Can this number fit inside
 the positive side of int256?"
        ↓
       Check
        ↓
   ┌────┴────┐
   YES       NO
    ↓         ↓
 convert    revert
```

The check:

```solidity
require(y < 2**255);
```

means:

> **"Make sure this positive number is not bigger than the biggest positive number an `int256` can hold."**

Then:

```solidity
z = int256(y);
```

means:

> **"Now that I know it fits, convert it."**

---

# 16. Final mental model

Think of `uint256` and `int256` as two rooms with exactly the same number of spaces.

```text
uint256:

[ 0 ................................................ 2^256 - 1 ]
  ←──────────── all spaces are for non-negative values ───────→


int256:

[ -2^255 ................ 0 ................ 2^255 - 1 ]
  ← negative spaces →       ← positive spaces →
```

Both rooms have:

```text
2^256 total spaces
```

But the `int256` room uses some of those spaces for negative numbers.

A `uint256` value can only enter the **non-negative side** of the `int256` room.

Therefore, it must satisfy:

```text
y ≤ 2^255 - 1
```

which Uniswap writes as:

```solidity
y < 2**255
```

---

# One-line summary

```solidity
require(y < 2**255);
```

means:

> **"Before converting this `uint256` into `int256`, make sure it fits inside the positive range of `int256`; otherwise revert."**

And:

```solidity
z = int256(y);
```

means:

> **"Now safely perform the conversion."**
