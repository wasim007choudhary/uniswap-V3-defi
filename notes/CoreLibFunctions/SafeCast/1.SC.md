# Uniswap V3 — SafeCast.sol: Function-by-Function Dissection

## What is `SafeCast` made for?

`SafeCast` is a small library whose job is to make certain type conversions safe.

> A number can be stored in a bigger integer type and then converted into a smaller integer type. If the destination type cannot represent the original value, the conversion can change the value.

So SafeCast checks that the value still means exactly the same thing after the conversion.

The original Uniswap V3 library contains three functions:

```solidity
function toUint160(uint256 y) internal pure returns (uint160 z) {
    require((z = uint160(y)) == y);
}

function toInt128(int256 y) internal pure returns (int128 z) {
    require((z = int128(y)) == y);
}

function toInt256(uint256 y) internal pure returns (int256 z) {
    require(y < 2**255);
    z = int256(y);
}
```

For this note, we fully dissect the **first two functions**. The third function is intentionally omitted.

---

# 1. `toUint160()`

Original function:

```solidity
function toUint160(uint256 y) internal pure returns (uint160 z) {
    require((z = uint160(y)) == y);
}
```

## What is this function made for?

Its job is very simple:

> **Take a `uint256` number and safely turn it into a `uint160` number.**

So:

```text
uint256
   ↓
toUint160()
   ↓
uint160
```

Why do we need a special function?

Because `uint256` can hold much bigger numbers than `uint160`.

Think of it like two boxes:

```text
uint256 → BIGGER BOX
uint160 → SMALLER BOX
```

If the number is too big for the smaller box, we have a problem.

```text
        uint256
   ┌─────────────────┐
   │    BIGGER BOX   │
   └─────────────────┘
            ↓
       put it into
            ↓
      ┌────────────┐
      │   uint160  │
      │ SMALLER BOX│
      └────────────┘
```

The purpose of `SafeCast` is to make sure the number actually fits before accepting the conversion.

---

## What does `uint160` mean?

Both `uint256` and `uint160` are **unsigned integers**.

Unsigned means:

> They cannot represent negative numbers.

Their difference is their size:

```text
uint256 → 256 bits
uint160 → 160 bits
```

Therefore:

```text
uint256 → bigger range
uint160 → smaller range
```

The maximum values are:

```text
uint256 max = 2^256 - 1
uint160 max = 2^160 - 1
```

So:

> Every `uint160` value can fit inside a `uint256`, but not every `uint256` value can fit inside a `uint160`.

That is the important direction.

---

# 2. The dangerous part: `uint160(y)`

Look at:

```solidity
uint160(y)
```

This is a **type conversion**, also called a **cast**.

It says:

> "Take `y`, which is a `uint256`, and convert it to `uint160`."

If `y` fits:

```text
y = 500

uint256
   ↓
uint160(500)
   ↓
500
```

Everything is fine.

But if `y` is too large, the smaller `uint160` type cannot represent the whole value.

A narrowing conversion can therefore lose the high bits of the number.

Conceptually:

```text
uint256:
[ high bits ][          low 160 bits          ]
                 ↓
              uint160
                 ↓
          [ low 160 bits ]
```

So the converted number can become **different from the original number**.

---

# 3. This is why Uniswap checks it

Now look at the complete line:

```solidity
require((z = uint160(y)) == y);
```

Break it into two actions.

### First action

```solidity
z = uint160(y)
```

Convert `y` to `uint160` and store the result in `z`.

### Second action

```solidity
z == y
```

Ask:

> **"Did the converted number remain exactly the same?"**

Then:

```solidity
require(...)
```

says:

> **"This must be true. Otherwise revert."**

So the whole thing is:

```text
uint256 y
   ↓
convert to uint160
   ↓
compare converted value with original
   ↓
       same?
      /     \
    YES      NO
     ↓        ↓
 continue   revert
```

The key idea is:

> **If converting `uint256 → uint160` changes the value, reject the conversion.**

---

# 4. Easy example

Suppose:

```text
y = 100
```

Then:

```solidity
z = uint160(100);
```

gives:

```text
z = 100
```

Now:

```solidity
z == y
```

becomes:

```text
100 == 100
```

which is:

```text
true
```

Therefore:

```solidity
require(true);
```

passes.

The conversion is safe.

---

# 5. What happens when the number is too large?

Suppose:

```text
y > uint160 maximum
```

Then:

```solidity
uint160(y)
```

cannot represent the complete original value.

The resulting `z` is therefore different from `y`.

So:

```solidity
z == y
```

becomes:

```text
false
```

Then:

```solidity
require(false);
```

reverts.

So:

```text
number fits
   ↓
conversion accepted

number does not fit
   ↓
conversion rejected
```

---

# 6. Why compare instead of checking the maximum?

Uniswap could have written:

```solidity
require(y <= type(uint160).max);
z = uint160(y);
```

But the original implementation uses:

```solidity
require((z = uint160(y)) == y);
```

This compact expression does two things:

```text
1. Convert the value.
2. Check that the value did not change.
```

The important concept is not the clever syntax.

The important concept is:

> **Convert it, then verify that the converted value is exactly equal to the original.**

---

# 7. Why does `SqrtPriceMath` need this?

This is where `SafeCast` becomes useful in the V3 code we are studying.

For example, `SqrtPriceMath` contains a calculation like:

```solidity
return FullMath.mulDivRoundingUp(
    numerator1,
    sqrtPX96,
    denominator
).toUint160();
```

`FullMath.mulDivRoundingUp()` returns a:

```text
uint256
```

But the square-root price is represented using:

```text
uint160
```

So the result needs to go through:

```text
FullMath calculation
       ↓
     uint256
       ↓
   toUint160()
       ↓
     uint160
       ↓
sqrt price
```

`SafeCast` is therefore like a security guard at the smaller door:

> "Before we squeeze this `uint256` number into the smaller `uint160` box, make sure it actually fits."

---

# 8. The whole `toUint160()` function in one sentence

```solidity
function toUint160(uint256 y) internal pure returns (uint160 z) {
    require((z = uint160(y)) == y);
}
```

means:

> **"Convert this `uint256` into `uint160`, but revert if the conversion changes the number because it was too large to fit."**

# 9. `toInt128()`

Now the second function:

```solidity
function toInt128(int256 y) internal pure returns (int128 z) {
    require((z = int128(y)) == y);
}
```

Its job is:

> **Take an `int256` number and safely turn it into an `int128` number.**

So:

```text
int256
   ↓
toInt128()
   ↓
int128
```

---

# 10. What are `int256` and `int128`?

Unlike `uint`, an `int` can hold **positive and negative numbers**.

```text
int256 → 256 bits → BIGGER BOX
int128 → 128 bits → SMALLER BOX
```

Think of it as:

```text
        int256
   ┌───────────────┐
   │ positive      │
   │ and negative  │
   └───────────────┘
          ↓
       int128
   ┌─────────┐
   │ smaller │
   │  box    │
   └─────────┘
```

The problem is:

> **Not every `int256` number can fit inside an `int128`.**

---

# 11. Why can `int128` hold negative numbers?

Because `int` is **signed**.

For `int128`:

```text
minimum = -2^127
maximum =  2^127 - 1
```

For `int256`:

```text
minimum = -2^255
maximum =  2^255 - 1
```

So `int256` has a much larger range.

The destination `int128` can hold both positive and negative values, but its range is much smaller.

---

# 12. Look at the conversion

```solidity
int128(y)
```

This means:

> **"Convert the `int256` value `y` into an `int128`."**

If the number fits:

```text
y = 500

int256
   ↓
int128(500)
   ↓
500
```

No problem.

But if `y` is outside the `int128` range, the conversion can change the represented value.

---

# 13. This is why Uniswap checks it

The function does:

```solidity
require((z = int128(y)) == y);
```

Break it apart.

### First

```solidity
z = int128(y);
```

Convert `y` to `int128` and store it in `z`.

### Then

```solidity
z == y
```

Ask:

> **"Is the converted value exactly the same as the original value?"**

Finally:

```solidity
require(...)
```

says:

> **"If it isn't the same, revert."**

So:

```text
int256 y
   ↓
convert to int128
   ↓
compare with original
   ↓
       same?
      /     \
    YES      NO
     ↓        ↓
 continue   revert
```

---

# 14. Positive example

Suppose:

```text
y = 100
```

Then:

```solidity
z = int128(y);
```

gives:

```text
z = 100
```

Then:

```solidity
z == y
```

becomes:

```text
100 == 100
```

which is:

```text
true
```

Therefore:

```solidity
require(true);
```

passes.

The conversion is safe.

---

# 15. Negative example

Suppose:

```text
y = -100
```

That is perfectly valid for `int128`.

So:

```solidity
z = int128(y);
```

gives:

```text
z = -100
```

Then:

```text
z == y
-100 == -100
```

is:

```text
true
```

So the conversion is safe.

This is important because `int128` is **signed** and can represent negative numbers.

---

# 16. What if it is too positive?

Suppose:

```text
y > 2^127 - 1
```

That number cannot fit into `int128`.

After:

```solidity
z = int128(y);
```

the resulting `z` will not equal the original `y`.

Therefore:

```solidity
z == y
```

becomes:

```text
false
```

and:

```solidity
require(false);
```

reverts.

This protects against **positive overflow during the narrowing conversion**.

---

# 17. What if it is too negative?

Same idea.

If:

```text
y < -2^127
```

then it cannot fit into `int128`.

The conversion changes the represented value.

Therefore:

```solidity
z == y
```

is:

```text
false
```

and the function reverts.

This protects against **negative underflow during the narrowing conversion**.

So the single comparison catches both:

```text
positive overflow
        +
negative underflow
```

---

# 18. Why does the function return `z`?

Notice the function declaration:

```solidity
function toInt128(int256 y)
    internal
    pure
    returns (int128 z)
```

The return variable is already named:

```text
z
```

So this:

```solidity
z = int128(y);
```

does two things:

```text
1. Convert y → int128
2. Store the result in z
```

Because `z` is a **named return variable**, Solidity automatically returns it when the function finishes.

There is no explicit:

```solidity
return z;
```

needed.

---

# 19. `toUint160()` vs `toInt128()`

The same basic safety pattern is used by both:

```text
       SAFE CASTING
            ↓
    "Can the destination
     type hold this value?"
            ↓
       YES → convert
       NO  → revert
```

### `toUint160()`

```text
uint256 → uint160
```

Both are unsigned.

The problem is:

```text
uint256 can hold values
that uint160 cannot.
```

So it protects against a value being too large.

### `toInt128()`

```text
int256 → int128
```

Both are signed.

The destination has a smaller positive and negative range.

So it protects against:

```text
positive overflow
+
negative underflow
```

---

# 20. The key pattern to remember

Both functions use:

```solidity
require((z = CAST(y)) == y);
```

Read it as:

> **"Convert it. Then check that the converted result is exactly the same as the original. If not, revert."**

That is the core idea behind these two SafeCast functions.

---

# Important Solidity 0.8.20 point

You are rewriting these libraries in Solidity `0.8.20`.

Solidity 0.8.x automatically checks normal arithmetic overflow and underflow.

For example:

```solidity
uint256 x = type(uint256).max;
x += 1;
```

reverts.

But a narrowing type conversion such as:

```solidity
uint160 y = uint160(x);
```

is a **type conversion**, not ordinary arithmetic overflow.

So Solidity 0.8.20 does **not** automatically make this narrowing conversion safe.

That is why the SafeCast functionality is still useful in your `0.8.20` implementation.

The exact custom implementation can be decided later, after we have finished understanding the original Uniswap code.

# Summary

| Function | Conversion | Main problem it prevents |
|---|---|---|
| `toUint160()` | `uint256 → uint160` | Source value too large |
| `toInt128()` | `int256 → int128` | Positive overflow or negative underflow |

The mental model:

```text
Bigger integer
      ↓
   SafeCast
      ↓
"Can the smaller type
 represent this EXACT value?"
      ↓
   ┌───────┴───────┐
   YES             NO
    ↓               ↓
 convert          revert
```

> **SafeCast is the guard that prevents a type conversion from silently changing a number.**
