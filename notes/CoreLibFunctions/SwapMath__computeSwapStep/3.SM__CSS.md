# 🎯 First: Where Are We Right Now?

Before this line:

```solidity
bool max = sqrtRatioTargetX96 == sqrtRatioNextX96;
```

the function has already done a lot.

It has already determined:

```text
1. Swap direction
2. Exact Input or Exact Output
3. Amount needed/available for the full Current → Target movement
4. Whether the trader can reach the Target
5. If the trader cannot reach it, the actual Next price
```

This last point is **very important**.

We are **not** starting from zero here.

---

# 🧠 What Did the First Half Already Calculate?

For Exact Input:

```solidity
if (exactIn) {
    uint256 amountRemainingLessFee =
        FullMath.mulDiv(
            uint256(amountRemaining),
            1e6 - feePips,
            1e6
        );

    amountIn = zeroForOne
        ? SqrtPriceMath.getAmount0Delta(
            sqrtRatioTargetX96,
            sqrtRatioCurrentX96,
            liquidity,
            true
        )
        : SqrtPriceMath.getAmount1Delta(
            sqrtRatioCurrentX96,
            sqrtRatioTargetX96,
            liquidity,
            true
        );

    if (amountRemainingLessFee >= amountIn)
        sqrtRatioNextX96 = sqrtRatioTargetX96;
    else
        sqrtRatioNextX96 =
            SqrtPriceMath.getNextSqrtPriceFromInput(
                sqrtRatioCurrentX96,
                liquidity,
                amountRemainingLessFee,
                zeroForOne
            );
}
```

This first part already knows:

```text
How much input would be needed for Current → Target
```

and then asks:

```text
Do I have enough usable input?
```

If yes:

```text
Next = Target
```

If no:

```text
Next = actual price reachable with my available input
```

# ❓ Question: “We Already Calculated Everything. Why Again?”

This was the main confusion.

The question was essentially:

> **“We already know how much is needed to hit the target. And if we don't have enough, we already know how far our available amount can move the price. So why are `amountIn` and `amountOut` calculated again?”**

This is the right question.

The answer needs to be very precise.

---

# 🔥 The Important Distinction

The first half can indeed determine the **actual Next price**.

For example:

```text
Current
   ↓
   ↓
Next
   ↓
Target
```

If the trader does not have enough to reach Target, then:

```solidity
getNextSqrtPriceFromInput(...)
```

or:

```solidity
getNextSqrtPriceFromOutput(...)
```

already tells us where the price actually ends.

So yes:

> **The first half already knows the actual Next price.**

The second half is **not calculating the Next price again**.

That is NOT what the second half is doing.

---

# 🧠 What Does `getNextSqrtPriceFromInput()` Actually Return?

Look at:

```solidity
sqrtRatioNextX96 =
    SqrtPriceMath.getNextSqrtPriceFromInput(
        sqrtRatioCurrentX96,
        liquidity,
        amountRemainingLessFee,
        zeroForOne
    );
```

This function gives us:

```text
NEXT PRICE
```

It does not return:

```text
amountIn
amountOut
```

So after this calculation, we know:

```text
Current Price
      ↓
Available Input
      ↓
Next Price
```

But `computeSwapStep()` must finally return:

```text
Next Price
Amount In
Amount Out
Fee
```

The second half is where the known:

```text
Current → Next
```

price movement is converted into the corresponding token deltas.

# ⚠️ One Very Important Detail

For Exact Input + insufficient input, you might naturally think:

> “But we already passed `amountRemainingLessFee` into `getNextSqrtPriceFromInput()`. Why not simply say `amountIn = amountRemainingLessFee`?”

This is exactly the subtle point.

The first part uses:

```solidity
amountRemainingLessFee
```

to determine the **Next price**.

The second part calculates the token delta from:

```text
Current Price → Next Price
```

using the canonical `SqrtPriceMath.getAmountXDelta()` calculation.

So the two operations have different jobs:

```text
amountRemainingLessFee
        ↓
"Where does the price go?"

getAmountXDelta(Current, Next, Liquidity)
        ↓
"What token amount corresponds to that actual price movement?"
```

The function wants the final `amountIn` / `amountOut` values to correspond to the actual finalized price movement and Uniswap's token-delta rounding rules.

# 🎯 Now `max`

The code is:

```solidity
bool max = sqrtRatioTargetX96 == sqrtRatioNextX96;
```

This is very simple.

It asks:

> **“Did the actual Next price reach the Target price?”**

If:

```text
Next == Target
```

then:

```text
max = true
```

If:

```text
Next != Target
```

then:

```text
max = false
```

# ❗ What `max` Does NOT Mean

Do not think:

> “max means maximum swap in the entire pool.”

No.

It means:

> **This particular step reached its target.**

So:

```text
max = true
```

means:

```text
Current → Target
```

actually happened.

While:

```text
max = false
```

means:

```text
Current → Next
```

stopped before Target.

# 🟢 First Line Inside the Block

```solidity

        true
```


```text

```

# 🟢 Case 1 — `max = true`, `exactIn = true`

Then:

```text
max && exactIn
=
true && true
=
true
```

So Solidity chooses:

```solidity

```

which is effectively:

```solidity
amountIn = amountIn;
```

This looks silly, but it means:

> **Keep the `amountIn` we calculated earlier.**

Why is that safe?

Because earlier we calculated the amount needed for:

```text
Current → Target
```

and now:

```text
Next = Target
```

So:

```text
actual movement
=
Current → Target
```

Therefore the old `amountIn` is already the actual `amountIn`.

# 🧠 Why `getAmount1Delta()`?

# 🔢 Why `true` for Input and `false` for Output?

For:

```solidity
getAmount0Delta(..., true)
```

the final argument:

```text
true
```

means:

```text
roundUp = true
```

Input amounts are rounded up.

Why?

Because we do not want to underestimate how much input is required.

For:

```solidity
getAmount1Delta(..., false)
```

the final argument:

```text
false
```

means:

```text
roundUp = false
```

Output amounts are rounded down.

Why?

Because we do not want to give the trader more output than the calculation safely allows.

So the simple rule is:

```text
INPUT
    ↓
round UP

OUTPUT
    ↓
round DOWN
```

|---|---:|---:|---|---|

| 2 | false | true | Calculate | Calculate |
| 3 | true | false | Calculate | Keep old |
| 4 | false | false | Calculate | Calculate |

This is not random.

It follows one simple rule:

> **Keep the value that was already calculated correctly for the full Current → Target movement. Recalculate the values that need to match the actual Current → Next movement.**

# 🎯 The Entire Second Half

The complete block is:

```solidity
// get the input/output amounts
if (zeroForOne) {
    amountIn = max && exactIn
        ? amountIn
        : SqrtPriceMath.getAmount0Delta(
            sqrtRatioNextX96,
            sqrtRatioCurrentX96,
            liquidity,
            true
        );

    amountOut = max && !exactIn
        ? amountOut
        : SqrtPriceMath.getAmount1Delta(
            sqrtRatioNextX96,
            sqrtRatioCurrentX96,
            liquidity,
            false
        );
} else {
    amountIn = max && exactIn
        ? amountIn
        : SqrtPriceMath.getAmount1Delta(
            sqrtRatioCurrentX96,
            sqrtRatioNextX96,
            liquidity,
            true
        );

    amountOut = max && !exactIn
        ? amountOut
        : SqrtPriceMath.getAmount0Delta(
            sqrtRatioCurrentX96,
            sqrtRatioNextX96,
            liquidity,
            false
        );
}
```

The simple interpretation is:

> **Use the swap direction to know which token is input and which is output. If the first calculation already gave the correct specified-side amount because we reached the target, keep it. Otherwise calculate the amount for the actual Current → Next movement.**


and:

```solidity
uint256(-amountRemaining)
```

converts it into an unsigned integer.

Now the function can compare:

```text
calculated amountOut
```

against:

```text
requested remaining amountOut
```

---

# 🧒 Why Do We Need the Cap?

Imagine the trader says:

> “Give me 100 candies.”

The calculation says:

```text
103 candies
```

The function must not return:

```text
103
```

because the trader requested only:

```text
100
```

So:

```solidity
amountOut = uint256(-amountRemaining);
```

caps it to:

```text
100
```

The rule is:

> **Exact Output must not give more output than the trader still requested.**

---

# 💰 Final Fee Block

Now we reach the final code:

```solidity
if (exactIn && sqrtRatioNextX96 != sqrtRatioTargetX96) {
    feeAmount = uint256(amountRemaining) - amountIn;
} else {
    feeAmount =
        FullMath.mulDivRoundingUp(
            amountIn,
            feePips,
            1e6 - feePips
        );
}
```

This calculates:

```text
feeAmount
```

---

# 🔀 Two Different Fee Cases

The condition is:

```solidity
exactIn &&
sqrtRatioNextX96 != sqrtRatioTargetX96
```

Meaning:

```text
Exact Input
+
Target NOT reached
```

If that is true:

```solidity
feeAmount = uint256(amountRemaining) - amountIn;
```

Otherwise:

```solidity
feeAmount =
    FullMath.mulDivRoundingUp(
        amountIn,
        feePips,
        1e6 - feePips
    );
```

---

# 🟢 Case 1 — Exact Input + Target NOT Reached

Suppose:

```text
Trader has 100 input remaining.
```

The target is too far away.

The whole available input for this step is consumed.

After fee:

```text
99 → price movement
1  → fee
```

Therefore:

```text
fee = 100 - 99
    = 1
```

The code:

```solidity
feeAmount =
    uint256(amountRemaining) - amountIn;
```

does exactly that.

---

# ❓ Question: “Can't We Just Do Total - Amount After Fee Deduction?”

**Yes, in this specific partial Exact Input case.**

The relationship is:

```text
Total Input
=
Input Used
+
Fee
```

Therefore:

```text
Fee
=
Total Input - Input Used
```

This works because the entire remaining Exact Input amount is consumed by this step.

---

# 🔴 Why Can't We Always Do That?

Imagine:

```text
Trader has 100 input.
```

But this step only needs:

```text
50 input
```

to reach the target.

Then:

```text
50 → this step
50 → remains available
```

If we do:

```text
100 - 50
```

we get:

```text
50
```

But that 50 is not the fee.

It contains input that was simply **not used in this step**.

Therefore subtraction cannot always be used.

---

# 🧠 Case 2 — Target Reached

When:

```text
Next = Target
```

the trader may have more input available than this step needs.

Therefore:

```text
amountRemaining - amountIn
```

could include:

```text
unused input
```

So Uniswap instead calculates the fee directly from the actual `amountIn`:

```solidity
FullMath.mulDivRoundingUp(
    amountIn,
    feePips,
    1e6 - feePips
);
```

---

# ❓ Question: “But Every `amountIn` Is After the Fee Deduction, Right?”

For Exact Input, yes:

```text
amountIn
```

represents the input used for the price movement after the fee has been accounted for.

That does **not** mean the fee is being removed again later.

The final calculation:

```solidity
feeAmount = ...
```

is calculating the fee that corresponds to that `amountIn`.

It is not charging another fee.

---

# ❓ Question: “Are We Removing the Fee Again?”

No.

The sequence is:

```text
Trader's total input
        ↓
account for fee
        ↓
usable input
        ↓
price movement
        ↓
final amountIn
        ↓
calculate/report feeAmount
```

The fee is accounted for once.

The final formula is simply determining the exact fee amount associated with the final `amountIn`.

---

# 🧮 Why the Reverse Fee Formula?

Suppose:

```text
F = fee rate
A = total input including fee
a = amount used for price movement
```

Then:

```text
a = A × (1 - F)
```

We want the fee.

So:

```text
Fee = a × F / (1 - F)
```

Uniswap uses:

```text
1e6
```

as the fee-rate scale.

Therefore:

```solidity
feeAmount =
    amountIn × feePips
    -------------------
    1e6 - feePips
```

implemented as:

```solidity
FullMath.mulDivRoundingUp(
    amountIn,
    feePips,
    1e6 - feePips
);
```

---

# ❓ Question: “Why Is the First Fee Formula Different?”

Because the two situations give us different information.

### Partial Exact Input

We know:

```text
total input
```

and:

```text
actual input used
```

and all of the total input was consumed.

So:

```text
Fee = Total - Used
```

---

### Target Reached

We know:

```text
actual input used
```

but the trader may still have unused input remaining.

So:

```text
Total - Used
```

would not isolate the fee.

Therefore:

```text
Fee = Used × F / (1 - F)
```

---

# 🧠 The Two Fee Cases in One Picture

```text
EXACT INPUT + TARGET NOT REACHED

100 total
│
├── 99 used
└── 1 fee

Fee = 100 - 99
```

But:

```text
TARGET REACHED

100 total available
│
├── 50 used
└── 50 unused

Fee is NOT:
100 - 50

because that gives:
50 unused + fee
```

So instead:

```text
Fee = 50 × F / (1 - F)
```

---

# 🔢 Why `mulDivRoundingUp()`?

The final fee calculation uses:

```solidity
FullMath.mulDivRoundingUp(...)
```

rather than:

```solidity
FullMath.mulDiv(...)
```

because Solidity performs integer arithmetic.

If the mathematical result has a remainder, the fee calculation deliberately rounds upward.

Conceptually:

```text
calculated fee = 2.4
```

becomes:

```text
3
```

when rounding up.

The purpose is:

> **Do not undercharge the fee because of integer truncation.**

# 🎯 The Most Important Thing About the Two Halves

This is the point that caused the most confusion, so keep this exact mental model:

## First Half

```text
"What happens if we try to move from CURRENT to TARGET?"
```

It calculates the full-target amount.

Then it determines:

```text
Can we reach TARGET?
```

If not, it calculates:

```text
NEXT PRICE
```

based on the trader's actual available/requested amount.

---

## Second Half

It does **not** calculate `NEXT PRICE` again.

Instead:

```text
"We already know NEXT.
Now calculate the token amounts
for the movement that actually happened:
CURRENT → NEXT."
```

And if:

```text
NEXT = TARGET
```

then the full-target movement and actual movement are the same.

So the already-calculated specified-side amount can be reused.

---

# 🧒 The One-Sentence Version

> **The first half finds where the price ends; the second half calculates the token amounts for the price movement that actually happened.**

That is the cleanest way to understand why both sections exist.
