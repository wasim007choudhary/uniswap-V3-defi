## 1. The Two Boolean Variables

```solidity
bool zeroForOne = currentSqrtRatioPriceX96 >= targetSqrtRatioPriceX96;
bool exactIn = amountRemaining >= 0;
```

These answer two different questions:

| Boolean | Question | `true` | `false` |
|---|---|---|---|
| `zeroForOne` | Which direction is price moving? | token0 → token1, price decreases | token1 → token0, price increases |
| `exactIn` | What did the trader specify? | Exact In: fixed input | Exact Out: fixed output |

Mental model:

```text
zeroForOne → DIRECTION
exactIn    → SWAP TYPE
```

Example:

```text
zeroForOne = true
exactIn    = true
```

means token0 → token1, with the input amount specified.

```text
zeroForOne = true
exactIn    = false
```

means token0 → token1, with the output amount specified.

The two Booleans are independent.

---

## 2. `zeroForOne`

```solidity
bool zeroForOne = currentSqrtRatioPriceX96 >= targetSqrtRatioPriceX96;
```

This determines the direction by comparing current and target sqrt prices.

Assume:

```text
Pool A/B
B = token0
A = token1
```

The token identities are already fixed by the pool's token ordering. This line does not decide which token is token0 or token1.

### Current price > target price

Example:

```text
Current = 1500
Target  = 1000
```

Therefore:

```text
1500 >= 1000
     ↓
true
```

So:

```text
zeroForOne = true
    ↓
token0 → token1
    ↓
B → A
    ↓
price decreases
```

### Current price < target price

Example:

```text
Current = 1500
Target  = 2000
```

Therefore:

```text
1500 >= 2000
     ↓
false
```

So:

```text
zeroForOne = false
    ↓
token1 → token0
    ↓
A → B
    ↓
price increases
```

Important distinction:

> `zeroForOne` does not decide which token is token0 or token1. Those identities are already fixed. It determines the direction of the price movement, which under V3's fixed price convention corresponds to the swap direction.

Thus:

```text
true  → token0 → token1 → price ↓
false → token1 → token0 → price ↑
```

Edge case:

```text
current == target
```

makes `>=` evaluate to `true`. This is deterministic, although there is no meaningful price movement when the two prices are identical.

---

## 3. `exactIn`

```solidity
bool exactIn = amountRemaining >= 0;
```

This determines the swap type from the sign of `amountRemaining`.

```text
amountRemaining > 0
        ↓
exactIn = true
        ↓
Exact In
```

Exact In means:

> The trader fixes the amount of input they are giving.

Example:

```text
+100 B
```

means the trader is giving 100 units of the input token.

For Exact Out:

```text
amountRemaining < 0
        ↓
exactIn = false
        ↓
Exact Out
```

Example:

```text
-100 A
```

means the trader still wants 100 units of output.

The negative sign is only an encoding used by the function; it does not mean negative tokens exist.

### Zero edge case

Because the check is:

```solidity
amountRemaining >= 0
```

zero is classified as Exact In.

For example, after an Exact In swap has consumed the entire specified input:

```text
amountRemaining = 0
```

and:

```text
0 >= 0
```

is still true.

---

## 4. Entering the Exact In Branch

```solidity
if (exactIn) {
```

If `exactIn` is true, Solidity enters the Exact In calculations.

If it is false, this block is skipped and the later `else` handles Exact Out.

This line only chooses the calculation path; it performs no calculation itself.

## 5. Remaining Input After Fee Deduction

```solidity
uint256 amountRemainingAfterFeeDeduction =
    MyCustomFullMath.mulDiv(
        uint256(amountRemaining),
        1e6 - feePips,
        1e6
    );
```

This calculates the input amount remaining **after accounting for the swap fee**.

The distinction is:

```text
amountRemaining
    ↓
gross input available

amountRemainingAfterFeeDeduction
    ↓
input available for the actual swap
    after the fee is accounted for
```

### Why `1e6`?

```text
1e6 = 1,000,000
```

Uniswap represents the fee in millionths.

Examples:

```text
500 / 1,000,000   = 0.05%
3000 / 1,000,000  = 0.30%
10000 / 1,000,000 = 1%
```

Example:

```text
amountRemaining = 100 B
feePips = 3000
```

Then:

```text
fee = 0.30 B
usable input = 99.70 B
```

This line does not yet calculate the final `feeAmountTaken`. It calculates the usable input so it can be compared with the input required to reach the target.

`mulDiv(a, b, c)` safely computes:

```text
a × b / c
```

with full-precision multiplication and division.

## 6. Calculating `amountIn`

The next calculation asks:

> How much input token would be required to move the price all the way from the current price to the target price?

```solidity
if (zeroForOne) {
    // Swap token0 for token1.
    amountIn = SqrtPriceMath.getAmount0Delta(
        targetSqrtRatioPriceX96,
        currentSqrtRatioPriceX96,
        liquidity,
        true
    ); // Δx = L(1/√Plower - 1/√Pupper): token0 (x) is the input token
} else {
    // Swap token1 for token0.
    amountIn = SqrtPriceMath.getAmount1Delta(
        currentSqrtRatioPriceX96,
        targetSqrtRatioPriceX96,
        liquidity,
        true
    ); // Δy = L(√Pupper - √Plower): token1 (y) is the input token
}
```

At this point, `amountIn` means the amount that **would be required to reach the target**. It is not automatically the final amount the trader will actually spend.

## 7. Why `zeroForOne` Chooses Different Delta Functions

### `zeroForOne = true`

```text
token0 → token1
```

Therefore token0 is the input token, so Uniswap calculates Token0 Delta:

```solidity
getAmount0Delta(...)
```

For a downward movement:

```text
current = upper price
target  = lower price
```

so the arguments are:

```text
target  → lower price
current → upper price
```

The Token0 formula is:

\[
\Delta x = L\left(rac{1}{\sqrt{P_{lower}}}-rac{1}{\sqrt{P_{upper}}}
ight)
\]

The final `true` means round up because this is required input.

### `zeroForOne = false`

```text
token1 → token0
```

Therefore token1 is the input token, so Uniswap calculates Token1 Delta:

```solidity
getAmount1Delta(...)
```

For the corresponding price ordering:

```text
current = upper price
target  = lower price
```

so the arguments are:

```text
current → upper price
target  → lower price
```

The Token1 formula is:

\[
\Delta y = L(\sqrt{P_{upper}}-\sqrt{P_{lower}})
\]

The final `true` again means round up because this is required input.

## 8. Why the Delta Argument Order Is Different

A key question was:

> Why does one call use `target, current` while the other uses `current, target`? Couldn't both use `current, target`?

The answer is that the order is intentional and follows the mathematical orientation required by the two Delta calculations.

Token0:

\[
\Delta x =
L\left(rac{1}{\sqrt{P_{lower}}}
-
rac{1}{\sqrt{P_{upper}}}
ight)
\]

The lower price comes first.

For:

```text
current = 1500 → upper
target  = 1000 → lower
```

the call:

```solidity
getAmount0Delta(target, current, ...)
```

means:

```text
lower, upper
```

Token1:

\[
\Delta y =
L(\sqrt{P_{upper}}-\sqrt{P_{lower}})
\]

The upper price comes first.

Therefore:

```solidity
getAmount1Delta(current, target, ...)
```

means:

```text
upper, lower
```

So for this downward movement:

```text
Token0 Delta → lower, upper
Token1 Delta → upper, lower
```

This is not arbitrary.

### Would reversing the arguments affect the result?

Yes.

For:

```text
current = 1500
target  = 1000
```

Token1's intended calculation is:

```text
√1500 - √1000
```

If the arguments were reversed, the mathematical subtraction would become:

```text
√1000 - √1500
```

which reverses the result.

Therefore, you cannot simply keep `current, target` everywhere without also changing how the Delta functions interpret their arguments.

You could design a different API that always accepts `current, target`, but the internal implementation would then have to compensate for that ordering.

Do not memorize:

```text
getAmount0Delta = always target, current
getAmount1Delta = always current, target
```

The better rule is:

> Understand which price is lower and which is upper, and then follow the ordering required by the particular Delta formula.

The same mathematical principle applies in the Exact Out branch.

## 10. Exact In: Target Is Reachable


## 11. Exact In: Target Is Not Reachable

When:

```text
amountRemainingAfterFeeDeduction < amountIn
```

the `else` branch is entered.

The trader does not have enough usable input to reach the target.

So Uniswap calculates an intermediate price:

```solidity
nextSqrtRatioPriceX96 = SqrtPriceMath.getNextSqrtPriceFromInput(
    currentSqrtRatioPriceX96,
    amountRemainingAfterFeeDeduction,
    liquidity,
    zeroForOne
);
```

The question is:

> Given the current price, active liquidity, available usable input, and direction, what is the furthest price we can actually reach?

The inputs represent:

```text
currentSqrtRatioPriceX96
    ↓
current price

liquidity
    ↓
active liquidity

amountRemainingAfterFeeDeduction
    ↓
input available for the swap

zeroForOne
    ↓
swap direction
```

The result is:

```text
nextSqrtRatioPriceX96
```

the intermediate price actually reachable with the available input.

Example:

```text
Current = 1500
Target  = 1000

Required input = 80 B
Available      = 50 B
```

Since:

```text
50 < 80
```

the target cannot be reached.

Conceptually:

```text

 ↓
```

## 12. Entering the Exact Out Branch

If:

```solidity
exactIn == false
```


Exact Out means:

> The trader specifies the amount of output they want to receive.

In this branch, the function first calculates how much output the entire current-to-target price movement could provide.

## 14. Exact Out With `zeroForOne = true`

When:

```text
zeroForOne = true
```

the swap is:

```text
token0 → token1
```

Therefore:

```text
token0 = input
token1 = output
```

So the output calculation uses:

```solidity
getAmount1Delta(...)
```

because token1 is the output.

The formula is:

\[
\Delta y = L(\sqrt{P_{upper}}-\sqrt{P_{lower}})
\]

For the downward movement:

```text
current = upper price
target  = lower price
```

The call is therefore arranged as:

```text
target  → lower price
current → upper price
```

The important distinction is:

> `y` represents token1, but in Exact Out with `zeroForOne = true`, token1 is the **output**, not the input.

The final `false` means the Delta calculation rounds down because this is output.

## 16. Exact Out: Check Whether the Target Can Be Reached

```solidity
if (uint256(-amountRemaining) >= amountOut)
```

Because `amountRemaining` is negative in Exact Out, the negative sign is removed first.

Example:

```text
amountRemaining = -100
```

then:

```text
uint256(-amountRemaining)
= 100
```

So the comparison asks:

> Is the amount of output the trader still wants greater than or equal to the output that would be produced by reaching the target?

### Example 1

```text
Trader still wants = 100 A
Full target movement gives = 80 A

100 >= 80
     ↓
true
```

Reaching the target provides only 80 A, while the trader still wants 100 A. The target can be reached, and the outer swap process can continue for the remaining requested output.

### Example 2

```text
Trader still wants = 50 A
Full target movement gives = 80 A

50 >= 80
     ↓
false
```

The full movement would give more output than requested, so the swap must stop before the target.

## 18. Exact Out: Target Would Produce Too Much Output

The `else` branch is entered when:


Meaning:

> The trader wants less output than the full price movement would provide.


The swap cannot take the full 80 A because the trader only requested 50 A.

Therefore, the swap must stop at an intermediate price before reaching the target.

## 20. Exact In vs Exact Out — Main Difference So Far

### Exact In

The trader specifies:

```text
INPUT
```

So the function asks:

```text
How much input is available after the fee?
        ↓
Is it enough to reach the target?
        ↓
YES → next price = target
NO  → calculate next price from available input
```

### Exact Out

The trader specifies:

```text
OUTPUT
```

So the function asks:

```text
How much output would the full movement provide?
        ↓
Would that exceed the requested output?
        ↓
NO  → next price = target
YES → calculate next price from requested output
```

## 21. Rounding Direction Seen So Far

For required/input-side calculations:

```solidity
true
```

is used, meaning:

```text
round up
```

because underestimating required input could make the amount insufficient.

For output-side calculations:

```solidity
false
```

is used, meaning:

```text
round down
```

because the output calculation should not overstate the amount that can actually be received.

The detailed Delta implementation and rounding behavior will be studied separately.

# 22. Clean Code for the Section Covered

```solidity
function computeSwapStep(
    uint160 currentSqrtRatioPriceX96,
    uint160 targetSqrtRatioPriceX96,
    uint128 liquidity,
    int256 amountRemaining,
    uint24 feePips
)
    internal
    pure
    returns (
        uint160 nextSqrtRatioPriceX96,
        uint256 amountIn,
        uint256 amountOut,
        uint256 feeAmountTaken
    )
{
    bool zeroForOne = currentSqrtRatioPriceX96 >= targetSqrtRatioPriceX96;
    bool exactIn = amountRemaining >= 0;

    if (exactIn) {
        uint256 amountRemainingAfterFeeDeduction =
            MyCustomFullMath.mulDiv(
                uint256(amountRemaining),
                1e6 - feePips,
                1e6
            );

        if (zeroForOne) {
            // Swap token0 for token1.
            amountIn = SqrtPriceMath.getAmount0Delta(
                targetSqrtRatioPriceX96,
                /** lower price */
                currentSqrtRatioPriceX96,
                /** upper price */
                liquidity,
                true
            ); // Δx = L(1/√Plower - 1/√Pupper): token0 (x) is the input token
        } else {
            // Swap token1 for token0.
            amountIn = SqrtPriceMath.getAmount1Delta(
                currentSqrtRatioPriceX96,
                /** upper price */
                targetSqrtRatioPriceX96,
                /** lower price */
                liquidity,
                true
            ); // Δy = L(√Pupper - √Plower): token1 (y) is the input token
        }

        if (amountRemainingAfterFeeDeduction >= amountIn) {
            nextSqrtRatioPriceX96 = targetSqrtRatioPriceX96;
        } else {
            nextSqrtRatioPriceX96 = SqrtPriceMath.getNextSqrtPriceFromInput(
                currentSqrtRatioPriceX96,
                amountRemainingAfterFeeDeduction,
                liquidity,
                zeroForOne
            );
        }
    } else {
        // Exact Out: the output amount is specified, so we calculate
        // how much output can be obtained before reaching the target price.

        if (zeroForOne) {
            // Swap token0 for token1.
            amountOut = SqrtPriceMath.getAmount1Delta(
                targetSqrtRatioPriceX96,
                /** lower price */
                currentSqrtRatioPriceX96,
                /** upper price */
                liquidity,
                false
            ); // Δy = L(√Pupper - √Plower): token1 (y) is the output token
        } else {
            // Swap token1 for token0.
            amountOut = SqrtPriceMath.getAmount0Delta(
                targetSqrtRatioPriceX96,
                /** lower price */
                currentSqrtRatioPriceX96,
                /** upper price */
                liquidity,
                false
            ); // Δx = L(1/√Plower - 1/√Pupper): token0 (x) is the output token
        }

        if (uint256(-amountRemaining) >= amountOut) {
            nextSqrtRatioPriceX96 = targetSqrtRatioPriceX96;
        } else {
            nextSqrtRatioPriceX96 = SqrtPriceMath.getNextSqrtPriceFromOutput(
                currentSqrtRatioPriceX96,
                uint256(-amountRemaining),
                liquidity,
                zeroForOne
            );
        }
    }
}
```
