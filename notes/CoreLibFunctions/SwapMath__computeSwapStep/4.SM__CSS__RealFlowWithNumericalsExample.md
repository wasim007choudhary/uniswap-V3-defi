# `computeSwapStep()` — Real Numerical Examples

> **Prerequisite:** Read:
>
> Read All the **1.SM__CSS.md** `to` **3.SM__CSS.md** before coming to this part.
>
> This note is the **numerical companion**.
>
> Here we will actually run `computeSwapStep()` with numbers.
>
> We will hit all four important cases:
>
> 1. Exact Input + Target Reached
> 2. Exact Input + Target NOT Reached
> 3. Exact Output + Target Reached
> 4. Exact Output + Target NOT Reached
>
> And we will do them in **both directions**:
>
> ```text
> zeroForOne = true
>     token0 → token1
>     price goes DOWN
>
> zeroForOne = false
>     token1 → token0
>     price goes UP
> ```
>
> The goal is not just to see the final answer.
>
> We will put the **Solidity line beside the actual calculation**, so we can see exactly what the code is doing.
>
> ---
>
> ## Important simplification for this note
>
> Real Uniswap uses:
>
> ```text
> sqrtPriceX96 = √P × 2^96
> ```
>
> The actual Solidity values are therefore very large encoded integers.
>
> To make the arithmetic understandable by a human, this note uses **simplified square-root price units** such as:
>
> ```text
> current √P = 4
> target  √P = 2
> ```
>
> We are still using the **same SqrtPriceMath relationships and the same branch logic**. We are only removing the huge `2^96` encoding from the hand calculations.
>
> A later implementation-level exercise can use actual Q64.96 integers if needed.

# 🧮 Our Common Numbers

To make the examples comparable, we will use:

```text
Liquidity L = 10,000
Fee = 0.30%
feePips = 3,000
Fee scale = 1,000,000
```

Therefore:

```text
1e6 - feePips
=
1,000,000 - 3,000
=
997,000
```

and:

```text
997,000 / 1,000,000
=
0.997
```

So for Exact Input:

```text
usable input
=
remaining input × 0.997
```

---

# 🧠 The Simplified Delta Formulas We Will Use

For these examples, let:

```text
√Current = C
√Target  = T
√Next    = N
L        = liquidity
```

## Token0 delta

```text
amount0
=
L × (1/√Lower - 1/√Upper)
```

The library internally orders the two square-root prices, so the caller does not have to manually put the lower value first.

---

## Token1 delta

```text
amount1
=
L × (√Upper - √Lower)
```

Again, the library internally normalizes the two prices.

# Step 10 — Calculate Fee

### Solidity

```solidity
if (exactIn && sqrtRatioNextX96 != sqrtRatioTargetX96) {
    feeAmount = uint256(amountRemaining) - amountIn;
} else {
    feeAmount =
        FullMath.mulDivRoundingUp(
            amountIn,
            feePips,
            1e6 - feePips
        );
}
```

Check the first condition:

```text
exactIn = true
```

but:

```text
Next = Target
```

so:

```text
sqrtRatioNextX96 != sqrtRatioTargetX96
=
false
```

Therefore the first branch is NOT used.

We use:

```solidity
FullMath.mulDivRoundingUp(
    amountIn,
    feePips,
    1e6 - feePips
);
```

### Numbers

```text
amountIn = 2,500

feePips = 3,000

denominator = 997,000
```

So:

```text
fee
=
2,500 × 3,000 / 997,000

≈ 7.522...
```

Rounded UP:

```text

```

# Step 6 — Find the Actual `Next` Price

### Solidity

```solidity

        sqrtRatioCurrentX96,
        liquidity,
        amountRemainingLessFee,
        zeroForOne

```

```text

=
L × √Current
----------------
L + amount0 × √Current
```

Numbers:

```text

√Current = 4
amount0 = 997
```

Therefore:

```text

=

--------------------

=
40,000
----------------

≈ 2.8596
```

So:

```text
Next ≈ 2.8596
```

Notice:

```text

Next    ≈ 2.8596
Target  = 2
```

Therefore:

```text
4 → 2.8596
```

and we stopped before:

```text
2
```


The second half does NOT calculate `Next` again.

It uses:

```text
Current = 4
Next ≈ 2.8596
```

to calculate the actual token amounts for that movement.

# 🧠 Why Does This Pattern Make Sense?

The first half calculates the side that matches the trader's instruction.

```text
Exact Input
    ↓
first calculate amountIn
```

```text
Exact Output
    ↓
first calculate amountOut
```

Then:

```text
Did we reach Target?
```

If yes:

```text
Current → Next
=
Current → Target
```

So the first calculation is already the actual answer for that side.

If no:

```text
Current → Next
≠
Current → Target
```

So the old full-target amount cannot be used as the final amount for that movement.

# 🧒 The Simplest Analogy

Imagine a child has to walk from:

```text
A → B
```

## First question

> “How much walking would be needed to reach B?”

Then:

> “Does the child have enough energy?”

### Enough energy

The child reaches B:

```text
A ─────────→ B
```

The original calculation is correct.

### Not enough energy

The child stops at C:

```text
A ─────→ C ─────→ B
```

The first calculation was about:

```text
A → B
```

but the child actually did:

```text
A → C
```

So now we measure:

```text
A → C
```

That is exactly what the second half is doing.

# 🚨 The Most Important Clarification

Do **not** think:

```text
First half:
"Find Target"

Second half:
"Find Next"
```

That is wrong.

The first half already finds `Next` when the target cannot be reached.

The correct model is:

```text
FIRST HALF
────────────────────────

1. Calculate full Current → Target amount.

2. Ask whether trader can reach Target.

3. If YES:
       Next = Target

4. If NO:
       calculate actual Next price
       using trader's amount/request.
```

Then:

```text
SECOND HALF
────────────────────────

5. We already know Next.

6. Calculate the token amounts
   corresponding to Current → Next.

7. Reuse the old specified-side amount
   only when Next == Target and
   that old amount is already the actual amount.
```

# 🔥 Why `getNextSqrtPriceFromInput()` Is Different From `getAmount0Delta()`

This distinction is extremely important.

## `getNextSqrtPriceFromInput()`

Answers:

> **“Given this amount of input, where does the price end?”**

Output:

```text
Next Price
```

---

## `getAmount0Delta()` / `getAmount1Delta()`

Answers:

> **“Given these two prices and this liquidity, how many tokens correspond to this price movement?”**

Output:

```text
Token Amount
```

Therefore:

```text
getNextSqrtPriceFromInput()
        ↓
finds PRICE
```

while:

```text
getAmountXDelta()
        ↓
finds TOKEN AMOUNT
```

This is why both kinds of calculations appear in the function.

# 💰 The Fee Logic Seen Numerically

There are two important situations.

## Target NOT Reached + Exact Input

Example:

```text
Total input = 1,000
Amount used = 997
```

Therefore:

```text
Fee = 1,000 - 997
    = 3
```

This works because the entire remaining input was consumed.

---

## Target Reached

Example:

```text
Total input available = 21,000
Amount needed = 20,000
```

We cannot do:

```text
21,000 - 20,000
=
1,000
```

and call that the fee.

Why?

Because the trader did not use all 21,000 in this step.

There is unused input.

Instead:

```text
Fee
=
20,000 × 3,000 / 997,000
```

which is approximately:

```text
60.18
```

and rounds up to:

```text
61
```

# 🔥 One More Critical Point: Target Reached ≠ Whole Swap Finished

This is easy to misunderstand.

Suppose:

```text
Trader wants 25,000 output.

Current → Target
can only produce 20,000.
```

Then:

```text
Target is reached.
```

But:

```text
25,000 - 20,000
=
5,000
```

output is still requested.

So:

```text
current step finished
```

does **not** necessarily mean:

```text
entire swap finished
```

The outer:

```solidity
UniswapV3Pool.swap()
```

can:

```text
1. cross the target tick
2. update active liquidity
3. find the next target
4. call computeSwapStep() again
```

This is how a large V3 swap travels through multiple liquidity regions.

# 🧱 One Step vs Entire Swap

```text
  │
  ▼
```

So if Target is reached:

```text

```

not necessarily:


The biggest confusion in this function was:

```text
    getNextSqrtPriceFromInput()
    and
    getNextSqrtPriceFromOutput()
```

```text

is smaller than

    ↓
the old full-target amount is not the actual final amount

calculate the actual token delta
```
