# 1️⃣ First Line — `absTick`

```solidity
uint256 absTick =
    tick < 0
        ? uint256(-int256(tick))
        : uint256(int256(tick));
```

### 🎯 What is this line doing?

Very simply:

> **It takes the tick and removes its negative sign, giving us the absolute value of the tick.**

Mathematically:

\[
\boxed{absTick = |tick|}
\]

Examples:

```text
tick =  5  → absTick = 5
tick = -5  → absTick = 5
tick =  2  → absTick = 2
tick = -2  → absTick = 2
tick =  0  → absTick = 0
```

---

Whether the child is:

```text

```

The original `tick` is still kept because its sign matters later.


means:

```text

    absTick = -tick

ELSE:
    absTick = tick
```

So conceptually:

```solidity
uint256 absTick = |tick|;
```

The price itself is **never negative** in this context.

\[

Since `1.0001` is positive, raising it to **any integer tick**, including a negative tick, still produces a **positive price**.

```text

tick = 0  →  P = 1
tick > 0  →  P > 1
```

> **The negative sign belongs to the tick, not to the price.**

Even though the tick is negative, the price remains positive.

### 📚 Quick Context Before the Deep-Level Report

**# Why Did Uniswap Choose `uint256` for `absTick`?**

> **Even though the value of `absTick` only needs 24 bits, `TickMath` performs the rest of its computation in the EVM's 256-bit execution environment.**

`absTick` is a **local variable**, not a storage variable, so there is no storage-packing benefit from making it `uint24`.

More importantly, `absTick` is used repeatedly throughout the function:

```solidity
absTick & 0x1
absTick & 0x2
absTick & 0x4
absTick & 0x8
...
```

The EVM works with 256-bit stack words. A `uint24` does not give the EVM a smaller 24-bit register. Solidity still has to preserve the narrower type's semantics, and that can affect the generated code.

And we **tested exactly this idea**:

```text
Original uint256:    7584 gas
Persistent uint24:   7677 gas
Hybrid uint24→256:   7591 gas
```

So the persistent `uint24` version was actually **93 gas more expensive** in the complete function.

The hybrid experiment is especially revealing:

```solidity
uint24 absTick24 = ...;
uint256 absTick = uint256(absTick24);
```

This brought the result to only **7 gas above the original**.

That strongly suggests the problem is not that `uint24` cannot represent the value.

The problem is **keeping `absTick` as `uint24` throughout the larger computation**.

**## 🧒 The Simplest Possible Explanation**

> **The tick is not big enough to need `uint256`. But the calculation around it works naturally with 256-bit EVM values, and our benchmark shows that keeping `absTick` as `uint256` is cheaper for the complete function.**

Think of it like this:

```text
The number is small

        ↓

but the machine works with 256-bit words

        ↓

so "smaller number" does not automatically mean

"cheaper computation"
```

And one crucial distinction:

```text
Local variable
    ↓
think about computation

State variable
    ↓
also think about storage packing
```

For `TickMath`, `absTick` is local, so the storage-size argument does not apply.

**## 🧠 The Real Lesson**

> **Do not optimize a Solidity variable only because its numerical range is small. First ask what the compiler and the EVM have to do with that value throughout the entire computation.**

Our experiment showed:

```text
uint24 locally
    ↓
cheaper in isolation ✅

uint24 throughout TickMath
    ↓
more expensive ❌

uint24 → uint256 once
    ↓
almost identical to original
```

So the important lesson is:

> **Smaller Solidity type ≠ automatically cheaper EVM execution.**

# 📚 What Does the Logarithm Mean Here?

A logarithm asks:

\[
\log_b(x)=y
\]

which means:

> **"What power do I need to raise \(b\) to in order to get \(x\)?"**

For example:

\[
2^3=8
\]

therefore:

\[
\log_2(8)=3
\]

So here we have:

\[
1.0001^{tick}=2^{128}
\]

We are basically asking:

> **"What power of `1.0001` do I need to reach \(2^{128}\)?"**

Taking logarithms gives:

\[
tick\log(1.0001)=\log(2^{128})
\]

Then divide by \(\log(1.0001)\):

\[
\boxed{
tick=
\frac{\log(2^{128})}
{\log(1.0001)}
}
\]

Using the logarithm power rule:

\[
\log(a^b)=b\log(a)
\]

we get:

\[
\log(2^{128})
=

\]

Therefore:

\[
\boxed{

\frac{128\log(2)}
{\log(1.0001)}
}
\]

And this evaluates to approximately:

\[

\]

This decimal is extremely important.

At this stage, `ratio` is being used as a **Q128.128 fixed-point number**.

Conceptually:

```text

│       128 integer bits       │       128 fraction bits      │
└──────────────────────────────┴──────────────────────────────┘
```

The scaling factor is:

\[

\]

Therefore a real mathematical value \(x\) is encoded approximately as:

\[

\]

This is why the code contains numbers around \(2^{128}\).

# 5️⃣ Why Q128.128?

The precomputed lookup constants need very high precision because TickMath repeatedly multiplies these factors.

The intermediate constants are therefore represented at the Q128.128 scale.

The neutral value `1` is represented as:

\[
1\times2^{128}=2^{128}
\]

which is written in hexadecimal as:

```solidity
0x100000000000000000000000000000000
```

$$
\boxed{\text{encoded value} = \text{real value}\times2^{128}}
$$

\boxed{\frac{A\times B\times2^{256}}{2^{128}}
