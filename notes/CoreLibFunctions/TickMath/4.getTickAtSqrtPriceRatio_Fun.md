# `getTickAtSqrtRatio()` — Starting Point

We will dissect `getTickAtSqrtRatio()` **line-by-line / tightly related topic-by-topic**, exactly like we did for `getSqrtPriceAtTick()`.

## The Function Is

```solidity
function getTickAtSqrtRatio(uint160 sqrtPriceX96) internal pure returns (int24 tick) {
```

### 🎯 First question: What is this function doing?

The previous function went:

```text
tick
  ↓
getSqrtPriceRatioAtTick()
  ↓
sqrtPriceX96
```

This function goes **backwards**:

```text
sqrtPriceX96
  ↓
getTickAtSqrtRatio()
  ↓
tick
```

So this function is basically the **reverse machine**.

We already know:

\[
\boxed{sqrtPriceX96=\sqrt{1.0001^{tick}}\times2^{96}}
\]

Now we are given `sqrtPriceX96`, and we want to recover the tick.

But there is an important detail in the NatSpec:

> **greatest tick such that `getSqrtPriceAtTick(tick) <= sqrtPriceX96`**

That means we are not simply asking:

> “What tick produces exactly this price?”

Instead, we are asking:

> **“What is the highest tick whose sqrt-price is still less than or equal to the given sqrt-price?”**

Example:

```text
tick 10 → sqrtPrice = 100
tick 11 → sqrtPrice = 105
tick 12 → sqrtPrice = 110
```

Given:

```text
sqrtPriceX96 corresponding to 107
```

Then:

```text
tick 10 → 100 ≤ 107 ✅
tick 11 → 105 ≤ 107 ✅
tick 12 → 110 ≤ 107 ❌
```

So the answer is:

```text
tick = 11
```

because `11` is the **highest tick whose sqrt-price does not exceed 107**.

---

## 🔹 Function parameter

```solidity
uint160 sqrtPriceX96
```

This is the Q64.96 sqrt-price we already learned from the previous function.

Meaning:

\[
\boxed{sqrtPriceX96=\sqrt P\times2^{96}}
\]

And unlike `tick`, which can be negative, `sqrtPriceX96` is positive, so it uses:

```solidity
uint160
```

---

## 🔹 Return value

```solidity
returns (int24 tick)
```

The answer is a signed tick because valid ticks can be:

```text
negative
   ↓
  0
   ↓
positive
```

So:

```text
sqrtPriceX96
      ↓
     tick
```

---

# 🚀 First actual line

Now we reach:

```solidity
require(
    sqrtPriceX96 >= MIN_SQRT_RATIO &&
    sqrtPriceX96 < MAX_SQRT_RATIO,
    'R'
);
```

This is simply the **input-range check**.

We already know:

```text
MIN_SQRT_RATIO
      ↓
lowest sqrtPriceX96 supported

MAX_SQRT_RATIO
      ↓
highest boundary sqrtPriceX96
```

So the condition is asking:

```text
Is the given sqrtPriceX96:

    >= minimum

AND

    < maximum ?
```

### Example

```text
sqrtPriceX96 = MIN_SQRT_RATIO
```

passes because:

```text
MIN >= MIN ✅
```

But:

```text
sqrtPriceX96 = MAX_SQRT_RATIO
```

does **not** pass because the second condition is:

```text
sqrtPriceX96 < MAX_SQRT_RATIO
```

not:

```text
sqrtPriceX96 <= MAX_SQRT_RATIO
```

So the valid input range is:

```text
MIN_SQRT_RATIO <= sqrtPriceX96 < MAX_SQRT_RATIO
```

Think of it as:

```text
✅────────────────────────────❌
MIN                         MAX
 ↑                            ↑
included                    excluded
```

And this is directly connected to what we just discussed:

> `getTickAtSqrtRatio()` needs a sqrt-price that lies inside the range from which it can recover a valid tick.

The interesting part is **why the minimum uses `>=` but the maximum uses `<`**.

---

# ❓ Why is `MAX_SQRT_RATIO` not accepted?

This is exactly the confusing part.

`MAX_SQRT_RATIO` represents the sqrt-price **at the maximum tick**, but this function deliberately does **not accept that exact endpoint as an input**.

We have:

```solidity
sqrtPriceX96 >= MIN_SQRT_RATIO &&
sqrtPriceX96 < MAX_SQRT_RATIO
```

So:

```text
MIN_SQRT_RATIO → ✅ allowed
MAX_SQRT_RATIO → ❌ not allowed
```

### Why?

Remember what this function is doing:

```text
sqrtPriceX96
      ↓
find the tick
```

And the result is supposed to be the **greatest tick whose sqrt-price is ≤ the input**.

At the very top boundary:

```text
MAX_SQRT_RATIO
      ↓
sqrt-price at MAX_VALID_TICK
      ↓
887272
```

But the implementation defines the inverse function's usable input range as **strictly below** that maximum.

So the condition is intentionally:

\[
\boxed{MIN\_SQRT\_RATIO \le sqrtPriceX96 < MAX\_SQRT\_RATIO}
\]

### 🧒 Think of a ruler

Suppose the valid ticks are:

```text
...
887270
887271
887272 ← maximum tick
```

and `MAX_SQRT_RATIO` is the sqrt-price corresponding to that upper endpoint.

The inverse function says:

> "Give me a sqrt-price **before I reach that endpoint**."

So:

```text
MIN ───────────────────────────── MAX
 ✅       valid input range       ❌
```

### And this is different from the forward function

`getSqrtPriceAtTick()` can do:

```text
tick = MAX_VALID_TICK
       ↓
return MAX_SQRT_RATIO
```

But `getTickAtSqrtRatio()` has the stricter input condition:

```text
sqrtPriceX96 < MAX_SQRT_RATIO
```

So yes:

> **`MAX_SQRT_RATIO` really is the sqrt-price associated with the maximum tick.**

The weird-looking part is simply that **this inverse function excludes that exact upper endpoint from its input range**.

---

# ❓ So `tick <= sqrtPrice` doesn't work for this max?

**For this inverse function, `<= MAX_SQRT_RATIO` does not work.**

The important distinction is:

```text
getSqrtPriceAtTick()
```

can take:

```text
tick = MAX_VALID_TICK
```

and produce:

```text
MAX_SQRT_RATIO ✅
```

But:

```text
getTickAtSqrtRatio()
```

does **not** accept `MAX_SQRT_RATIO` as an input.

So the ranges are intentionally asymmetric:

```text
FORWARD:

MAX_VALID_TICK
      ↓
getSqrtPriceAtTick()
      ↓
MAX_SQRT_RATIO ✅
```

but:

```text
BACKWARD:

MAX_SQRT_RATIO
      ↓
❌ rejected
```

Therefore this:

```solidity
sqrtPriceX96 < MAX_SQRT_RATIO
```

is required here.

And importantly, **it's not because `MAX_SQRT_RATIO` is wrong**.

It is the correct maximum sqrt-price associated with the maximum tick. The inverse function simply defines its valid input domain as **strictly below that endpoint**.

---

# ❓ What about the rule “tick ≤ sqrtPrice”? Isn't that violating its own principle?

Yes — the important distinction is that these are **two different rules**.

The wording:

> “the greatest tick whose sqrt-price is ≤ the input”

is correct **for inputs that the function accepts**.

The actual function first restricts its input to:

\[
\boxed{MIN\_SQRT\_RATIO \le sqrtPriceX96 < MAX\_SQRT\_RATIO}
\]

Only after passing that boundary check does it search for the tick satisfying:

\[
\boxed{getSqrtPriceAtTick(tick)\le sqrtPriceX96}
\]

So the complete rule is:

### 1. First: input boundary

```text
MIN_SQRT_RATIO <= sqrtPriceX96 < MAX_SQRT_RATIO
```

This defines the **only sqrt-price inputs the function accepts**.

### 2. Then: tick selection

For an accepted `sqrtPriceX96`, it finds the **greatest tick** satisfying:

\[
\boxed{getSqrtPriceAtTick(tick)\le sqrtPriceX96}
\]

So:

```text
                 INPUT BOUNDARY
┌──────────────────────────────────────────────┐
│                                              │
MIN_SQRT_RATIO <= sqrtPriceX96 < MAX_SQRT_RATIO
│                                              │
└──────────────────────┬───────────────────────┘
                       ↓
             find greatest tick where
                       ↓
      getSqrtPriceAtTick(tick) <= sqrtPriceX96
```

---

# 🧠 The clean mental model

It is basically **rounding down to the nearest tick**.

Example:

```text
tick 10 → 100
tick 11 → 105
tick 12 → 110

given price = 107
```

Then:

```text
107 → between tick 11 and tick 12

floor → tick 11
```

So mentally:

\[
\boxed{getTickAtSqrtRatio \approx \text{floor to the valid tick}}
\]

But one precision point:

> It is not literally doing a generic `floor()` on the numerical price.

It is finding the **greatest discrete tick whose generated sqrt-price is ≤ the input**.

---

# 🎯 Core distinction

So the complete picture is:

```text
getSqrtPriceAtTick()
────────────────────

tick
 ↓
exact corresponding sqrt-price
```

versus:

```text
getTickAtSqrtRatio()
────────────────────

sqrtPriceX96
 ↓
find where it sits between discrete ticks
 ↓
choose the greatest tick that is still ≤ that price
```

For example:

```text
tick 10 → 100
tick 11 → 105
tick 12 → 110

given sqrtPrice = 107
```

There is no exact tick at `107`.

Therefore:

```text
tick 11 → 105 ≤ 107 ✅
tick 12 → 110 > 107 ❌

answer = 11
```

# `getTickAtSqrtRatio()` — `ratio` Scaling Dissection

## Next line

```solidity
uint256 ratio = uint256(sqrtPriceX96) << 32;
```

We do **only this line** first.

### 🎯 What is it doing?

We currently have:

```text
sqrtPriceX96
```

which is a **Q64.96** value:

\[
\boxed{sqrtPriceX96=\sqrt P\times2^{96}}
\]

But the logarithm calculation that comes next wants the sqrt-price on a **\(2^{128}\) scale**.

So we do:

```solidity
uint256(sqrtPriceX96) << 32
```

### Why `<< 32`?

Because:

\[
2^{96}\times2^{32}=2^{128}
\]

So:

```text
Q64.96
   ↓
<< 32
   ↓
same mathematical value
but now scaled by 2^128
```

Mathematically:

\[
sqrtPriceX96 = \sqrt P\times2^{96}
\]

then:

\[
sqrtPriceX96\times2^{32}
=
\sqrt P\times2^{128}
\]

So `ratio` now represents:

\[
\boxed{ratio=\sqrt P\times2^{128}}
\]

### 🧒 Tiny example

Forget Uniswap's huge numbers.

Imagine our scale was:

```text
old scale = 2^4
```

and we wanted:

```text
new scale = 2^6
```

We need:

\[
2^6/2^4=2^2
\]

So we'd shift left by 2:

```text
old value << 2
```

Same idea here:

```text
2^96 → 2^128
```

Difference:

\[
128-96=32
\]

therefore:

```solidity
<< 32
```

### ⚠️ Important

This does **not** mean the mathematical sqrt-price became 32 times bigger.

It means the **fixed-point encoding scale** became \(2^{32}\) larger.

So:

```text
MATHEMATICAL VALUE
√P
   ↓
unchanged

ENCODING
√P × 2^96
   ↓ << 32
√P × 2^128
```

### One-line mental model

> **We already have the right sqrt-price, but it is encoded with \(2^{96}\). We shift left by 32 so it becomes encoded with \(2^{128}\), which is the scale needed for the logarithm work that follows.**

---

# 📐 Formula Picture — What Happens After This Line?

The important big-picture formula is:

\[
\boxed{sqrtPriceX96=\sqrt P\times2^{96}}
\]

After:

```solidity
uint256 ratio = uint256(sqrtPriceX96) << 32;
```

we have:

\[
\boxed{ratio=\sqrt P\times2^{128}}
\]

Now the mathematical job of the next section is to recover the logarithm.

We want:

\[
\log_2(\sqrt P)
\]

But we currently have:

\[
ratio=\sqrt P\times2^{128}
\]

Using:

\[
\log_2(ab)=\log_2(a)+\log_2(b)
\]

we get:

\[
\log_2(ratio)
=
\log_2(\sqrt P)+128
\]

Therefore:

\[
\boxed{
\log_2(\sqrt P)
=
\log_2(ratio)-128
}
\]

---

# 📐 Connecting the Logarithm to the Tick

We already know:

\[
P=1.0001^{tick}
\]

Take the square root:

\[
\sqrt P=1.0001^{tick/2}
\]

Take \(\log_2\):

\[
\log_2(\sqrt P)
=
\frac{tick}{2}\log_2(1.0001)
\]

Therefore:

\[
\boxed{
tick=
\frac{2\log_2(\sqrt P)}
{\log_2(1.0001)}
}
\]

And because we obtained `log₂(√P)` from `ratio`:

\[
\boxed{
tick=
\frac{2(\log_2(ratio)-128)}
{\log_2(1.0001)}
}
\]

### 🚨 Important

The actual Solidity does **not** literally write that formula.

Instead, it builds `log₂(ratio)` using the:

```text
msb search
   ↓
normalization
   ↓
repeated squaring
   ↓
binary fractional logarithm
```

So the mathematical formula is the **roadmap**, while the assembly is the optimized implementation of that roadmap.

---

# 🧠 Full Picture Before the Next Line

```text
sqrtPriceX96
      ↓
Q64.96
      ↓
√P × 2^96
      │
      │ << 32
      ▼
√P × 2^128
      ↓
   ratio
      ↓
find log₂(ratio)
      ↓
remove the +128 from the scaling
      ↓
log₂(√P)
      ↓
convert logarithm into tick
      ↓
tickLow / tickHi
      ↓
choose the greatest valid tick
```

So when we see:

```solidity
uint256 ratio = uint256(sqrtPriceX96) << 32;
```

the mental model is:

> **“We are taking the Q64.96 sqrt-price and changing its encoding scale from \(2^{96}\) to \(2^{128}\), because the logarithm machinery that follows is built around that \(2^{128}\) scale.”**

---

# ❓ Is `128` Some Mathematical Requirement?

**No.**

The `128` here is primarily a **fixed-point scaling choice**.

In principle, another scaling factor could be chosen.

For example, one could mathematically imagine representing the same value as:

\[
\sqrt P\times2^{64}
\]

or:

\[
\sqrt P\times2^{192}
\]

The mathematical value \(\sqrt P\) itself does not care whether we encode it using \(2^{64}\), \(2^{128}\), or another scale.

The scale is an **encoding choice**.

---

# ⚠️ But Can We Just Change `128` in This Implementation?

Not arbitrarily.

For **this implementation**, the rest of the algorithm is designed around this \(2^{128}\) scale.

The following logarithm calculations use operations such as:

```solidity
mul(r, r)
```

and fixed shifts such as:

```solidity
shr(127, ...)
shr(128, ...)
```

The precision, range, shifts, and overflow safety are all connected.

So:

```text
Mathematically:
128 = a scaling choice ✅

For this implementation:
128 = a carefully chosen scaling choice
      that the surrounding arithmetic is built around ✅
```

If we changed the scale, we would also need to redesign the related arithmetic and precision handling.

---

# 🎯 Final Mental Model

```text
Q64.96 input
    │
    │ sqrtPriceX96 = √P × 2^96
    ▼
shift left by 32
    │
    │ 2^96 × 2^32 = 2^128
    ▼
ratio = √P × 2^128
    │
    ▼
high-precision intermediate scale
    │
    ▼
log₂ calculation
    │
    ▼
recover √P's logarithm
    │
    ▼
recover tick
```

### The key point

> **`128` is the chosen intermediate fixed-point scale. It is not a universal mathematical requirement. It is used here because the rest of this particular logarithm implementation is built around that scale.**
