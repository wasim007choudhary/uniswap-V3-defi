# `getNextSqrtPriceFromAmount1RoundingDown()`

```solidity
function getNextSqrtPriceFromAmount1RoundingDown(
    uint160 sqrtPX96,
    uint128 liquidity,
    uint256 amount,
    bool add
)
    internal
    pure
    returns (uint160)
{
    if (add) {
        uint256 quotient =
            (amount <= type(uint160).max
                ? (amount << FixedPoint96.RESOLUTION) / liquidity
                : FullMath.mulDiv(amount, FixedPoint96.Q96, liquidity));

        return uint256(sqrtPX96).add(quotient).toUint160();
    } else {
        uint256 quotient =
            (amount <= type(uint160).max
                ? UnsafeMath.divRoundingUp(
                    amount << FixedPoint96.RESOLUTION,
                    liquidity
                )
                : FullMath.mulDivRoundingUp(
                    amount,
                    FixedPoint96.Q96,
                    liquidity
                ));

        require(sqrtPX96 > quotient);
        return uint160(sqrtPX96 - quotient);
    }
}
```

---

# Purpose

This function calculates the **next sqrt price** when token1 is added to or removed from the virtual reserves.

The formula is:

```text
√Pnext = √Pcurrent ± amount / liquidity
```

So:

```text
ADD token1    → sqrt price goes UP
REMOVE token1 → sqrt price goes DOWN
```

The function is called `RoundingDown` because the **final sqrt price is always rounded down**.

The interesting part is that the **quotient** is rounded differently depending on whether it will be added or subtracted.

---

# The Basic Example We Use Throughout

To make the logic easy to see, use:

```text
Current sqrt price = 100
Liquidity          = 10
Token1 amount      = 7
```

Therefore:

```text
amount / liquidity
= 7 / 10
= 0.7
```

So the exact mathematical price movement is:

```text
0.7
```

We will keep these same numbers while looking at the different branches.

---

# `if (add)`

```solidity
if (add) {
```

If `add == true`, token1 is being added.

Adding token1 makes the sqrt price increase.

So the formula is:

```text
√Pnext = √Pcurrent + amount / liquidity
```

With our numbers:

```text
√Pnext = 100 + 0.7
       = 100.7
```

The exact mathematical answer is therefore:

```text
100.7
```

---

# ADD — Why Does The Code Round Down?

The code calculates the quotient using:

```solidity
(amount << FixedPoint96.RESOLUTION) / liquidity
```

Conceptually, ignoring the Q96 encoding for the moment:

```text
7 / 10 = 0.7
```

Integer division cannot keep the decimal fraction, so:

```text
0.7 → 0
```

Then the code adds that quotient:

```solidity
sqrtPX96 + quotient
```

So our simplified calculation becomes:

```text
100 + 0
= 100
```

Therefore:

```text
Exact result:   100.7
Actual result:  100
```

---

# Why Not Round `100.7` Up To `101`?

This was an important question.

Yes, `101` is also a possible rounded value.

But think about what it would mean in practical terms.

The 7 token1 are supposed to move the price:

```text
100 → 100.7
```

If we use:

```text
101
```

we are treating those same 7 token1 as if they moved the price:

```text
100 → 101
```

That is a larger price movement than the token1 amount actually produced.

So:

```text
Exact movement:       +0.7
Rounded-up movement:  +1
```

The price has been pushed too far upward.

The sqrt price is subsequently used for token-amount calculations. Using `101` would therefore make later calculations behave as though the trader caused a larger price movement than the supplied token1 amount actually caused.

That can give the trader an unnecessarily favorable result at the expense of the pool.

Using `100` is also not exact:

```text
100 ≠ 100.7
```

But it does not pretend that the price moved farther upward than it actually should.

So the choice is:

```text
100.7
  ↓
100   ← below exact
```

rather than:

```text
100.7
  ↓
101   ← above exact
```

The goal is **not** to find the closest integer.

The goal is to choose the correct side of the exact result.

---

# ADD — Child Analogy

Imagine the price is a child standing at step `100`.

The 7 token1 tell the child:

> "Move upward by 0.7 step."

The exact destination is:

```text
100.7
```

If we force the child to step all the way to `101`, we made them move farther than the amount justified.

So we stay at:

```text
100
```

It is not the exact destination.

It is simply the safer side of the destination.

# REMOVE — `else`

```solidity
} else {
```

Now:

```text
add == false
```

So token1 is being removed.

Removing token1 makes the sqrt price decrease.

The formula becomes:

```text
√Pnext = √Pcurrent - amount / liquidity
```

Using the same numbers:

```text
√Pnext = 100 - 0.7
       = 99.3
```

The exact mathematical answer is:

```text
99.3
```

---

# REMOVE — Why Can't We Round The Quotient Down?

Suppose we used normal integer division again:

```text
0.7 → 0
```

Then:

```text
100 - 0
= 100
```

Now compare:

```text
Wanted:  99.3
Got:     100
```

The price was supposed to go down, but it did not move down at all.

We are on the wrong side of the exact result:

```text
100 > 99.3
```

So rounding the quotient down does not work for the subtraction case.

---

# REMOVE — Why Does The Code Round The Quotient Up?

The code uses:

```solidity
UnsafeMath.divRoundingUp(
    amount << FixedPoint96.RESOLUTION,
    liquidity
)
```

Conceptually:

```text
0.7 → 1
```

Then:

```text
100 - 1
= 99
```

Compare:

```text
Exact result:   99.3
Actual result:  99
```

Now:

```text
99 < 99.3
```

So the final sqrt price is again on the lower side of the exact result.

---

# Why Is `99` Better Than `100`?

This was the other important question.

Again, `99` is not exact.

```text
99 ≠ 99.3
```

But compare the two possible whole-number choices:

```text
99  ← below 99.3
100 ← above 99.3
```

The price needs to move downward.

If we choose `100`, the price is still above the exact answer.

If we choose `99`, the price has actually moved downward.

So the function chooses:

```text
99.3 → 99
```

rather than:

```text
99.3 → 100
```

---

# REMOVE — Child Analogy

Imagine the price is a child standing at `100`.

Removing token1 tells the child:

> "Slide down by 0.7 step."

The exact destination is:

```text
99.3
```

If we round the movement down:

```text
0.7 → 0
```

the child does this:

```text
100 → 100
```

They did not slide down.

So instead we round the movement up:

```text
0.7 → 1
```

and the child does:

```text
100 → 99
```

Now the child has actually moved down.

---

# Rounding Up And Down — The Core Intuition

This is the part to remember.

The function is performing one of two operations:

```text
Current + movement
```

or:

```text
Current - movement
```

Because the movement is being added or subtracted, the quotient needs opposite rounding directions.

---

## ADD

Exact:

```text
100 + 0.7
= 100.7
```

If movement is rounded UP:

```text
0.7 → 1
```

then:

```text
100 + 1
= 101
```

That pushes the price **too far upward**.

Therefore:

```text
0.7 → 0
```

and:

```text
100 + 0
= 100
```

So:

> **ADD → quotient rounds DOWN.**

---

## REMOVE

Exact:

```text
100 - 0.7
= 99.3
```

If movement is rounded DOWN:

```text
0.7 → 0
```

then:

```text
100 - 0
= 100
```

The price does not move down far enough.

Therefore:

```text
0.7 → 1
```

and:

```text
100 - 1
= 99
```

So:

> **REMOVE → quotient rounds UP.**

---

# The Resulting Pattern

```text
                         Quotient       Final sqrt price
ADD token1                  ↓                ↓
                         round down       round down

REMOVE token1               ↑                ↓
                         round up         round down
```

The quotient uses opposite rounding directions.

But the **final sqrt price is rounded DOWN in both cases**.

# The Two Quotient Calculation Paths

The code contains:

```solidity
amount <= type(uint160).max
    ? ...
    : ...
```

This does **not** change the mathematical rounding rule.

It only changes how the quotient is calculated.

---

## Small Amount — ADD

```solidity
(amount << FixedPoint96.RESOLUTION) / liquidity
```

Normal integer division gives the quotient rounded DOWN.

---

## Small Amount — REMOVE

```solidity
UnsafeMath.divRoundingUp(
    amount << FixedPoint96.RESOLUTION,
    liquidity
)
```

This explicitly gives the quotient rounded UP.

---

## Large Amount

For a large `amount`, the intermediate multiplication:

```text
amount × 2^96
```

may not fit into one normal `uint256`.

So the code uses `FullMath`.

### ADD

```solidity
FullMath.mulDiv(
    amount,
    FixedPoint96.Q96,
    liquidity
)
```

This calculates the quotient rounded DOWN.

### REMOVE

```solidity
FullMath.mulDivRoundingUp(
    amount,
    FixedPoint96.Q96,
    liquidity
)
```

This calculates the quotient rounded UP.

So:

```text
Small amount → cheaper calculation
Large amount → FullMath for the large intermediate multiplication
```

The rounding rule stays exactly the same.

---

# `require(sqrtPX96 > quotient)`

After calculating the REMOVE quotient, the code says:

```solidity
require(sqrtPX96 > quotient);
```

We are about to perform:

```text
sqrtPX96 - quotient
```

So the function must make sure the result stays positive.

Using our normal example:

```text
sqrtPX96 = 100
quotient  = 1
```

Check:

```text
100 > 1
```

True.

So:

```text
100 - 1
= 99
```

Everything is valid.

---

# What If The Check Fails?

Suppose:

```text
sqrtPX96 = 100
quotient  = 100
```

Check:

```text
100 > 100
```

False.

The function reverts.

Why?

Because the new price would be:

```text
100 - 100
= 0
```

But sqrt price cannot become zero.

Even worse, suppose:

```text
sqrtPX96 = 100
quotient  = 101
```

Then:

```text
100 - 101
= -1
```

A `uint160` cannot represent a negative number.

So the `require` prevents the function from producing an invalid sqrt price.

---

# Final Cast

After:

```solidity
require(sqrtPX96 > quotient);
```

the code returns:

```solidity
return uint160(sqrtPX96 - quotient);
```

The result is smaller than `sqrtPX96`.

And `sqrtPX96` was already a `uint160`.

Therefore the result also fits into `uint160`.

Example:

```text
sqrtPX96 = 100
quotient  = 1

100 - 1
= 99
```

So the original code can safely use:

```solidity
uint160(...)
```

The comment in Uniswap's code captures this:

```solidity
// always fits 160 bits
```
