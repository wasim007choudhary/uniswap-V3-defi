# 🧮 `getNextSqrtPriceFromAmount1RoundingDown()` Dissection

~~~solidity
function getNextSqrtPriceFromAmount1RoundingDown(
    uint160 sqrtPX96,
    uint128 liquidity,
    uint256 amount,
    bool add
)
    internal
    pure
    returns (uint160)
{
    if (add) {
        uint256 quotient =
            (amount <= type(uint160).max
                ? (amount << FixedPoint96.RESOLUTION) / liquidity
                : FullMath.mulDiv(amount, FixedPoint96.Q96, liquidity));

        return uint256(sqrtPX96).add(quotient).toUint160();
    } else {
        uint256 quotient =
            (amount <= type(uint160).max
                ? UnsafeMath.divRoundingUp(
                    amount << FixedPoint96.RESOLUTION,
                    liquidity
                )
                : FullMath.mulDivRoundingUp(
                    amount,
                    FixedPoint96.Q96,
                    liquidity
                ));

        require(sqrtPX96 > quotient);
        return uint160(sqrtPX96 - quotient);
    }
}
~~~

---

# 🎯 Purpose

This function calculates the **next sqrt price** when token1 is added to or removed from the virtual reserves.

The formula is:

~~~text
√Pnext = √Pcurrent ± amount / liquidity
~~~

So:

~~~text
ADD token1    → sqrt price goes UP
REMOVE token1 → sqrt price goes DOWN
~~~

The function is called `RoundingDown` because the **final sqrt price is always rounded down**.

The interesting part is that the **quotient** is rounded differently depending on whether it will be added or subtracted.

# 🔽 ADD — Why Does The Code Round Down?

The code calculates the quotient using:

~~~solidity
(amount << FixedPoint96.RESOLUTION) / liquidity
~~~

Conceptually, ignoring the Q96 encoding for the moment:

~~~text
7 / 10 = 0.7
~~~

Integer division cannot keep the decimal fraction, so:

~~~text
0.7 → 0
~~~

Then the code adds that quotient:

~~~solidity
sqrtPX96 + quotient
~~~

So our simplified calculation becomes:

~~~text
100 + 0
= 100
~~~

Therefore:

~~~text
Exact result:   100.7
Actual result:  100
~~~

---

# 🤔 Why Not Round `100.7` Up To `101`?

This was an important question.

Yes, `101` is also a possible rounded value.

But think about what it would mean in practical terms.

The 7 token1 are supposed to move the price:

~~~text
100 → 100.7
~~~

If we use:

~~~text
101
~~~

we are treating those same 7 token1 as if they moved the price:

~~~text
100 → 101
~~~

That is a larger price movement than the token1 amount actually produced.

So:

~~~text
Actual movement:       +0.7
Rounded-down movement: +0
Rounded-up movement:   +1
~~~

The `+1` movement is larger than the real `+0.7` movement.

From the protocol's point of view, that is an unnecessary extra price movement.

That changed price is then used for token-amount calculations. Using `101` would therefore make later calculations behave as though the trader caused a larger price movement than the supplied token1 amount actually caused.

That can give the trader an unnecessarily favorable result at the expense of the pool.

Using `100` is also not exact:

~~~text
100 ≠ 100.7
~~~

But it does not pretend that the price moved farther upward than it actually should.

So the choice is:

~~~text
100.7
 ↓
100   ← below exact
~~~

rather than:

~~~text
100.7
 ↓
101   ← above exact
~~~

The goal is **not** to find the closest integer.

The goal is to choose the correct side of the exact result.

# 🧠 Rounding Up And Down — The Core Intuition

This is the part to remember.

The function is performing one of two operations:

~~~text
Current + movement
~~~

or:

~~~text
Current - movement
~~~

Because the movement is being added or subtracted, the quotient needs opposite rounding directions.

---

## ➕ ADD

Exact:

~~~text
100 + 0.7
= 100.7
~~~

If movement is rounded UP:

~~~text
0.7 → 1
~~~

then:

~~~text
100 + 1
= 101
~~~

That pushes the price **too far upward**.

Therefore:

~~~text
0.7 → 0
~~~

and:

~~~text
100 + 0
= 100
~~~

So:

> **ADD → quotient rounds DOWN.**

---

## ➖ REMOVE

Exact:

~~~text
100 - 0.7
= 99.3
~~~

If movement is rounded DOWN:

~~~text
0.7 → 0
~~~

then:

~~~text
100 - 0
= 100
~~~

The price does not move down far enough.

Therefore:

~~~text
0.7 → 1
~~~

and:

~~~text
100 - 1
= 99
~~~

So:

> **REMOVE → quotient rounds UP.**

                         Quotient       Final sqrt price

                         round down       round down

REMOVE token1               ↑                ↓
                         round up         round down

The quotient uses opposite rounding directions.

But the **final sqrt price is rounded DOWN in both cases**.

# ⚙️ The Two Quotient Calculation Paths

The code contains:

~~~solidity
amount <= type(uint160).max
    ? ...
    : ...
~~~

This does **not** change the mathematical rounding rule.

It only changes how the quotient is calculated.

---

## Small Amount — ADD

~~~solidity
(amount << FixedPoint96.RESOLUTION) / liquidity
~~~

Normal integer division gives the quotient rounded DOWN.

---

## Small Amount — REMOVE

~~~solidity
UnsafeMath.divRoundingUp(
    amount << FixedPoint96.RESOLUTION,
    liquidity
)
~~~

This explicitly gives the quotient rounded UP.

---

## Large Amount

For a large `amount`, the intermediate multiplication:

~~~text
amount × 2^96
~~~

may not fit into one normal `uint256`.

So the code uses `FullMath`.

### ADD

~~~solidity
FullMath.mulDiv(
    amount,
    FixedPoint96.Q96,
    liquidity
)
~~~

This calculates the quotient rounded DOWN.

### REMOVE

~~~solidity
FullMath.mulDivRoundingUp(
    amount,
    FixedPoint96.Q96,
    liquidity
)
~~~

This calculates the quotient rounded UP.

So:

~~~text
Small amount → cheaper calculation
Large amount → FullMath for the large intermediate multiplication
~~~

The rounding rule stays exactly the same.

---

# 🛡️ `require(sqrtPX96 > quotient)`

After calculating the REMOVE quotient, the code says:

~~~solidity
require(sqrtPX96 > quotient);
~~~

We are about to perform:

~~~text
sqrtPX96 - quotient
~~~

So the function must make sure the result stays positive.

Using our normal example:

~~~text
sqrtPX96 = 100
quotient  = 1
~~~

Check:

~~~text
100 > 1
~~~

True.

So:

~~~text
100 - 1
= 99
~~~

Everything is valid.

---

# 🚨 What If The Check Fails?

Suppose:

~~~text
sqrtPX96 = 100
quotient  = 100
~~~

Check:

~~~text
100 > 100
~~~

False.

The function reverts.

Why?

Because the new price would be:

~~~text
100 - 100
= 0
~~~

But sqrt price cannot become zero.

Even worse, suppose:

~~~text
sqrtPX96 = 100
quotient  = 101
~~~

Then:

~~~text
100 - 101
= -1
~~~

A `uint160` cannot represent a negative number.

So the `require` prevents the function from producing an invalid sqrt price.

---

# 🔒 Final Cast

After:

~~~solidity
require(sqrtPX96 > quotient);
~~~

the code returns:

~~~solidity
return uint160(sqrtPX96 - quotient);
~~~

The result is smaller than `sqrtPX96`.

And `sqrtPX96` was already a `uint160`.

Therefore the result also fits into `uint160`.

Example:

~~~text
sqrtPX96 = 100
quotient  = 1

100 - 1
= 99
~~~

So the original code can safely use:

~~~solidity
uint160(...)
~~~

The comment in Uniswap's code captures this:

~~~solidity
// always fits 160 bits
~~~

> # 💰 Uniswap V3 — Amount1 Rounding From the Money Point of View

## The Main Idea

In `getNextSqrtPriceFromAmount1RoundingDown()`, Uniswap V3 is not trying to find the mathematically closest integer.

It is choosing the rounding direction that protects the swap from moving the price **too far in the wrong direction**.

The important question is:

> **Who is giving tokens, who is receiving tokens, and could rounding accidentally give the trader too much or make the pool move too far?**

For token1:

~~~text
ADD token1    → sqrt price goes UP
REMOVE token1 → sqrt price goes DOWN
~~~

The function always makes the **final sqrt price round DOWN**.

That is why the quotient is rounded differently in the two branches.

---

# 1️⃣ ADD TOKEN1 — Trader Gives Token1 to the Pool

The formula is:

~~~text
sqrtPriceNext = sqrtPriceCurrent + amount / liquidity
~~~

Suppose:

~~~text
Current sqrt price = 100
Exact movement      = 0.7
~~~

The exact mathematical result is:

~~~text
100 + 0.7 = 100.7
~~~

But Solidity cannot keep the fractional part in this integer calculation.

So Uniswap has two choices:

~~~text
Round DOWN → 100
Round UP   → 101
~~~

Uniswap chooses:

~~~text
100
~~~

## Why not 101?

Because `101` would move the price **farther upward than the actual token1 amount justifies**.

Think of it like this:

~~~text
Actual movement:       +0.7
Rounded-down movement: +0
Rounded-up movement:   +1
~~~

The `+1` movement is larger than the real `+0.7` movement.

From the protocol's point of view, that is an unnecessary extra price movement.

That changed price is then used for the rest of the swap calculations. An unnecessarily high price can make the pool behave as though more price movement occurred than the trader's token1 actually caused.

So Uniswap does **not** say:

> "101 is closer to 100.7, so let's use 101."

Instead it says:

> "Do not push the pool's price farther than necessary."

---

# 2️⃣ From the Trader's Money Point of View

Suppose a trader is supplying token1 and receiving token0.

The trader gives:

~~~text
Token1 → Pool
~~~

and receives:

~~~text
Pool → Token0
~~~

If the implementation rounded the price upward to `101` instead of downward to `100`, it would create a slightly larger upward price movement.

That can affect the amount of token0 calculated as available to the trader.

The important principle is:

> **The rounding direction is chosen so integer arithmetic does not create an overly favorable amount of output by pretending that the price moved farther than the actual token1 input caused.**

So this is not simply:

~~~text
rounding = trader wins
~~~

or:

~~~text
rounding = LP wins
~~~

It is more precise to say:

> **The rounding protects the pool's accounting from an artificial price movement caused by integer truncation.**

---

# 3️⃣ REMOVE TOKEN1 — Trader Wants Token0 Out

Now the formula becomes:

~~~text
sqrtPriceNext = sqrtPriceCurrent - amount / liquidity
~~~

Suppose:

~~~text
Current sqrt price = 100
Exact movement      = 0.7
~~~

The exact result is:

~~~text
100 - 0.7 = 99.3
~~~

Again, suppose we can only represent whole numbers.

Two choices:

~~~text
Round DOWN → 99
Round UP   → 100
~~~

But here the quotient itself is what matters.

If we rounded the quotient DOWN:

~~~text
amount / liquidity ≈ 0
~~~

then:

~~~text
100 - 0 = 100
~~~

The price would **not move at all**.

That is not enough.

The trader is removing token1 from the virtual reserves, so the price must actually move downward.

Therefore Uniswap rounds the quotient UP:

~~~text
quotient = 1
~~~

and:

~~~text
100 - 1 = 99
~~~

Now the price has moved downward far enough.

---

# 4️⃣ Why This Matters for the Trader

In the REMOVE case, the trader is effectively asking for output that requires the price to move downward.

If Uniswap rounded:

~~~text
0.7 → 0
~~~

then:

~~~text
100 → 100
~~~

The price would stop too early.

That would mean the calculation did not move the price far enough to account for the requested token movement.

Instead:

~~~text
0.7 → 1
~~~

gives:

~~~text
100 → 99
~~~

The price moves slightly farther downward than the exact mathematical value:

~~~text
Exact:   99.3
Actual:  99
~~~

This is deliberate.

It makes sure the required price movement is **not understated**.

---

# 5️⃣ The Important Difference Between ADD and REMOVE

The same mathematical rounding cannot be used in both branches.

### ADD token1

~~~text
100 + 0.7
~~~

If we round the movement UP:

~~~text
100 + 1 = 101
~~~

The price moves too far upward.

So:

~~~text
quotient → ROUND DOWN
~~~

### REMOVE token1

~~~text
100 - 0.7
~~~

If we round the movement DOWN:

~~~text
100 - 0 = 100
~~~

The price does not move far enough downward.

So:

~~~text
quotient → ROUND UP
~~~

Therefore:

~~~text
ADD:
   quotient ↓
   100 + 0 = 100

REMOVE:
   quotient ↑
   100 - 1 = 99
~~~

And in both cases, the **final sqrt price is rounded DOWN** relative to the exact mathematical result.

---

# 6️⃣ Why Uniswap Calls the Function `RoundingDown`

The function name is:

~~~solidity
getNextSqrtPriceFromAmount1RoundingDown()
~~~

This does **not** mean:

> "Always round `amount / liquidity` down."

That would be wrong.

Instead:

> **The final sqrt price is rounded down.**

Example:

~~~text
ADD:

Exact price = 100.7
Final price = 100

100 < 100.7
~~~

And:

~~~text
REMOVE:

Exact price = 99.3
Final price = 99

99 < 99.3
~~~

So:

~~~text
ADD    → quotient rounds DOWN
REMOVE → quotient rounds UP

Both produce:

Final sqrt price ≤ exact sqrt price
~~~

That is the key.

---

# 7️⃣ Trader vs Uniswap V3 — Who Benefits?

It is tempting to describe every rounding decision as:

~~~text
Trader wins
~~~

or:

~~~text
LP wins
~~~

That is too simplistic.

The real purpose is **conservative protocol accounting**.

Uniswap V3 has to ensure that integer arithmetic does not accidentally:

\- move the price farther than the supplied token amount justifies,
\- move the price insufficiently for the required token movement,
\- or create an output amount that comes from rounding rather than real liquidity movement.

The rounding direction is therefore part of the AMM's **economic safety boundary**.

# 9️⃣ The Code Behind the Economic Rule

The ADD branch uses:

~~~solidity
(amount << RESOLUTION) / liquidity
~~~

which performs ordinary integer division and therefore rounds the quotient DOWN.

The REMOVE branch uses:

~~~solidity
UnsafeMath.divRoundingUp(
    amount << RESOLUTION,
    liquidity
)
~~~

which rounds the quotient UP.

For large `amount` values, the equivalent FullMath paths are used:

~~~solidity
FullMath.mulDiv(amount, Q96, liquidity)
~~~

for ADD, and:

~~~solidity
FullMath.mulDivRoundingUp(amount, Q96, liquidity)
~~~

for REMOVE.

So the code directly implements the economic rule:

~~~text
ADD token1:
    price moves UP
    quotient rounds DOWN
    final price stays on/below exact result

REMOVE token1:
    price moves DOWN
    quotient rounds UP
    final price moves far enough DOWN
~~~
