# 💰 `getAmount1Delta()` — Signed Liquidity Overload

```solidity
function getAmount1Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    int128 liquidity
)
    internal
    pure
    returns (int256 amount1)
{
    return liquidity < 0
        ? -getAmount1Delta(
            sqrtRatioAX96,
            sqrtRatioBX96,
            uint128(-liquidity),
            false
        ).toInt256()
        : getAmount1Delta(
            sqrtRatioAX96,
            sqrtRatioBX96,
            uint128(liquidity),
            true
        ).toInt256();
}
```

---

## 🎯 What Is This Function Doing?

This is the **signed-liquidity overload** of:

```solidity
getAmount1Delta()
```

We already studied the unsigned version:

```solidity
getAmount1Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
```

That version calculates the **magnitude** of token1 required for a movement between two sqrt prices.

This version adds one important thing:

> **It allows liquidity to be positive or negative, so the returned token1 delta can also be positive or negative.**

```text
+liquidity
    ↓
liquidity contribution is being added
    ↓
+amount1


-liquidity
    ↓
liquidity contribution is being removed
    ↓
-amount1
```

So this function is not introducing a new token1 formula.

It is taking the existing unsigned `getAmount1Delta()` calculation and adding the **direction/sign**.

---

# 💰 1. Money Flow Point of View

Think about the signed liquidity as telling us what is happening to the liquidity contribution.

```text
+L
 ↓
liquidity contribution enters
 ↓
positive token1 delta
```

while:

```text
-L
 ↓
liquidity contribution leaves
 ↓
negative token1 delta
```

The negative number does **not** mean:

> "The pool has negative token1."

It means:

> **The token1 delta is moving in the opposite direction.**

This is a signed accounting value.

---

# 2. Function Parameters

### `sqrtRatioAX96`

One of the two sqrt prices.

### `sqrtRatioBX96`

The other sqrt price.

The underlying unsigned `getAmount1Delta()` function normalizes their order:

```text
A = lower sqrt price
B = upper sqrt price
```

and then calculates:

```text
amount1 = L × (B - A) / Q96
```

### `liquidity`

```solidity
int128 liquidity
```

This is the important difference.

It can be:

```text
+L
```

or:

```text
-L
```

### `amount1`

```solidity
returns (int256 amount1)
```

It must be `int256` because the result can be:

```text
+amount1
```

or:

```text
-amount1
```

---

# 3. The Main Decision

The function begins:

```solidity
return liquidity < 0
    ? ...
    : ...;
```

This asks:

```text
Is liquidity negative?
```

There are two possible paths:

```text
                    liquidity
                        │
               ┌────────┴────────┐
               │                 │
             < 0               >= 0
               │                 │
               ▼                 ▼
          negative L         positive L
```

---

# 4. Negative Liquidity = Remove the Liquidity Contribution

The negative branch is:

```solidity
-getAmount1Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
).toInt256()
```

Suppose:

```text
liquidity = -100
```

The unsigned `getAmount1Delta()` cannot accept `-100` because it expects:

```solidity
uint128
```

So first we remove the sign:

```solidity
-liquidity
```

which gives:

```text
-(-100) = +100
```

Then:

```solidity
uint128(-liquidity)
```

becomes:

```text
100
```

Now the normal unsigned function can calculate the **magnitude** of the token1 delta.

---

# 5. Why Temporarily Remove the Negative Sign?

Because the underlying function only understands positive liquidity.

Think of it like this:

```text
-liquidity
    ↓
turn -100 into +100
    ↓
calculate the amount1 magnitude
    ↓
put the negative sign back
```

So:

```text
-100 liquidity
      ↓
+100 liquidity
      ↓
calculate amount1
      ↓
+amount1
      ↓
negate
      ↓
-amount1
```

The wrapper is responsible for the sign.

The unsigned function is responsible for the magnitude.

---

# 6. Why Does Negative Liquidity Use `roundUp = false`?

Look at:

```solidity
getAmount1Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
)
```

The final argument is:

```solidity
false
```

which means:

```text
roundUp = false
```

Therefore the positive magnitude is rounded **DOWN** before we make it negative.

Suppose the exact mathematical token1 amount is:

```text
100.7 token1
```

The unsigned function calculates:

```text
100.7
 ↓ round DOWN
100
```

Then the outer `-` gives:

```text
-100
```

So:

```text
100.7
   ↓
100
   ↓
-100
```

---

# 7. Why Not Round Up for Negative Liquidity?

Because then:

```text
100.7
 ↓ round UP
101
 ↓ negate
-101
```

would make the negative delta larger in magnitude.

Instead:

```text
100.7
 ↓ round DOWN
100
 ↓ negate
-100
```

This preserves the intended signed rounding behavior.

The important pattern is:

```text
positive liquidity
    → round UP
    → positive result

negative liquidity
    → round DOWN
    → negate
    → negative result
```

---

# 8. Convert `uint256` to `int256`

The unsigned `getAmount1Delta()` returns:

```solidity
uint256
```

But this function returns:

```solidity
int256
```

So:

```solidity
.toInt256()
```

converts:

```text
uint256
   ↓
int256
```

For example:

```text
100 uint256
    ↓
100 int256
```

Then the outer negative sign can turn it into:

```text
-100 int256
```

---

# 9. The Final `-`

Look carefully at the beginning of the negative branch:

```solidity
-getAmount1Delta(...)
```

That final negative sign restores the original direction of the liquidity.

So:

```text
liquidity = -100
```

becomes:

```text
-liquidity
    ↓
100
```

Then:

```text
getAmount1Delta(..., 100, false)
    ↓
100
```

Then:

```text
.toInt256()
    ↓
100
```

Then:

```text
-
    ↓
-100
```

Final:

```text
amount1 = -100
```

---

# 10. Positive Liquidity = Add the Liquidity Contribution

Now the positive side:

```solidity
getAmount1Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(liquidity),
    true
).toInt256()
```

Suppose:

```text
liquidity = +100
```

We convert it to:

```solidity
uint128(liquidity)
```

and call the unsigned function.

This time:

```solidity
true
```

means:

```text
roundUp = true
```

Suppose the exact amount is:

```text
100.7 token1
```

Then:

```text
100.7
 ↓ round UP
101
```

After `.toInt256()`:

```text
+101
```

So:

```text
+liquidity
    ↓
calculate positive token1 amount
    ↓
round UP
    ↓
+amount1
```

# 13. Why Does It Call `getAmount1Delta()` Again?

You see:

```solidity
getAmount1Delta(...)
```

inside:

```solidity
getAmount1Delta(...)
```

This is **function overloading**, not infinite recursion.

There are two versions.

### Unsigned version

```solidity
getAmount1Delta(
    uint160,
    uint160,
    uint128,
    bool
)
```

### Signed version

```solidity
getAmount1Delta(
    uint160,
    uint160,
    int128
)
```

When we write:

```solidity
getAmount1Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
)
```

the arguments are:

```text
uint160
uint160
uint128
bool
```

so the compiler selects the **unsigned four-parameter version**.

Therefore this signed function is simply a wrapper around the existing unsigned function.

---

# 🔥 14. Why `getAmount1Delta()` Is Simpler Than `getAmount0Delta()`

The underlying token1 formula is:

```text
                 L × (upper - lower)
amount1 = ─────────────────────────────
                         Q96
```

So the unsigned function only needs:

```solidity
FullMath.mulDiv(...)
```

or:

```solidity
FullMath.mulDivRoundingUp(...)
```

There is no `upper × lower` denominator like token0 has.

But the **signed wrapper works exactly the same conceptually**:

```text
positive liquidity
    → positive amount1

negative liquidity
    → negative amount1
```

# 💡 16. The Rounding Rule

Remember this exact relationship:

```text
liquidity > 0
    ↓
roundUp = true
    ↓
amount1 rounded UP
    ↓
positive amount1
```

```text
liquidity < 0
    ↓
make liquidity positive
    ↓
roundUp = false
    ↓
amount1 rounded DOWN
    ↓
negate
    ↓
negative amount1
```

Example:

```text
Exact amount = 100.7
```

Positive:

```text
100.7
 ↓
101
 ↓
+101
```

Negative:

```text
100.7
 ↓
100
 ↓
-100
```

# 🔥 Final Mental Model

> **This overload allows `getAmount1Delta()` to work with signed liquidity. Positive liquidity represents an added liquidity contribution and produces a positive token1 delta. Negative liquidity represents a removed liquidity contribution and produces a negative token1 delta.**

It does **not** calculate a new token1 formula.

It simply:

```text
+ liquidity
    ↓
calculate unsigned token1 delta
    ↓
round UP
    ↓
return +amount1
```

and:

```text
- liquidity
    ↓
temporarily remove the negative sign
    ↓
calculate unsigned token1 delta
    ↓
round DOWN
    ↓
convert to int256
    ↓
put negative sign back
    ↓
return -amount1
```

### 🧠 One-line memory trick

```text
Positive L → positive Δ1 → round UP

Negative L → negative Δ1 → round DOWN → negate
```

So the whole purpose is:

> **Unsigned function = calculates the magnitude.  
> Signed overload = adds the direction.**
