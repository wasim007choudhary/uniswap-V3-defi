# 🧮 `getAmount0Delta()` Dissection

```solidity
function getAmount0Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
    internal
    pure
    returns (uint256 amount0)
{
    if (sqrtRatioAX96 > sqrtRatioBX96)
        (sqrtRatioAX96, sqrtRatioBX96) = (sqrtRatioBX96, sqrtRatioAX96);

    uint256 numerator1 = uint256(liquidity) << FixedPoint96.RESOLUTION;
    uint256 numerator2 = sqrtRatioBX96 - sqrtRatioAX96;

    require(sqrtRatioAX96 > 0);

    return roundUp
        ? UnsafeMath.divRoundingUp(
            FullMath.mulDivRoundingUp(
                numerator1,
                numerator2,
                sqrtRatioBX96
            ),
            sqrtRatioAX96
        )
        : FullMath.mulDiv(
            numerator1,
            numerator2,
            sqrtRatioBX96
        ) / sqrtRatioAX96;
}
```

---

# 🎯 Purpose

This function calculates the amount of **token0** corresponding to a movement between two sqrt prices for a given amount of liquidity.

The previous functions worked in the opposite direction.

```text
Token amount
    ↓
calculate price movement
    ↓
next sqrt price
```

But this function does:

```text
Current sqrt price
        +
Next/target sqrt price
        +
Liquidity
        ↓
calculate token0 amount
```

So it answers:

> **"How much token0 corresponds to moving the price between these two sqrt prices with this amount of liquidity?"**

---

# 🧮 The Mathematical Formula

The underlying formula is:

```text
amount0 = L × (1 / √Pₐ - 1 / √Pᵦ)
```

where:

```text
Pₐ = lower price
Pᵦ = upper price
```

Equivalently:

```text
amount0 =
L × (√Pᵦ - √Pₐ)
──────────────────
    √Pᵦ × √Pₐ
```

This is why the function needs **two sqrt prices**.

It is measuring the amount of token0 represented by the price movement between them.

---

# `sqrtRatioAX96`

```solidity
uint160 sqrtRatioAX96,
```

This is one of the two sqrt-price boundaries.

It does **not necessarily mean "lower" just because it is called A**.

The function itself handles either ordering.

That becomes important in the very first line:

```solidity
if (sqrtRatioAX96 > sqrtRatioBX96)
    (sqrtRatioAX96, sqrtRatioBX96) =
        (sqrtRatioBX96, sqrtRatioAX96);
```

After that line executes:

```text
sqrtRatioAX96 = LOWER sqrt price
sqrtRatioBX96 = HIGHER sqrt price
```

So from that point onward, we can safely think:

```text
A = lower
B = upper
```

---

# `sqrtRatioBX96`

```solidity
uint160 sqrtRatioBX96,
```

This is the second sqrt-price boundary.

Again, before normalization it could be either higher or lower.

After the first `if`:

```text
A = lower sqrt price
B = higher sqrt price
```

---

# `liquidity`

```solidity
uint128 liquidity,
```

This is the liquidity associated with the price interval.

The amount of token0 required for a given price movement depends on liquidity.

The relationship is:

```text
more liquidity
    ↓
more token0 required

less liquidity
    ↓
less token0 required
```

So `liquidity` is part of the amount0 calculation.

---

# `roundUp`

```solidity
bool roundUp
```

This tells the function how to round the final token0 amount.

```text
roundUp = true
    ↓
round the token0 amount UP

roundUp = false
    ↓
round the token0 amount DOWN
```

This matters because Solidity works with integers.

The exact mathematical token amount may contain a fractional part, but the contract must return an integer number of wei.

So Uniswap must deliberately choose a rounding direction.

---

# `internal`

```solidity
internal
```

The function is intended for internal use.

It is not directly callable by an external user.

---

# `pure`

```solidity
pure
```

The function does not read or modify blockchain state.

Everything required for the calculation is passed in:

```text
sqrtRatioAX96
sqrtRatioBX96
liquidity
roundUp
```

It simply calculates `amount0`.

---

# `returns (uint256 amount0)`

```solidity
returns (uint256 amount0)
```

The function returns the calculated amount of **token0**.

So conceptually:

```text
two sqrt prices
      +
   liquidity
      ↓
 token0 amount
```

# 🔄 First Line — Normalize The Prices

Now the first actual operation:

```solidity
if (sqrtRatioAX96 > sqrtRatioBX96)
    (sqrtRatioAX96, sqrtRatioBX96) =
        (sqrtRatioBX96, sqrtRatioAX96);
```

This is extremely important.

The function does **not require the caller to provide the prices in a particular order**.

It accepts:

```text
A < B
```

or:

```text
A > B
```

and fixes the ordering internally.

---

# Example

Suppose the caller gives:

```text
A = 200
B = 500
```

Since:

```text
200 < 500
```

nothing happens.

We already have:

```text
A = lower
B = upper
```

---

Now suppose the caller gives:

```text
A = 500
B = 200
```

The condition:

```solidity
sqrtRatioAX96 > sqrtRatioBX96
```

is:

```text
500 > 200
```

True.

So Solidity executes:

```solidity
(sqrtRatioAX96, sqrtRatioBX96) =
    (sqrtRatioBX96, sqrtRatioAX96);
```

and they become:

```text
A = 200
B = 500
```

So after this line:

> **A is always the lower sqrt price and B is always the higher sqrt price.**

# 🧒 Child Analogy

Imagine you give the function two kids:

```text
Kid A = 500
Kid B = 200
```

The function says:

> "I need the smaller number first."

So it swaps them:

```text
Kid A = 200
Kid B = 500
```

Now the function knows:

```text
A = small
B = big
```

This makes the rest of the math much easier.

---

# 🧠 Why Does This Matter?

Because the formula requires:

```text
√Pₐ < √Pᵦ
```

so that:

```text
√Pᵦ - √Pₐ
```

is positive.

The function guarantees this itself.

This is also why you should **not** memorize a special caller rule like:

> "`getAmount0Delta()` requires A lower and B upper."

It doesn't.

The function accepts either order and normalizes internally.

# 🧮 Next Line

```solidity
uint256 numerator1 = uint256(liquidity) << FixedPoint96.RESOLUTION;
```

We have already seen this pattern.

Remember:

```text
RESOLUTION = 96
```

Therefore:

```text
uint256(liquidity) << 96
```

is:

```text
liquidity × 2^96
```

So:

```text
numerator1 = L × 2^96
```

The cast:

```solidity
uint256(liquidity)
```

widens the `uint128` liquidity into a `uint256`.

Then:

```text
<< 96
```

scales it into the Q96 fixed-point representation used by the sqrt prices.

---

# 🧮 Next Line

```solidity
uint256 numerator2 = sqrtRatioBX96 - sqrtRatioAX96;
```

Because we already normalized the prices:

```text
A = lower
B = higher
```

we know:

```text
B - A > 0
```

So:

```text
numerator2 = upper sqrt price - lower sqrt price
```

Mathematically:

```text
numerator2 = √Pᵦ - √Pₐ
```

This is the **distance between the two sqrt prices**.

---

# 🧠 Put The Two Numerators Together

We now have:

```text
numerator1 = L × 2^96
```

and:

```text
numerator2 = √Pᵦ - √Pₐ
```

So the important pieces are:

```text
Liquidity
    ×
sqrt-price distance
```

The remaining part of the formula will divide by the two sqrt prices.

---

# 🛡️ Next Line

```solidity
require(sqrtRatioAX96 > 0);
```

Remember:

```text
A = lower sqrt price
```

So this requires:

```text
lower sqrt price > 0
```

Why?

Because the amount0 formula contains:

```text
1 / √Pₐ
```

Therefore `√Pₐ` cannot be zero.

If:

```text
sqrtRatioAX96 = 0
```

we would eventually be dividing by zero.

So the function stops immediately:

```text
sqrtRatioAX96 = 0
        ↓
      revert
```

---

# 🎯 Now The Main Return

```solidity
return roundUp
    ? UnsafeMath.divRoundingUp(
        FullMath.mulDivRoundingUp(
            numerator1,
            numerator2,
            sqrtRatioBX96
        ),
        sqrtRatioAX96
    )
    : FullMath.mulDiv(
        numerator1,
        numerator2,
        sqrtRatioBX96
    ) / sqrtRatioAX96;
```

Again, this is a ternary operator.

It means:

```text
if roundUp == true
    use the first calculation

else
    use the second calculation
```

So there are two versions:

```text
roundUp = true
    ↓
calculate amount0 rounded UP

roundUp = false
    ↓
calculate amount0 rounded DOWN
```

---

# 🔼 `roundUp == true`

The code is:

```solidity
UnsafeMath.divRoundingUp(
    FullMath.mulDivRoundingUp(
        numerator1,
        numerator2,
        sqrtRatioBX96
    ),
    sqrtRatioAX96
)
```

Let's read it from the inside outward.

First:

```solidity
FullMath.mulDivRoundingUp(
    numerator1,
    numerator2,
    sqrtRatioBX96
)
```

Conceptually this calculates:

```text
(numerator1 × numerator2) / sqrtRatioBX96
```

and rounds that intermediate result **UP**.

Then:

```solidity
UnsafeMath.divRoundingUp(
    intermediateResult,
    sqrtRatioAX96
)
```

divides by the lower sqrt price and rounds that division **UP** as well.

So the entire calculation is deliberately constructed to return a token0 amount that is **rounded up**.

---

# 🧮 Why Two Rounding-Up Operations?

This is important.

The mathematical formula is:

```text
amount0
=
(L × 2^96 × (√Pᵦ - √Pₐ))
────────────────────────────
      √Pᵦ × √Pₐ
```

The code splits this into:

```text
((L × 2^96 × (√Pᵦ - √Pₐ)) / √Pᵦ)
/
√Pₐ
```

So there are effectively two divisions.

The `roundUp` branch ensures the calculation does not underestimate the required token0 amount.

For example, if the exact required amount were:

```text
100.2 token0
```

then:

```text
round DOWN → 100
round UP   → 101
```

If the function is being used in a context where the amount must be sufficient, returning `100` would be too little.

Returning `101` ensures the required amount is covered.

---

# 🔽 `roundUp == false`

The other branch is:

```solidity
FullMath.mulDiv(
    numerator1,
    numerator2,
    sqrtRatioBX96
) / sqrtRatioAX96
```

Conceptually:

```text
(numerator1 × numerator2)
────────────────────────
       sqrtRatioB
```

and then:

```text
result / sqrtRatioA
```

The operations use normal integer division, so the result is rounded **DOWN**.

Therefore:

```text
roundUp = false
    ↓
amount0 is rounded DOWN
```

---

# 💰 When Is `roundUp = false` Used?

This is an important practical case.

`roundUp = false` is used when the token0 amount is being calculated as an **output amount**.

For example, in `computeSwapStep()`:

```solidity
amountOut = max && !exactIn
    ? amountOut
    : SqrtPriceMath.getAmount0Delta(
        sqrtRatioCurrentX96,
        sqrtRatioNextX96,
        liquidity,
        false
    );
```

Here:

```text
roundUp = false
        ↓
token0 amount is rounded DOWN
        ↓
token0 is OUTPUT
```

Why round the output DOWN?

Because the protocol should not give the trader more token0 than the precise mathematical calculation allows.

If the exact amount were:

```text
100.7 token0
```

then:

```text
round DOWN → 100
round UP   → 101
```

Giving `101` would give the trader extra token0 that does not come from the exact liquidity calculation.

So:

> **Output amounts are rounded DOWN.**

---

# 🧠 The General Uniswap V3 Rule

For these unsigned token-delta calculations:

```text
INPUT amount
    ↓
round UP
```

because the pool must receive enough.

And:

```text
OUTPUT amount
    ↓
round DOWN
```

because the pool must not send extra.

So when you see:

```solidity
getAmount0Delta(..., true)
```

think:

> **Token0 amount needs to be rounded UP.**

And when you see:

```solidity
getAmount0Delta(..., false)
```

think:

> **Token0 amount is being rounded DOWN, commonly because it is an output amount.**

---

# 🧠 Why Is `FullMath` Needed?

Look at:

```solidity
FullMath.mulDiv(...)
```

The mathematical operation contains:

```text
numerator1 × numerator2
```

That intermediate multiplication can exceed 256 bits even when the final result fits.

This is the same **phantom overflow** problem we studied in `FullMath`.

So instead of doing:

```solidity
numerator1 * numerator2 / sqrtRatioBX96
```

directly, Uniswap uses:

```solidity
FullMath.mulDiv(...)
```

to calculate:

```text
numerator1 × numerator2 ÷ sqrtRatioBX96
```

without losing precision from an overflowing intermediate multiplication.

# 🎯 Final Mental Model

Remember the function as:

> **`getAmount0Delta()` converts a sqrt-price movement into the corresponding token0 amount for a given liquidity.**

The formula is:

```text
amount0 = L × (1 / √Pₗₒw - 1 / √Pₕᵢgh)
```

The function first guarantees:

```text
A = lower sqrt price
B = higher sqrt price
```

Then:

```text
numerator1 = L × 2^96
numerator2 = B - A
```

Then it calculates:

```text
(L × 2^96 × (B - A))
──────────────────────
        B × A
```

Finally:

```text
roundUp = true
    ↓
amount0 rounded UP

roundUp = false
    ↓
amount0 rounded DOWN
```

The most important thing:

> **This function goes in the opposite direction from `getNextSqrtPriceFromAmount0RoundingUp()`: that function starts with a token0 amount and finds the next sqrt price; `getAmount0Delta()` starts with two sqrt prices and finds the token0 amount between them.**
