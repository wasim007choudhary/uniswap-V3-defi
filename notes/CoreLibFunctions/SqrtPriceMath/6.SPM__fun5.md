# 🧮 `getAmount0Delta()` Dissection

```solidity
function getAmount0Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
    internal
    pure
    returns (uint256 amount0)
{
    if (sqrtRatioAX96 > sqrtRatioBX96)
        (sqrtRatioAX96, sqrtRatioBX96) = (sqrtRatioBX96, sqrtRatioAX96);

    uint256 numerator1 = uint256(liquidity) << FixedPoint96.RESOLUTION;
    uint256 numerator2 = sqrtRatioBX96 - sqrtRatioAX96;

    require(sqrtRatioAX96 > 0);

    return roundUp
        ? UnsafeMath.divRoundingUp(
            FullMath.mulDivRoundingUp(
                numerator1,
                numerator2,
                sqrtRatioBX96
            ),
            sqrtRatioAX96
        )
        : FullMath.mulDiv(
            numerator1,
            numerator2,
            sqrtRatioBX96
        ) / sqrtRatioAX96;
}
```

---

# 🎯 Purpose

This function calculates the amount of **token0** corresponding to a movement between two sqrt prices for a given amount of liquidity.

The previous functions worked in the opposite direction.

```text
Token amount
    ↓
calculate price movement
    ↓
next sqrt price
```

But this function does:

```text
Current sqrt price
        +
Next/target sqrt price
        +
Liquidity
        ↓
calculate token0 amount
```

So it answers:

> **"How much token0 corresponds to moving the price between these two sqrt prices with this amount of liquidity?"**

---

# 🧮 The Mathematical Formula

The underlying formula is:

```text
amount0 = L × (1 / √Pₐ - 1 / √Pᵦ)
```

where:

```text
Pₐ = lower price
Pᵦ = upper price
```

Equivalently:

```text
amount0 =
L × (√Pᵦ - √Pₐ)
──────────────────
    √Pᵦ × √Pₐ
```

This is why the function needs **two sqrt prices**.

It is measuring the amount of token0 represented by the price movement between them.

---

# `sqrtRatioAX96`

```solidity
uint160 sqrtRatioAX96,
```

This is one of the two sqrt-price boundaries.

It does **not necessarily mean "lower" just because it is called A**.

The function itself handles either ordering.

That becomes important in the very first line:

```solidity
if (sqrtRatioAX96 > sqrtRatioBX96)
    (sqrtRatioAX96, sqrtRatioBX96) =
        (sqrtRatioBX96, sqrtRatioAX96);
```

After that line executes:

```text
sqrtRatioAX96 = LOWER sqrt price
sqrtRatioBX96 = HIGHER sqrt price
```

So from that point onward, we can safely think:

```text
A = lower
B = upper
```

---

# `sqrtRatioBX96`

```solidity
uint160 sqrtRatioBX96,
```

This is the second sqrt-price boundary.

Again, before normalization it could be either higher or lower.

After the first `if`:

```text
A = lower sqrt price
B = higher sqrt price
```

---

# `liquidity`

```solidity
uint128 liquidity,
```

This is the liquidity associated with the price interval.

The amount of token0 required for a given price movement depends on liquidity.

The relationship is:

```text
more liquidity
    ↓
more token0 required

less liquidity
    ↓
less token0 required
```

So `liquidity` is part of the amount0 calculation.

---

# `roundUp`

```solidity
bool roundUp
```

This tells the function how to round the final token0 amount.

```text
roundUp = true
    ↓
round the token0 amount UP

roundUp = false
    ↓
round the token0 amount DOWN
```

This matters because Solidity works with integers.

The exact mathematical token amount may contain a fractional part, but the contract must return an integer number of wei.

So Uniswap must deliberately choose a rounding direction.

```solidity
internal
```

It is not directly callable by an external user.

It accepts:


```text

    ×
```

Remember:


```text
lower sqrt price > 0
```

Because the amount0 formula contains:


Therefore `√Pₐ` cannot be zero.

If:


# 🎯 Now The Main Return

```solidity
return roundUp
    ? UnsafeMath.divRoundingUp(
        FullMath.mulDivRoundingUp(
            numerator1,
            numerator2,
            sqrtRatioBX96
        ),
        sqrtRatioAX96
    )
    : FullMath.mulDiv(
        numerator1,
        numerator2,
        sqrtRatioBX96
    ) / sqrtRatioAX96;
```

Again, this is a ternary operator.

It means:

```text
if roundUp == true
    use the first calculation

else
    use the second calculation
```

So there are two versions:

```text
roundUp = true
    ↓
calculate amount0 rounded UP

roundUp = false
    ↓
calculate amount0 rounded DOWN
```

---

# 🔼 `roundUp == true`

The code is:

```solidity
UnsafeMath.divRoundingUp(
    FullMath.mulDivRoundingUp(
        numerator1,
        numerator2,
        sqrtRatioBX96
    ),
    sqrtRatioAX96
)
```

Let's read it from the inside outward.

First:

```solidity
FullMath.mulDivRoundingUp(
    numerator1,
    numerator2,
    sqrtRatioBX96
)
```

Conceptually this calculates:

```text
(numerator1 × numerator2) / sqrtRatioBX96
```

and rounds that intermediate result **UP**.

Then:

```solidity
UnsafeMath.divRoundingUp(
    intermediateResult,
    sqrtRatioAX96
)
```

divides by the lower sqrt price and rounds that division **UP** as well.

So the entire calculation is deliberately constructed to return a token0 amount that is **rounded up**.

---

# 🧮 Why Two Rounding-Up Operations?

This is important.

The mathematical formula is:

```text
amount0
=
(L × 2^96 × (√Pᵦ - √Pₐ))
────────────────────────────
      √Pᵦ × √Pₐ
```

The code splits this into:

```text
((L × 2^96 × (√Pᵦ - √Pₐ)) / √Pᵦ)
/
√Pₐ
```

So there are effectively two divisions.

The `roundUp` branch ensures the calculation does not underestimate the required token0 amount.

For example, if the exact required amount were:

```text
100.2 token0
```

then:

```text
round DOWN → 100
round UP   → 101
```

If the function is being used in a context where the amount must be sufficient, returning `100` would be too little.

Returning `101` ensures the required amount is covered.

---

# 🔽 `roundUp == false`

The other branch is:

```solidity
FullMath.mulDiv(
    numerator1,
    numerator2,
    sqrtRatioBX96
) / sqrtRatioAX96
```

Conceptually:

```text
(numerator1 × numerator2)
────────────────────────
       sqrtRatioB
```

and then:

```text
result / sqrtRatioA
```

The operations use normal integer division, so the result is rounded **DOWN**.

Therefore:

```text
roundUp = false
    ↓
amount0 is rounded DOWN
```

---

# 💰 When Is `roundUp = false` Used?

This is an important practical case.

`roundUp = false` is used when the token0 amount is being calculated as an **output amount**.

For example, in `computeSwapStep()`:

```solidity
amountOut = max && !exactIn
    ? amountOut
    : SqrtPriceMath.getAmount0Delta(
        sqrtRatioCurrentX96,
        sqrtRatioNextX96,
        liquidity,
        false
    );
```

Here:

```text
roundUp = false
        ↓
token0 amount is rounded DOWN
        ↓
token0 is OUTPUT
```

Why round the output DOWN?

Because the protocol should not give the trader more token0 than the precise mathematical calculation allows.

If the exact amount were:

```text
100.7 token0
```

then:

```text
round DOWN → 100
round UP   → 101
```

Giving `101` would give the trader extra token0 that does not come from the exact liquidity calculation.

So:

> **Output amounts are rounded DOWN.**

---

# 🧠 The General Uniswap V3 Rule

For these unsigned token-delta calculations:

```text
INPUT amount
    ↓
round UP
```

because the pool must receive enough.

And:

```text
OUTPUT amount
    ↓
round DOWN
```

because the pool must not send extra.

So when you see:

```solidity
getAmount0Delta(..., true)
```

think:

> **Token0 amount needs to be rounded UP.**

And when you see:

```solidity
getAmount0Delta(..., false)
```

think:

> **Token0 amount is being rounded DOWN, commonly because it is an output amount.**

---

# 🧠 Why Is `FullMath` Needed?

Look at:

```solidity
FullMath.mulDiv(...)
```

The mathematical operation contains:

```text
numerator1 × numerator2
```

That intermediate multiplication can exceed 256 bits even when the final result fits.

This is the same **phantom overflow** problem we studied in `FullMath`.

So instead of doing:

```solidity
numerator1 * numerator2 / sqrtRatioBX96
```

directly, Uniswap uses:

```solidity
FullMath.mulDiv(...)
```

to calculate:

```text
numerator1 × numerator2 ÷ sqrtRatioBX96
```

without losing precision from an overflowing intermediate multiplication.

# 🧠 First: The Formula Is Correct

For `amount0`, the mathematical formula is:

\[
amount0 =
L \times
\frac{\sqrt{P_{upper}}-\sqrt{P_{lower}}}
{\sqrt{P_{upper}}\times\sqrt{P_{lower}}}
\]

So yes, we can write it as:

```text
                 L × (upper - lower)
amount0 = ─────────────────────────────
                  upper × lower
```

This algebra is completely correct.

The important part is that `upper` and `lower` here are the **encoded Q64.96 sqrt prices** used by Uniswap.

---

# 🔥 So Why Not Calculate `upper × lower` First?

This is the interesting part.

Each sqrt price is:

```solidity
uint160
```

So:

```text
upper = uint160
lower = uint160
```

A multiplication of two 160-bit numbers can require:

```text
160 + 160 = 320 bits
```

to represent the complete result.

But a Solidity `uint256` can only hold:

```text
256 bits
```

So this:

```solidity
upper * lower
```

can potentially require **320 bits**.

Therefore, your idea would require something like a 512-bit multiplication to safely create:

```text
upper × lower
```

---

# 🤔 But What If We Use 512-bit Multiplication?

This is where your idea gets very close to the real implementation.

You absolutely **can mathematically** think about doing:

```text
denominator = upper × lower
```

with a wide multiplication.

The problem is what happens next.

You would have:

```text
numerator:
    L × (upper - lower)

denominator:
    upper × lower
```

The numerator can also be larger than 256 bits:

```text
L                  → up to 128 bits
upper - lower      → up to 160 bits

128 + 160 = 288 bits
```

So your proposed calculation becomes conceptually:

```text
              up to 288-bit numerator
amount0 = ───────────────────────────────
              up to 320-bit denominator
```

You would then need a division routine capable of dealing with a **wide numerator and a wide denominator**.

That is no longer the normal:

```solidity
FullMath.mulDiv(a, b, denominator)
```

interface.

`FullMath.mulDiv()` accepts:

```solidity
mulDiv(
    uint256 a,
    uint256 b,
    uint256 denominator
)
```

So the denominator itself must fit inside a `uint256`.

Your:

```text
upper × lower
```

does not necessarily fit.

---

# 💡 This Is Why Uniswap Does Something Clever

Instead of ever constructing:

```text
upper × lower
```

as one giant denominator, Uniswap **splits the division**.

The mathematical expression is:

```text
                 L × 2^96 × (upper - lower)
amount0 = ─────────────────────────────────────
                         upper × lower
```

Uniswap can calculate it as:

```text
                 L × 2^96 × (upper - lower)
                 ───────────────────────────
                              upper

                              ↓

                           / lower
```

In code:

```solidity
FullMath.mulDiv(
    numerator1,
    numerator2,
    sqrtRatioBX96
) / sqrtRatioAX96;
```

where:

```solidity
numerator1 = uint256(liquidity) << 96;
numerator2 = sqrtRatioBX96 - sqrtRatioAX96;
```

So conceptually:

```text
                L × 2^96 × (upper - lower)
                ───────────────────────────
                            upper
                              ↓
                           / lower
```

---

# 🚀 Why Is This Better?

Because instead of creating:

```text
upper × lower
```

which could require:

```text
320 bits
```

Uniswap deals with:

```text
upper
```

and:

```text
lower
```

**separately**.

Each one individually is only:

```text
uint160
```

and therefore fits safely inside:

```text
uint256
```

So Uniswap never needs a 320-bit denominator.

Uniswap creates:


as one number.

**That's essentially the trick Uniswap is using.**

---

# 🎯 The Main Point

Your algebra was **correct**:

```text
                 L × (upper - lower)
amount0 = ─────────────────────────────
                  upper × lower
```

The reason Uniswap doesn't simply construct:

```text
upper × lower
```

is not because the mathematics is wrong.

It is because:

```text
upper = uint160
lower = uint160
```

so:

```text
upper × lower
```

can require:

```text
320 bits
```

A `uint256` denominator cannot hold that in the general case.

Instead, Uniswap transforms the expression so it can work with the two denominator values separately:

```text
                 L × 2^96 × (upper - lower)
                 ───────────────────────────
                              upper
                              ↓
                           / lower
```

This lets `FullMath.mulDiv()` handle the dangerous **numerator multiplication** with its 512-bit intermediate while keeping each denominator individually within `uint256`.

```text
                 ↓

        denominator may need
             320 bits ❌

                 ↓

                 ↓

                 ↓
               ✅
```

> **So the clever part is not the algebra itself. The clever part is choosing an algebraic form that keeps every denominator inside `uint256` while letting `FullMath` handle the potentially oversized numerator multiplication.**

The calculation is effectively:

```text
numerator1 × numerator2
───────────────────────
       upper
```

and then:

```text
result
──────
 lower
```

The code is:

```solidity

        numerator1,
```

The first operation:

```solidity
FullMath.mulDivRoundingUp(...)
```

rounds the first division **UP**.

Then:

```solidity
UnsafeMath.divRoundingUp(...)
```

rounds the second division **UP**.

# 🤔 Isn't That Bad for the Trader?

It can mean the final integer amount is slightly higher than the exact mathematical amount.

For example, if the **final exact amount** is:

```text
100.7
```

then a final round-up gives:

```text
100.7 → 101
```

So yes, the trader could be dealing with:

```text
101
```

instead of the mathematical:

```text
100.7
```

But this is intentional.

The important question is:

> **What does `roundUp == true` mean?**

It means:

> Do not underestimate the amount.

---

# 📥 Why Is Rounding UP Used for an Amount Required?

Suppose the exact amount required is:

```text
100.7 token0
```

But token amounts are integers.

We cannot use:

```text
100.7
```

We have to choose:

```text
100
```

or:

```text
101
```

If we choose:

```text
100
```

then the pool receives **less than the mathematically required amount**.

That is unsafe.

So the safe direction is:

```text
100.7 → 101
```

The pool gets enough.

---

# 📤 What Happens When the Amount Is an Output?

For an output amount, the direction is reversed.

Suppose the mathematical output is:

```text
100.7 token0
```

The pool should not give:

```text
101
```

because that would give the trader more than the calculated amount.

So:

```text
100.7 → 100
```

The output is rounded **DOWN**.

Therefore:

```text
INPUT  → round UP
OUTPUT → round DOWN
```

---

# 🔥 So Does Uniswap Have the Upper Hand?

**Yes, in the rounding sense.**

The rounding is deliberately conservative toward the pool.

```text
INPUT:

100.7 → 101
       ↑
Pool receives enough
Trader may provide a tiny bit more
```

and:

```text
OUTPUT:

100.7 → 100
       ↓
Pool does not give extra
Trader receives a tiny bit less
```

So:

> **In both directions, the rounding protects the pool from losing value because of integer truncation.**

It is not doing:

```text

```

It is doing:

```text

```

# 🤔 Why Not Just Round Once at the Very End?

Because the calculation is implemented as two divisions:

```text
                 numerator1 × numerator2
                 ────────────────────────
                         upper
                           ↓
                        / lower
```

The first division has to produce an integer before Solidity can perform the second integer division.

So Uniswap uses the round-up version for the intermediate calculation as well.

The goal is to preserve the conservative direction rather than allowing the first integer truncation to underestimate the amount.
