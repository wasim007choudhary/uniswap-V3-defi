# 💰 `getAmount0Delta()` — Signed Liquidity Overload

```solidity
function getAmount0Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    int128 liquidity
)
    internal
    pure
    returns (int256 amount0)
{
    return liquidity < 0
        ? -getAmount0Delta(
            sqrtRatioAX96,
            sqrtRatioBX96,
            uint128(-liquidity),
            false
        ).toInt256()
        : getAmount0Delta(
            sqrtRatioAX96,
            sqrtRatioBX96,
            uint128(liquidity),
            true
        ).toInt256();
}
```

---

## 🎯 What Is This Function Doing?

This is the **signed-liquidity overload** of `getAmount0Delta()`.

The previous `getAmount0Delta()` function accepted:

```solidity
uint128 liquidity
```

So liquidity could only be positive.

This version accepts:

```solidity
int128 liquidity
```

So liquidity can be:

```text
+L
-L
```

The important difference is that the **sign now carries direction**.

```text
+ liquidity
    ↓
liquidity is being added to the active range
    ↓
positive token0 delta


- liquidity
    ↓
liquidity is being removed from the active range
    ↓
negative token0 delta
```

So this function is basically saying:

> "Calculate the normal token0 amount, but preserve the sign of the liquidity."

---

# 💰 Think About It From the Pool's Money Point of View

Suppose an LP position has:

```text
liquidity = +100
```

That means this liquidity is being **added into the active liquidity calculation**.

The function therefore calculates a positive token0 delta:

```text
+amount0
```

Now suppose:

```text
liquidity = -100
```

That means this liquidity is being **removed from the active liquidity calculation**.

The corresponding token0 delta becomes:

```text
-amount0
```

So:

```text
+liquidity → +token0 delta

-liquidity → -token0 delta
```

### ⚠️ Important

The negative sign does **not** mean that "negative tokens" exist.

It means:

> **The token0 movement is in the opposite direction.**

The signed result allows the caller to represent the direction of the token0 delta.

---

# 1. Function Parameters

### `sqrtRatioAX96`

One of the two sqrt prices.

### `sqrtRatioBX96`

The other sqrt price.

The underlying unsigned `getAmount0Delta()` function normalizes them internally so the lower sqrt price comes first.

### `liquidity`

```solidity
int128 liquidity
```

Unlike the previous function:

```solidity
uint128 liquidity
```

this one can be:

```text
positive
or
negative
```

### `amount0`

```solidity
returns (int256 amount0)
```

The result is `int256` because the result may need to represent:

```text
+amount0
```

or:

```text
-amount0
```

---

# 2. The Main Decision

The function starts with:

```solidity
liquidity < 0
```

inside a ternary:

```solidity
return liquidity < 0
    ? ...
    : ...;
```

The ternary operator means:

```text
condition ? valueIfTrue : valueIfFalse
```

So:

```text
liquidity < 0
```

asks:

> "Is this liquidity negative?"

If **YES**:

```text
→ negative-liquidity branch
```

If **NO**:

```text
→ positive-liquidity branch
```

---

# 3. Negative Liquidity = Remove the Liquidity Contribution

Look at the negative branch:

```solidity
-getAmount0Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
).toInt256()
```

Suppose:

```text
liquidity = -100
```

The first thing we do is:

```solidity
-liquidity
```

which gives:

```text
-(-100) = +100
```

So:

```solidity
uint128(-liquidity)
```

becomes:

```text
100
```

Now we can pass that value into the original unsigned function because that function expects:

```solidity
uint128 liquidity
```

---

# 4. Why Remove the Negative Sign Temporarily?

The original `getAmount0Delta()` function only knows how to calculate the **magnitude** of the token0 amount.

It accepts:

```solidity
uint128 liquidity
```

Therefore it needs a positive liquidity value.

So if we have:

```text
liquidity = -100
```

we temporarily turn it into:

```text
100
```

and calculate:

```text
amount0 = 100
```

Then we put the negative sign back:

```text
-100
```

So the flow is:

```text
-100 liquidity
      ↓
remove the sign
      ↓
+100 liquidity
      ↓
calculate amount0
      ↓
+amount0
      ↓
put the negative sign back
      ↓
-amount0
```

---

# 5. Why Does Negative Liquidity Use `roundUp = false`?

This is an important part.

The negative branch calls:

```solidity
getAmount0Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
)
```

Notice:

```solidity
false
```

means:

```text
roundUp = false
```

Therefore the unsigned amount is rounded **DOWN**.

Suppose the exact mathematical amount is:

```text
100.7 token0
```

The unsigned calculation gives:

```text
100.7
  ↓ round DOWN
100
```

Then the outer `-` gives:

```text
-100
```

So:

```text
100.7
   ↓
100
   ↓ negate
-100
```

### Why not round up?

Because:

```text
-(100.7 rounded UP)
=
-101
```

That would make the negative delta larger in magnitude than necessary.

Instead:

```text
-(100.7 rounded DOWN)
=
-100
```

This preserves the intended signed rounding behavior.

---

# 6. Convert the Result to `int256`

The unsigned `getAmount0Delta()` returns:

```solidity
uint256
```

But this function needs to return:

```solidity
int256
```

because the final result can be negative.

Therefore:

```solidity
.toInt256()
```

converts:

```text
uint256
    ↓
int256
```

For example:

```text
100 uint256
    ↓
100 int256
```

Then the outer `-` can make it:

```text
-100 int256
```

---

# 7. Finally Put the Negative Sign Back

The negative branch starts with:

```solidity
-
```

So after calculating the positive magnitude:

```text
+100
```

the function returns:

```text
-100
```

The complete negative branch is therefore:

```text
liquidity = -100
      ↓
-liquidity
      ↓
100
      ↓
uint128(100)
      ↓
getAmount0Delta(..., false)
      ↓
100
      ↓
.toInt256()
      ↓
100
      ↓
-
      ↓
-100
```

---

# 8. Positive Liquidity = Add the Liquidity Contribution

Now look at the other branch:

```solidity
getAmount0Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(liquidity),
    true
).toInt256()
```

Suppose:

```text
liquidity = +100
```

We simply convert it:

```solidity
uint128(liquidity)
```

and pass it into the unsigned function.

But this time:

```solidity
true
```

means:

```text
roundUp = true
```

So the amount is rounded **UP**.

Suppose the exact amount is:

```text
100.7 token0
```

Then:

```text
100.7
   ↓ round UP
101
```

The result becomes:

```text
+101
```

---

# 9. Why Does Positive Liquidity Use `roundUp = true`?

The positive branch represents a positive token0 delta.

So:

```text
exact amount = 100.7
```

becomes:

```text
+101
```

rather than:

```text
+100
```

The function therefore follows:

```text
positive liquidity
    ↓
positive amount
    ↓
round UP
```

while negative liquidity follows:

```text
negative liquidity
    ↓
negative amount
    ↓
round DOWN before applying the negative sign
```

# 💰 10. Connect This to LP / Pool Money Flow

This is the most important intuition.

An LP position has liquidity over a price range.

When that liquidity is being **added to the active liquidity**, its signed liquidity contribution is:

```text
+L
```

When that liquidity contribution is being **removed from the active liquidity**, its signed liquidity contribution is:

```text
-L
```

The signed `getAmount0Delta()` overload allows the corresponding token0 delta to carry that same direction.

So conceptually:

```text
+L
 ↓
liquidity contribution enters
 ↓
+amount0


-L
 ↓
liquidity contribution leaves
 ↓
-amount0
```

The negative result is therefore a **directional accounting value**.

It does not mean the pool literally stores a negative balance of token0.

Suppose an LP position has:

```text
L = 1,000
```

and the price interval corresponds to an exact token0 amount of:

```text
250.7 token0
```

### Positive liquidity side

```text
+L
 ↓
+250.7
 ↓ round UP
+251
```

So the function returns:

```text
+251
```

### Negative liquidity side

```text
-L
 ↓
-250.7
 ↓ round DOWN
-250
```

So the function returns:

```text
-250
```

The sign tells us which direction the liquidity contribution is going.

# 12. Why Does It Call Another Function With the Same Name?

At first this can look strange:

```solidity
getAmount0Delta(...)
```

is being called from inside another:

```solidity
getAmount0Delta(...)
```

Is it recursively calling itself forever?

**No.**

These are two overloaded functions.

We have one version:

```solidity
function getAmount0Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
```

and another:

```solidity
function getAmount0Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    int128 liquidity
)
```

The compiler selects the correct function based on the argument types.

When we write:

```solidity
getAmount0Delta(
    sqrtRatioAX96,
    sqrtRatioBX96,
    uint128(-liquidity),
    false
)
```

the arguments are:

```text
uint160
uint160
uint128
bool
```

Therefore Solidity selects:

```solidity
getAmount0Delta(
    uint160,
    uint160,
    uint128,
    bool
)
```

So the signed version is simply a **wrapper around the unsigned version**.

# 💡 Rounding Behavior

The important relationship is:

```text
liquidity > 0
    ↓
roundUp = true
    ↓
amount0 rounded UP
    ↓

```

while:

```text
liquidity < 0
    ↓
make liquidity positive
    ↓
roundUp = false
    ↓
amount0 rounded DOWN
    ↓
negate
    ↓
negative amount0
```

For example:

```text
Exact amount = 100.7
```

Positive:

```text
100.7
 ↓
101
 ↓
+101
```

Negative:

```text
100.7
 ↓
100
 ↓
-100
```

# 🔥 Final Mental Model

> **This overload exists because liquidity can be positive or negative. Positive liquidity produces a positive token0 delta; negative liquidity represents removal of the liquidity contribution, so the token0 delta is returned as negative.**

It does **not** introduce a new token0 formula.

It simply takes the existing unsigned `getAmount0Delta()` calculation and adds **direction through the sign of liquidity**.

```text
+ liquidity
    ↓
liquidity is being added to the active range
    ↓
calculate unsigned amount0
    ↓
round UP
    ↓
return +amount0
```

```text
- liquidity
    ↓
liquidity contribution is being removed
    ↓
temporarily remove the minus sign
    ↓
calculate unsigned amount0
    ↓
round DOWN
    ↓
convert to int256
    ↓
put minus sign back
    ↓
return -amount0
```

### 🧠 One-line memory trick

```text
Positive L → positive Δ0 → round UP

Negative L → negative Δ0 → round DOWN → negate
```

The **sign represents direction**, while the underlying unsigned function calculates the **magnitude** of the token0 delta.
