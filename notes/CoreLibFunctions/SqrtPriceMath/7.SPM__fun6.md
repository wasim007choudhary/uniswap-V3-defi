# 🔹 `getAmount1Delta()` — Full Dissection

Here is the function:

```solidity
function getAmount1Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
    internal
    pure
    returns (uint256 amount1)
{
    if (sqrtRatioAX96 > sqrtRatioBX96) {
        (sqrtRatioAX96, sqrtRatioBX96) =
            (sqrtRatioBX96, sqrtRatioAX96);
    }

    return roundUp
        ? FullMath.mulDivRoundingUp(
            liquidity,
            sqrtRatioBX96 - sqrtRatioAX96,
            FixedPointQ96.Q96
        )
        : FullMath.mulDiv(
            liquidity,
            sqrtRatioBX96 - sqrtRatioAX96,
            FixedPointQ96.Q96
        );
}
```

---

# 🎯 What Does This Function Do?

`getAmount1Delta()` answers a very simple question:

> **Given a price movement from one sqrt price to another, and given some liquidity, how much token1 corresponds to that movement?**

Its mathematical formula is:

\[
\boxed{
amount1 =
L \times
\frac{\sqrt{P_{upper}}-\sqrt{P_{lower}}}{Q96}
}
\]

Or simply:

```text
              L × (upper - lower)
amount1 = ─────────────────────────
                    Q96
```

So unlike `getAmount0Delta()`, there is **no multiplication of the two sqrt prices in the denominator**.

That makes the calculation much simpler.

---

# 1️⃣ Function Parameters

```solidity
function getAmount1Delta(
    uint160 sqrtRatioAX96,
    uint160 sqrtRatioBX96,
    uint128 liquidity,
    bool roundUp
)
```

### `sqrtRatioAX96`

One of the two sqrt prices.

It is stored as:

```text
sqrt(price) × 2^96
```

using Q64.96 fixed-point representation.

---

### `sqrtRatioBX96`

The other sqrt price.

It is also a Q64.96 encoded sqrt price.

At this point, **A is not necessarily lower than B**.

For example:

```text
A = 500
B = 300
```

is perfectly possible when entering the function.

---

### `liquidity`

The liquidity associated with this price movement.

It is:

```solidity
uint128
```

and represents the amount of active liquidity used in this calculation.

More liquidity means:

```text
same price movement
        ↓
more token1 amount
```

---

### `roundUp`

Controls the direction of integer rounding:

```text
true  → round UP
false → round DOWN
```

This is important because Solidity integer arithmetic cannot keep fractional token amounts.

---

# 2️⃣ Normalize A and B

```solidity
if (sqrtRatioAX96 > sqrtRatioBX96) {
    (sqrtRatioAX96, sqrtRatioBX96) =
        (sqrtRatioBX96, sqrtRatioAX96);
}
```

This is the same normalization idea we saw in `getAmount0Delta()`.

The function wants:

```text
A = lower sqrt price
B = upper sqrt price
```

So if:

```text
A > B
```

we swap them.

### Example

Before:

```text
A = 500
B = 300
```

Since:

```text
500 > 300
```

swap:

```text
A = 300
B = 500
```

Now:

```text
A = lower
B = upper
```

From this point onward:

```text
sqrtRatioAX96 <= sqrtRatioBX96
```

Therefore:

```solidity
sqrtRatioBX96 - sqrtRatioAX96
```

is guaranteed to be non-negative.

---

# 🧠 Why Does the Function Normalize Them?

Because the formula is:

\[
L\times
\frac{\sqrt{P_{upper}}-\sqrt{P_{lower}}}{Q96}
\]

We want:

```text
upper - lower
```

not:

```text
lower - upper
```

If we allowed:

```text
A = 500
B = 300
```

then:

```text
B - A
=
300 - 500
```

would be negative.

But this function returns:

```solidity
uint256 amount1
```

so it cannot represent a negative amount.

Therefore the function normalizes the two prices first.

---

# 3️⃣ Calculate the Sqrt-Price Difference

The important expression is:

```solidity
sqrtRatioBX96 - sqrtRatioAX96
```

After normalization:

```text
B = upper
A = lower
```

so:

```text
B - A
```

is simply:

```text
upper sqrt price - lower sqrt price
```

We can call this:

```text
Δ√P
```

So the formula becomes:

```text
amount1 = L × Δ√P / Q96
```

---

# 4️⃣ Why Do We Divide by `Q96`?

The sqrt prices are not stored as normal decimal numbers.

They are encoded in Q64.96.

That means:

```text
encoded sqrt price
=
actual sqrt price × 2^96
```

And:

```solidity
FixedPointQ96.Q96
```

is:

```text
2^96
```

Therefore:

```solidity
sqrtRatioBX96 - sqrtRatioAX96
```

is also still scaled by:

```text
2^96
```

So we divide by:

```solidity
FixedPointQ96.Q96
```

to remove that scaling.

Conceptually:

```text
encoded difference
       ↓
     / 2^96
       ↓
actual sqrt-price difference
```

---

# 5️⃣ The `roundUp` Ternary

Now we reach the main calculation:

```solidity
return roundUp
    ? FullMath.mulDivRoundingUp(
        liquidity,
        sqrtRatioBX96 - sqrtRatioAX96,
        FixedPointQ96.Q96
    )
    : FullMath.mulDiv(
        liquidity,
        sqrtRatioBX96 - sqrtRatioAX96,
        FixedPointQ96.Q96
    );
```

This simply means:

```text
if roundUp == true
    use mulDivRoundingUp
else
    use mulDiv
```

---

# 6️⃣ `roundUp == true`

When:

```solidity
roundUp == true
```

we use:

```solidity
FullMath.mulDivRoundingUp(
    liquidity,
    sqrtRatioBX96 - sqrtRatioAX96,
    FixedPointQ96.Q96
)
```

Mathematically:

\[
\left\lceil
\frac{L\times(B-A)}{Q96}
\right\rceil
\]

So:

```text
L × (B - A)
────────────────
      Q96
```

is calculated and rounded **UP**.

### Example

If the exact mathematical result is:

```text
100.7
```

then:

```text
100.7 → 101
```

---

# 7️⃣ Why Round Up?

When the calculation needs an amount that must **not be underestimated**, rounding up is the safe direction.

```text
Exact amount = 100.7

Round DOWN:
100 ❌
```

That would underestimate the amount.

Instead:

```text
Round UP:
101 ✅
```

Now the calculated amount is guaranteed to be at least the mathematical amount.

---

# 8️⃣ `roundUp == false`

If:

```solidity
roundUp == false
```

we use:

```solidity
FullMath.mulDiv(
    liquidity,
    sqrtRatioBX96 - sqrtRatioAX96,
    FixedPointQ96.Q96
)
```

Mathematically:

\[
\left\lfloor
\frac{L\times(B-A)}{Q96}
\right\rfloor
\]

So the result is rounded **DOWN**.

Example:

```text
Exact amount = 100.7

100.7 → 100
```

This prevents the calculated amount from being overestimated.

---

# 9️⃣ Why `FullMath.mulDiv()` Instead of `liquidity * difference / Q96`?

We could mathematically write:

```solidity
liquidity
    * (sqrtRatioBX96 - sqrtRatioAX96)
    / FixedPointQ96.Q96
```

The mathematics is correct.

But the multiplication:

```text
liquidity × (B - A)
```

can require more than 256 bits.

Remember:

```text
liquidity → uint128
B - A     → potentially up to 160 bits
```

So the intermediate multiplication can potentially require:

```text
128 + 160 = 288 bits
```

A normal `uint256` cannot hold a 288-bit intermediate.

`FullMath.mulDiv()` solves this by handling the multiplication with its wider internal arithmetic and then dividing.

Conceptually:

```text
L × (B - A)
       ↓
full-precision intermediate
       ↓
     / Q96
       ↓
final uint256 amount
```

---

# 🔥 Why This Is Simpler Than `getAmount0Delta()`

This is an important difference.

For token0:

```text
                 L × (upper - lower)
amount0 = ─────────────────────────────
                  upper × lower
```

There are **two sqrt prices in the denominator**.

That creates the possibility of:

```text
upper × lower
```

requiring up to:

```text
320 bits
```

So `getAmount0Delta()` uses the clever split:

```text
             L × 2^96 × (upper - lower)
             ───────────────────────────
                          upper
                            ↓
                         / lower
```

But token1 is much simpler:

```text
              L × (upper - lower)
amount1 = ─────────────────────────
                    Q96
```

There is no:

```text
upper × lower
```

denominator.

So we can directly use:

```solidity
FullMath.mulDiv(
    liquidity,
    sqrtRatioBX96 - sqrtRatioAX96,
    FixedPointQ96.Q96
)
```

# 🔄 Rounding Mental Model

For the `roundUp` parameter:

```text
roundUp = true
        ↓
FullMath.mulDivRoundingUp()
        ↓
result goes UP
        ↓
100.7 → 101
```

and:

```text
roundUp = false
        ↓
FullMath.mulDiv()
        ↓
result goes DOWN
        ↓
100.7 → 100
```

So:

```text
INPUT / REQUIRED AMOUNT
        ↓
     ROUND UP


OUTPUT / AMOUNT GIVEN
        ↓
    ROUND DOWN
```

The protocol uses the conservative direction so that:

```text
Input  → pool does not receive too little
Output → pool does not give too much
```

---

# 🧠 Double Rounding — Important Comparison With `getAmount0Delta()`

Unlike `getAmount0Delta(..., true)`, this function does **not** have two separate rounding operations.

Here we have only:

```solidity
FullMath.mulDivRoundingUp(...)
```

for the `roundUp == true` path.

There is only one division:

```text
L × (B - A)
────────────────
      Q96
```

So there is only one rounding decision.

The **double-rounding** situation we studied earlier belongs to the `amount0` calculation:

```solidity
UnsafeMath.divRoundingUp(
    FullMath.mulDivRoundingUp(
        numerator1,
        numerator2,
        sqrtRatioBX96
    ),
    sqrtRatioAX96
)
```

There, the calculation is split into two divisions, so both can round up.

For `amount1`, it is simply:

```solidity
FullMath.mulDivRoundingUp(
    liquidity,
    sqrtRatioBX96 - sqrtRatioAX96,
    FixedPointQ96.Q96
)
```

One multiplication + one division + one rounding direction.

# 💰 Does Rounding Give Uniswap a Tiny Advantage?

There can be tiny **rounding dust**.

For example:

```text
Exact mathematical amount = 100.7
Integer amount             = 101
Difference                 = 0.3
```

That difference is caused by integer arithmetic and conservative rounding.

It is **not an additional explicit protocol fee**.

The actual swap fee is handled separately through:

```text
feePips
```

So:

```text
rounding ≠ additional protocol fee
```

Instead:

```text
rounding = protection against precision loss
```

# 🔥 Uniswap Has the Upper Hand in Both Directions

The simple way to remember the rounding behavior is:

## 📥 Input / Amount Required

```text
100.7 → 101
       ↑
Pool receives enough
Trader may provide a tiny bit more
```

## 📤 Output / Amount Given

```text
100.7 → 100
       ↓
Pool does not give extra
Trader receives a tiny bit less
```

So:

```text
INPUT  → round UP
OUTPUT → round DOWN
```

> **In both directions, the rounding is conservative in favor of the pool.**

This gives the pool the **rounding safety advantage**.

Imagine the pool has a bucket.

```text
"You need exactly 100.7 tokens."
```

If the bucket **needs** tokens:

You don't want to give only:


If the bucket is **giving** tokens:


You don't want it to give:


So:

```text
Need tokens? → round UP
Give tokens? → round DOWN
```

# 🔑 Final Mental Model

> **`getAmount1Delta()` converts a movement between two sqrt prices into the corresponding amount of token1 for a given liquidity.**

The formula is:

\[
\boxed{
amount1 =
L\times
\frac{\sqrt{P_{upper}}-\sqrt{P_{lower}}}{Q96}
}
\]

The function first makes sure:

```text
A = lower
B = upper
```

Then calculates:

```text
B - A
```

Then:

```text
L × (B - A) / Q96
```

using `FullMath` so the multiplication does not lose precision through a 256-bit intermediate overflow.

Finally:

```text
roundUp == true  → round UP
roundUp == false → round DOWN
```

So the entire function is basically:

```text
Two sqrt prices
      ↓
Make A lower and B upper
      ↓
Find price difference
      ↓
Multiply by liquidity
      ↓
Remove Q96 scaling
      ↓
Round in the requested direction
      ↓
amount1
```
