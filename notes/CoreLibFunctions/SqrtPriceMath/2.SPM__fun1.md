# Uniswap V3 — SqrtPriceMath
## Function 1: `getNextSqrtPriceFromAmount0RoundingUp()`

```solidity
function getNextSqrtPriceFromAmount0RoundingUp(
    uint160 sqrtPX96,
    uint128 liquidity,
    uint256 amount,
    bool add
)
    internal
    pure
    returns (uint160)
```

---

## What this function does

This function calculates the **next square-root price** after token0 is added to or removed from the current V3 liquidity range.

It takes:

- `sqrtPX96` → current square-root price
- `liquidity` → active liquidity
- `amount` → amount of token0 being added or removed
- `add` → whether token0 is being added or removed

It returns:

- the new square-root price as a `uint160`

The function is specifically for **token0 movement**.

The important idea is:

> Token0 and token1 do not move the square-root price in the same mathematical way.

For token0, the formula is:

### Adding token0

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L + amount\sqrt{P}}
\]

### Removing token0

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L - amount\sqrt{P}}
\]

Where:

- `L` = liquidity
- `√P` = current square-root price
- `amount` = token0 amount

---

# 1. Zero amount

```solidity
if (amount == 0) return sqrtPX96;
```

This is the first shortcut.

If no token0 is added or removed:

```text
amount = 0
```

then the price does not move.

So:

```text
new price = current price
```

Therefore the function immediately returns:

```solidity
sqrtPX96
```

### Why return immediately?

There is no reason to perform any of the later multiplication, division, or rounding.

It is a **short circuit**:

```text
amount == 0
      ↓
nothing changes
      ↓
return current price
```

This is also a correctness guarantee. The function does not try to recreate the same price through integer arithmetic and rounding; it simply returns the exact existing representation.

---

# 2. Create `numerator1`

```solidity
uint256 numerator1 = uint256(liquidity) << FixedPoint96.RESOLUTION;
```

There are several things happening here.

## `liquidity` is `uint128`

The function receives:

```solidity
uint128 liquidity
```

but the calculations need a wider type.

So it is first converted:

```solidity
uint256(liquidity)
```

This is safe because every `uint128` value fits inside `uint256`.

Then:

```solidity
<< FixedPoint96.RESOLUTION
```

The resolution is:

```solidity
RESOLUTION = 96
```

Therefore:

```solidity
uint256(liquidity) << 96
```

A left shift by 96 bits is mathematically equivalent to multiplying by:

\[
2^{96}
\]

So conceptually:

```text
numerator1 = liquidity × 2^96
```

or:

```text
numerator1 = liquidity × Q96
```

because:

```text
Q96 = 2^96
```

---

## Important: `96` vs `2^96`

These are different things.

```text
96
```

is the **number of bits to shift**.

```text
2^96
```

is the **actual scaling value**.

Therefore:

```solidity
value << 96
```

means:

> Move the bits 96 positions to the left.

Mathematically:

```text
value << 96
=
value × 2^96
```

But:

```solidity
value << 2^96
```

would mean:

> Move the bits `2^96` positions to the left.

That is completely different.

So:

```text
RESOLUTION = 96
Q96        = 2^96
```

are deliberately separate constants.

---

# 3. The `add` branch

```solidity
if (add) {
```

If:

```solidity
add == true
```

token0 is being **added**.

For token0:

> Adding token0 moves the price DOWN.

The mathematical formula is:

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L + amount\sqrt{P}}
\]

The code now tries to calculate that efficiently.

---

# 4. Calculate `product`

```solidity
uint256 product;
```

A variable is created to hold:

```text
amount × sqrtPX96
```

Then:

```solidity
if ((product = amount * sqrtPX96) / amount == sqrtPX96) {
```

The multiplication happens here:

```solidity
product = amount * sqrtPX96;
```

---

# 5. Why divide the product back by `amount`?

This part:

```solidity
(product = amount * sqrtPX96) / amount == sqrtPX96
```

looks strange at first.

It is an **overflow detection technique from older Solidity versions**.

The idea is:

```text
amount × sqrtPX96
        ↓
    product
        ↓
product / amount
        ↓
should equal sqrtPX96
```

If the multiplication did not overflow:

```text
amount × sqrtPX96 = product
product / amount = sqrtPX96
```

So the check passes.

### Simple example

```text
amount     = 10
sqrtPX96   = 20

10 × 20 = 200

200 / 10 = 20
```

Therefore:

```text
20 == 20
```

The multiplication was valid.

---

# 6. What happens if multiplication overflowed?

Older Solidity arithmetic could overflow and wrap around.

For example, imagine a tiny `uint8`:

```text
maximum = 255
```

Now:

```text
200 × 2 = 400
```

But `uint8` cannot hold 400.

It wraps around:

```text
400 → 144
```

Then:

```text
144 / 2 = 72
```

instead of:

```text
200
```

Therefore:

```text
72 != 200
```

The check fails.

So:

```solidity
(product = amount * sqrtPX96) / amount == sqrtPX96
```

was a way to detect whether the multiplication produced the correct result.

---

# 7. Why does Uniswap NOT immediately revert here?

This is an important part of the function.

You might think:

> "If multiplication overflows, why not just revert?"

Because in the **add-token0 case**, the multiplication overflowing does not necessarily mean that the mathematical operation itself is invalid.

The same mathematical result can be calculated using an algebraically equivalent formula.

The function therefore does:

```text
try direct calculation
        ↓
if safe → use direct calculation
        ↓
if unsafe → use fallback calculation
```

This is intentional.

It is not simply an overflow safety check.

The overflow check also decides **which calculation path to use**.

---

# 8. Calculate `denominator`

If the product is valid:

```solidity
uint256 denominator = numerator1 + product;
```

Remember:

```text
numerator1 = L × 2^96
product    = amount × sqrtPX96
```

So:

```text
denominator
=
L × 2^96 + amount × sqrtPX96
```

This is the fixed-point-scaled representation of the denominator:

\[
L + amount\sqrt{P}
\]

---

# 9. Check the denominator

```solidity
if (denominator >= numerator1) {
```

This is another old-Solidity overflow check.

The calculation was:

```text
denominator = numerator1 + product
```

Since `product` is positive, a valid addition should produce:

```text
denominator > numerator1
```

If the addition overflows and wraps around, the result can become smaller than `numerator1`.

So:

```text
denominator >= numerator1
```

checks whether the addition behaved correctly.

---

# 10. Direct calculation

If both calculations are safe:

```solidity
return uint160(
    FullMath.mulDivRoundingUp(
        numerator1,
        sqrtPX96,
        denominator
    )
);
```

The important calculation is:

```text
(numerator1 × sqrtPX96) / denominator
```

with rounding **UP**.

Since:

```text
numerator1 = L × 2^96
```

this corresponds to:

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L + amount\sqrt{P}}
\]

The `FullMath.mulDivRoundingUp()` function is used because the intermediate multiplication can require more than 256 bits even when the final result fits.

The result is then converted to:

```solidity
uint160
```

---

# 11. The fallback calculation

If either:

```text
amount × sqrtPX96
```

overflowed,

or:

```text
numerator1 + product
```

overflowed,

the direct calculation is skipped.

The function reaches:

```solidity
return uint160(
    UnsafeMath.divRoundingUp(
        numerator1,
        (numerator1 / sqrtPX96).add(amount)
    )
);
```

This looks completely different from the original formula.

But it is **algebraically equivalent**.

Start with:

\[
\frac{L\sqrt{P}}
{L + amount\sqrt{P}}
\]

Divide the numerator and denominator by `√P`:

\[
\frac{L}
{L/\sqrt{P} + amount}
\]

So the fallback uses:

```text
numerator1
----------------------------
numerator1 / sqrtPX96 + amount
```

The multiplication:

```text
amount × sqrtPX96
```

has disappeared.

That is the entire point of the fallback.

---

# 12. The fallback is not an approximation

This is important.

The fallback is not:

> "Let's use a rougher formula because the first one failed."

It is an algebraically equivalent formula.

Original:

\[
\frac{L\sqrt{P}}
{L + amount\sqrt{P}}
\]

Rearranged:

\[
\frac{L}
{L/\sqrt{P} + amount}
\]

Both represent the same mathematical value.

The fallback simply avoids the dangerous multiplication.

---

# 13. Why `UnsafeMath.divRoundingUp()`?

The fallback ends with:

```solidity
UnsafeMath.divRoundingUp(...)
```

The normal Solidity division:

```solidity
a / b
```

rounds down because Solidity works with integers.

For example:

```text
10 / 3 = 3
```

But Uniswap needs this calculation rounded **UP**.

So:

```text
ceil(10 / 3) = 4
```

The helper performs:

```text
a / b
+
1 if a % b > 0
```

Therefore:

```text
10 / 3 → 4
12 / 3 → 4
```

The rounding direction is part of the correctness of the price calculation.

---

# 14. The `.add(amount)`

The original code contains:

```solidity
(numerator1 / sqrtPX96).add(amount)
```

Because the original library uses:

```solidity
using LowGasSafeMath for uint256;
```

`.add()` is the old Uniswap safe-math helper.

Conceptually it means:

```solidity
(numerator1 / sqrtPX96) + amount
```

In Solidity 0.8.20, normal checked arithmetic already protects this addition:

```solidity
(numerator1 / sqrtPX96) + amount
```

So the custom `LowGasSafeMath.add()` is not required merely for overflow protection.

---

# 15. The `else` branch — removing token0

Now:

```solidity
} else {
```

means:

```text
add == false
```

So token0 is being **removed**.

For token0 removal:

> Removing token0 moves the price UP.

The formula is:

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L - amount\sqrt{P}}
\]

Notice the critical difference:

```text
ADD:
L + amount × √P

REMOVE:
L - amount × √P
```

---

# 16. Calculate `product` again

```solidity
uint256 product;
```

Then:

```solidity
require(
    (product = amount * sqrtPX96) / amount == sqrtPX96 &&
    numerator1 > product
);
```

There are **two checks** here.

---

# 17. Check 1 — multiplication did not overflow

```solidity
(product = amount * sqrtPX96) / amount == sqrtPX96
```

This is the same old overflow-detection check used in the add branch.

It verifies that:

```text
amount × sqrtPX96
```

was calculated correctly.

---

# 18. Check 2 — `numerator1 > product`

```solidity
numerator1 > product
```

This is extremely important.

The denominator is going to be:

```solidity
numerator1 - product
```

So we need:

```text
numerator1 > product
```

Otherwise the subtraction would produce:

```text
0
```

or become mathematically invalid.

Remember:

```text
numerator1 = L × 2^96
product    = amount × sqrtPX96
```

So conceptually the condition is:

\[
L > amount\sqrt{P}
\]

This guarantees that the denominator remains positive.

---

# 19. Why is the condition `>` and not `>=`?

Because:

```text
numerator1 == product
```

would give:

```text
numerator1 - product = 0
```

Then the formula becomes:

\[
\frac{L\sqrt{P}}{0}
\]

which is invalid.

Therefore the code requires:

```solidity
numerator1 > product
```

not:

```solidity
numerator1 >= product
```

---

# 20. Calculate the denominator for removal

```solidity
uint256 denominator = numerator1 - product;
```

Conceptually:

\[
L - amount\sqrt{P}
\]

after accounting for the Q96 scaling.

---

# 21. Calculate the new price

```solidity
return FullMath
    .mulDivRoundingUp(
        numerator1,
        sqrtPX96,
        denominator
    )
    .toUint160();
```

This calculates:

\[
\sqrt{P_{new}}
=
\frac{L\sqrt{P}}
{L - amount\sqrt{P}}
\]

and rounds UP.

Then:

```solidity
.toUint160()
```

safely converts the result to `uint160`.

---

# 22. Why is there a fallback for ADD but not REMOVE?

This is one of the biggest design points in the function.

For addition:

```text
L + amount × √P
```

the intermediate multiplication can become enormous.

But even if:

```text
amount × √P
```

cannot safely fit into `uint256`, the mathematical operation can still be valid.

So Uniswap has an alternative:

\[
\frac{L\sqrt P}
{L + amount\sqrt P}
=
\frac{L}
{L/\sqrt P + amount}
\]

Therefore:

```text
overflow
   ↓
use algebraic fallback
   ↓
still calculate valid result
```

---

For removal:

```text
L - amount × √P
```

the operation is only valid when:

\[
amount\sqrt P < L
\]

And `L` is a `uint128`.

Therefore, when the removal is valid:

```text
amount × √P < L < 2^128
```

So the valid product is far below the `uint256` limit.

That means a valid removal cannot require a huge overflowing product.

If the multiplication overflows, the requested removal is not in the valid mathematical domain.

Therefore:

```text
REMOVE
   ↓
product must be valid
   ↓
product must be smaller than L
   ↓
otherwise revert
```

There is no useful fallback required.

---

# 23. Why `uint160(...)` in ADD but `.toUint160()` in REMOVE?

ADD uses:

```solidity
uint160(...)
```

while REMOVE uses:

```solidity
.toUint160()
```

At first this looks inconsistent.

The reason is the direction in which the price moves.

### ADD token0

Adding token0 makes:

```text
new √P < old √P
```

The old price is already a `uint160`.

So if the new value is smaller than the old value, it is automatically within the `uint160` range.

Example:

```text
old √P = 900
new √P = 800
```

If `900` fits into `uint160`, then `800` obviously fits too.

Therefore the direct cast is mathematically safe.

---

### REMOVE token0

Removing token0 makes:

```text
new √P > old √P
```

Now the new value can be larger than the existing `uint160` value.

Example:

```text
old √P = 900
new √P = 1200
```

We cannot simply assume that the new value fits into `uint160`.

So the code uses:

```solidity
.toUint160()
```

which explicitly checks the range.

Mental model:

```text
ADD:
new price goes DOWN
↓
old price already fits uint160
↓
new price must also fit
↓
direct cast is safe
```

```text
REMOVE:
new price goes UP
↓
new price could become too large
↓
must check
↓
.toUint160()
```

---

# 24. Why the old overflow checks matter when converting to Solidity 0.8.20

In Solidity 0.8.20:

```solidity
amount * sqrtPX96
```

normally reverts automatically if it overflows.

So it might look like we can simply delete:

```solidity
(product = amount * sqrtPX96) / amount == sqrtPX96
```

But that would change the behavior of this function.

The important distinction is:

> The old multiplication check is not only protecting the calculation. In the ADD branch, it decides whether to use the direct formula or the fallback formula.

So this would **not** be equivalent:

```solidity
uint256 product = amount * sqrtPX96;
```

with normal checked arithmetic followed by the old direct calculation.

If that multiplication overflows, Solidity 0.8.20 would revert immediately.

The original Uniswap implementation instead says:

```text
multiplication overflowed?
        ↓
do NOT revert
        ↓
use fallback
```

Therefore a Solidity 0.8.20 rewrite must deliberately preserve that behavior if the goal is to reproduce the original algorithm.

---

# 25. The important difference between ADD and REMOVE

The whole function becomes much easier to remember like this:

## Adding token0

```text
L + amount × √P
```

The intermediate value can become very large.

Therefore:

```text
try direct formula
        ↓
if intermediate is safe
        ↓
direct calculation

if intermediate is unsafe
        ↓
algebraic fallback
```

---

## Removing token0

```text
L - amount × √P
```

The operation is only valid when:

```text
amount × √P < L
```

Therefore:

```text
if multiplication invalid
        ↓
revert

if product >= L
        ↓
revert

otherwise
        ↓
calculate normally
```

# 27. Final mental model

The easiest way to remember Function 1 is:

> **This function answers: "If token0 changes by this amount, where does the square-root price move?"**

### Token0 added

```text
token0 enters
    ↓
sqrt price goes DOWN
    ↓
L + amount × √P
    ↓
direct formula if safe
    ↓
fallback formula if intermediate multiplication overflows
```

### Token0 removed

```text
token0 leaves
    ↓
sqrt price goes UP
    ↓
L - amount × √P
    ↓
amount × √P must be smaller than L
    ↓
otherwise revert
```

And always:

```text
round UP
```

because this function is specifically:

```solidity
getNextSqrtPriceFromAmount0RoundingUp()
```

# 29. What Function 1 does NOT do

This function does not:

- find the next initialized tick
- cross a tick
- update `liquidityNet`
- update pool storage
- execute the entire swap
- calculate the entire swap amount
- decide the whole swap path

It is only the mathematical calculator for **one token0 amount → one new sqrt price**.

`computeSwapStep()` uses this function when it needs to determine how token0 movement changes the price inside the current liquidity range.

---

# 30. One-line summary

> **`getNextSqrtPriceFromAmount0RoundingUp()` calculates the next Q64.96 square-root price after a token0 amount is added or removed, using the token0 price formula, rounding UP, with an algebraic overflow fallback for the ADD case and validity checks for the REMOVE case.**
