# 💰 `getNextSqrtPriceFromOutput()` Dissection

```solidity
function getNextSqrtPriceFromOutput(
    uint160 sqrtPX96,
    uint128 liquidity,
    uint256 amountOut,
    bool zeroForOne
)
    internal
    pure
    returns (uint160 sqrtQX96)
{
    require(sqrtPX96 > 0);
    require(liquidity > 0);

    // round to make sure that we pass the target price
    return zeroForOne
        ? getNextSqrtPriceFromAmount1RoundingDown(sqrtPX96, liquidity, amountOut, false)
        : getNextSqrtPriceFromAmount0RoundingUp(sqrtPX96, liquidity, amountOut, false);
}
```

---

# 🎯 First: What Is This Function's Job?

The previous function was:

```text
getNextSqrtPriceFromInput()
```

That meant:

> **We know how much input the trader is giving. Calculate how far the price moves.**

This function is the opposite:

```text
getNextSqrtPriceFromOutput()
```

That means:

> **We know how much output the trader wants. Calculate how far the price must move to produce that output.**

So:

```text
Exact Input
    ↓
amountIn is known
    ↓
calculate next price
```

versus:

```text
Exact Output
    ↓
amountOut is known
    ↓
calculate next price
```

This distinction is extremely important.

---

# 🧩 Function Signature

```solidity
function getNextSqrtPriceFromOutput(
    uint160 sqrtPX96,
    uint128 liquidity,
    uint256 amountOut,
    bool zeroForOne
)
    internal
    pure
    returns (uint160 sqrtQX96)
```

Let's go one by one.

---

# `sqrtPX96`

```solidity
uint160 sqrtPX96,
```

This is the **current sqrt price**.

Conceptually:

```text
sqrtPX96
    ↓
Current sqrt price
```

The function starts from this price and calculates:

```text
Current price
      ↓
move price enough to produce amountOut
      ↓
Next sqrt price
```

Remember:

```text
sqrtPX96 = √P × 2^96
```

---

# `liquidity`

```solidity
uint128 liquidity,
```

This is the **active liquidity** available for this price movement.

It determines how much the price must move to produce the requested output.

For example, for token1:

```text
Δ√P = amount / liquidity
```

So if the requested output increases, the required price movement increases.

---

# `amountOut`

```solidity
uint256 amountOut,
```

This is the **amount of output token we want to receive**.

This is the key difference from the previous function.

Previously:

```text
amountIn
```

Now:

```text
amountOut
```

For example:

```text
amountOut = 100
```

means:

> We need the price to move enough to produce 100 units of output.

The function then works backward from that requested output to calculate the required next sqrt price.

---

# `zeroForOne`

```solidity
bool zeroForOne
```

This again tells us the swap direction.

```text
zeroForOne = true
    ↓
token0 → token1
```

and:

```text
zeroForOne = false
    ↓
token1 → token0
```

But notice something important:

The **output token changes** depending on the direction.

| `zeroForOne` | Swap | Input | Output |
|---|---|---|---|
| `true` | token0 → token1 | token0 | token1 |
| `false` | token1 → token0 | token1 | token0 |

So when we know `amountOut`, we have to determine:

> **Which token is being removed from the pool?**

That determines which lower-level function we use.

---

# `internal`

```solidity
internal
```

Same as before.

This function is only callable internally by the contract/library system.

It is not directly callable by an external user.

---

# `pure`

```solidity
pure
```

The function does not read or modify blockchain state.

Everything required for the calculation is supplied as arguments:

```text
sqrtPX96
liquidity
amountOut
zeroForOne
```

It simply calculates and returns the next sqrt price.

---

# `returns (uint160 sqrtQX96)`

```solidity
returns (uint160 sqrtQX96)
```

It returns the **next sqrt price**.

We have:

```text
sqrtP
    ↓
current sqrt price

sqrtQ
    ↓
next sqrt price
```

So:

```text
sqrtPX96 → current
sqrtQX96 → next
```

---

# 🛡️ First Check

```solidity
require(sqrtPX96 > 0);
```

This ensures the current sqrt price is valid.

The sqrt price cannot be zero.

Why?

Because the underlying token0 price calculations involve the sqrt price in the denominator.

For example:

```text
1 / √P
```

So:

```text
√P = 0
```

would create invalid mathematics.

Therefore:

```text
sqrtPX96 > 0
```

must be true.

If not:

```text
revert
```

---

# 🛡️ Second Check

```solidity
require(liquidity > 0);
```

There must be active liquidity.

Otherwise calculations such as:

```text
amount / liquidity
```

would divide by zero.

More fundamentally:

> There must be usable liquidity for the requested output to be produced.

So:

```text
liquidity > 0
```

is required.

---

# 🎯 The Important Comment

```solidity
// round to make sure that we pass the target price
```

Compare this with the previous function.

### Input function

```solidity
// round to make sure that we don't pass the target price
```

### Output function

```solidity
// round to make sure that we pass the target price
```

That difference is **very important**.

---

# 🧠 Why Does Exact Output Need To "Pass" The Target?

With Exact Output, the trader says:

> "I want this much output."

The pool therefore needs to move the price **far enough** to generate that requested output.

If rounding makes the price stop before the required point, the pool would not produce enough output.

So the rounding direction is chosen to make sure the calculation **passes the target price rather than stopping short**.

---

# 🔥 Now The Core Return Statement

```solidity
return zeroForOne
    ? getNextSqrtPriceFromAmount1RoundingDown(
        sqrtPX96,
        liquidity,
        amountOut,
        false
    )
    : getNextSqrtPriceFromAmount0RoundingUp(
        sqrtPX96,
        liquidity,
        amountOut,
        false
    );
```

Again, this is a **ternary operator**.

It means:

```text
if zeroForOne == true
    use first function

else
    use second function
```

But this time, notice that the functions are **reversed compared with `getNextSqrtPriceFromInput()`**.

That is the key thing to understand.

---

# 🟥 Case 1 — `zeroForOne == true`

```text
token0 → token1
```

Therefore:

```text
Input  = token0
Output = token1
```

We know:

```text
amountOut
```

So the output we care about is:

```text
token1
```

Therefore we need the function that handles **token1 being removed from the virtual reserves**:

```solidity
getNextSqrtPriceFromAmount1RoundingDown(
    sqrtPX96,
    liquidity,
    amountOut,
    false
)
```

Notice:

```text
false
```

for `add`.

Why?

Because the trader is receiving token1.

So from the pool's perspective:

```text
Pool → Trader
```

Token1 is leaving the pool.

Therefore:

```text
add = false
```

---

# 🧠 Follow The Tokens

For:

```text
zeroForOne = true
```

we have:

```text
token0 → token1
```

Trader:

```text
gives token0
receives token1
```

Pool:

```text
receives token0
gives token1
```

Therefore:

```text
token0 → add
token1 → remove
```

Since `amountOut` refers to token1:

```solidity
getNextSqrtPriceFromAmount1RoundingDown(..., false)
```

Exactly.

---

# 📉 What Happens To Price?

For token1 removal:

```text
remove token1
    ↓
sqrt price goes DOWN
```

So:

```text
zeroForOne = true
    ↓
token0 → token1
    ↓
token1 is output
    ↓
token1 is removed
    ↓
sqrt price ↓
```

Everything lines up.

# 🔥 Why Are The Functions Reversed?

This is the biggest thing to understand.

In `getNextSqrtPriceFromInput()` we had:

```text
zeroForOne = true
    ↓
token0 is INPUT
    ↓
use Amount0 function

zeroForOne = false
    ↓
token1 is INPUT
    ↓
use Amount1 function
```

So:

```text
INPUT
 ↓
Which token is entering?
 ↓
Use that token's ADD calculation
```

But here we have:

```text
getNextSqrtPriceFromOutput()
```

So:

```text
OUTPUT
 ↓
Which token is leaving?
 ↓
Use that token's REMOVE calculation
```

That's why the functions are reversed.

# 🧩 Side-by-Side Comparison

## Exact Input

```text
getNextSqrtPriceFromInput()
```

We know:

```text
amountIn
```

So follow the **input token**:

```text
token0 input → Amount0 + true
token1 input → Amount1 + true
```

## Exact Output

```text
getNextSqrtPriceFromOutput()
```

We know:

```text
amountOut
```

So follow the **output token**:

```text
token1 output → Amount1 + false
token0 output → Amount0 + false
```

This is the whole reason the branches look reversed.

# 📊 Complete Table

| Swap direction | Input | Output | Function used | `add` | Price |
|---|---|---|---|---|---|
| `zeroForOne = true` | token0 | token1 | Amount1 | `false` | ↓ |
| `zeroForOne = false` | token1 | token0 | Amount0 | `false` | ↑ |

Compare that with Exact Input:

| Swap direction | Input | Output | Function used | `add` | Price |
|---|---|---|---|---|---|
| `zeroForOne = true` | token0 | token1 | Amount0 | `true` | ↓ |
| `zeroForOne = false` | token1 | token0 | Amount1 | `true` | ↑ |

calculator.

```text

```

calculator.

```text

```

# 🧠 The Most Important Connection

You already studied:

```text
getNextSqrtPriceFromAmount0RoundingUp()
```

and:

```text
getNextSqrtPriceFromAmount1RoundingDown()
```

Those functions answer:

> "What happens to the sqrt price when this specific token is added or removed?"

Now:

```text
getNextSqrtPriceFromInput()
```

asks:

> "Which token is the input?"

And:

```text
getNextSqrtPriceFromOutput()
```

asks:

> "Which token is the output?"

That's the abstraction.

# 🎯 Final Mental Model

```text
                    getNextSqrtPriceFromOutput()
                                │
                                │
                          Exact Output
                                │
                                ▼
                     "Which token leaves?"
                                │
                    ┌───────────┴───────────┐
                    │                       │
           zeroForOne = true      zeroForOne = false
                    │                       │
                    ▼                       ▼
             token0 → token1          token1 → token0
                    │                       │
                    ▼                       ▼
              output = token1         output = token0
                    │                       │
                    ▼                       ▼
                REMOVE                 REMOVE
                    │                       │
                    ▼                       ▼
             Amount1 function         Amount0 function
                    │                       │
                    ▼                       ▼
                 add=false              add=false
                    │                       │
                    ▼                       ▼
               price ↓                 price ↑
```

The one sentence to lock in:

> **`getNextSqrtPriceFromOutput()` starts with the known output amount, identifies which token is leaving the pool based on `zeroForOne`, and calls that token's price function with `add = false` to calculate the sqrt price required to produce that output.**

# 🧠 Final Connection Between Input and Output

```text
                    SWAP
                     │
            ┌────────┴────────┐
            │                 │
        Exact Input       Exact Output
            │                 │
            ▼                 ▼
         amountIn          amountOut
            │                 │
            ▼                 ▼
     Which token enters?  Which token leaves?
            │                 │
            ▼                 ▼
          ADD               REMOVE
            │                 │
            ▼                 ▼
     Use input token's    Use output token's
     price function       price function
```

So the clean mental model is:

> **Exact Input follows the token coming IN. Exact Output follows the token going OUT.**

And that is exactly why the two wrapper functions choose opposite lower-level functions.
